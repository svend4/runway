# Runway — design-brief: канон для писателей вики

> Рабочее ТЗ (не страница вики, без frontmatter). Версия 1.1 от 2026-10-04 (арбитраж канона: решения C-001…C-098, см. §13 и [canon-decisions.md](canon-decisions.md); места изменений помечены «(v1.1, C-NNN)»; числа G-001 не менялись). Автор: «Главный архитектор, часть A». Сводит [proposal-engine](../wiki/ideas/proposal-engine.md), [proposal-product](../wiki/ideas/proposal-product.md), [proposal-architecture](../wiki/ideas/proposal-architecture.md) и [red-team-critique](../wiki/ideas/red-team-critique.md) в один согласованный дизайн. **При расхождении с любым из четырёх документов приоритет у этого файла.** Расчёт по введённым правилам пользователя — не консультация (оговорка обязательна везде, где речь о налогах).

## 0. Как пользоваться и что обязательно

1. Все определения, имена полей, имена функций, значения по умолчанию и **числа сквозного примера G-001 (раздел 9)** берутся отсюда дословно. Числа примеров из трёх предложений («Датасет R», «Elena») **не использовать** — они остаются иллюстрациями на страницах `ideas/`. Исключение: «независимые векторы» из раздела 9.6 (округление, sinking, аннуитет, FX, дедупликация) — они не зависят от датасета и проверены.
2. Деньги — целые `amount_minor` + `currency`; даты — календарные (`EpochDay` в движке, `YYYY-MM-DD` на диске и в тексте). Ни float для денег, ни `Date`/таймзон в алгоритмах.
3. Названия кода: **snake_case одинаково в псевдокоде и в JS-экспортах** (`next_business_day`, не `nextBusinessDay`) — псевдокод и код сверяются по имени.
4. Вердикты, режимы и статусы — только слова из раздела 2.0 («словарь»). Запрещённые слова — раздел 10.
5. v1 — срез раздела 8. Всё, что помечено v1.1/v2, описывается в страницах в отдельном подразделе «Не в v1» (кратко, без противоречия срезу).
6. Идентификаторы: определяй только назначенные тебе (раздел 7); ссылаться можно на любые.
7. Внешние факты — только со ссылкой на `tools/*` относительной ссылкой и пометкой «(не подтверждено)», если источника нет. О Budget Guru — только заявления лендинга, политики и условий ([страница](../wiki/tools/budget-guru.md)): вход в приложение не выполнялся, функции не проверялись, аккаунтов нет; открывались только публичные страницы (лендинг, sitemap, robots.txt); различай «подтверждено как текст» и «проверено в работе» (v1.1, C-092).

### D-01 Сетка времени, `close`, `trough`

Параметры запроса: `as_of: EpochDay` (явный; «сегодня» берётся с устройства и фиксируется в `inputs_hash`), `horizon_end`, `mode`, `scenario_id`. Сетка — дни `as_of .. horizon_end` включительно, `N = horizon_end − as_of + 1`, индекс `i = d − as_of`.

```pseudo
bal = opening_minor              # остаток после всех posted с date ≤ as_of, от последнего якоря (D-22)
for i in 0 .. N−1:               # d = as_of + i
  out_i = Σ e.amount_minor  по e ∈ events(d), e.amount_minor < 0     # ≤ 0
  in_i  = Σ e.amount_minor  по e ∈ events(d), e.amount_minor > 0     # ≥ 0
  trough[i] = bal + out_i        # «расходы раньше доходов» внутри дня
  bal       = bal + out_i + in_i
  close[i]  = bal                # остаток на конец дня
```

**Горизонт** (`horizon`): `horizon_end = as_of + horizon_days` (по умолчанию 180 дней); события за горизонтом в ряд не входят, а ответы о более поздних датах — «в горизонте нет».

`events(d)` — эффективные события режима и сценария (D-04, D-14): слои `planned` + `hypothetical`, без статусов `matched/skipped/cancelled`, только счета `operating`; переводы между operating-счетами исключены (нетто 0); суммы переведены в валюту решения (D-20). `posted` с `date > as_of` — ошибка валидации. Planned на дату `as_of` ещё «впереди» (входит в день 0), posted уже в `opening`. Инвариант: `close[i] − close[i−1] = out_i + in_i`, `close[−1] := opening`.

### D-02 Узкая точка (narrowest point)

`narrowest_point(series, a, b) = { date: первый d ∈ [a,b] с минимальным trough[d], amount_minor: min trough }` — при равенстве побеждает ранняя дата. Q1 и волны используют физический `trough` (хватит ли денег на счетах). Для вердиктов используется «свободная узкая точка» `narrowest_free` — то же по ряду `free` (D-08). Слово «узкая точка» без уточнения = `trough`.

### D-03 Буфер (buffer)

`B = params.buffer_minor ≥ 0` в валюте решения; показывается в каждом ответе. Подсказка: `buffer_hint = round_div(buffer_hint_days · Σ|amount_minor|, 90)` по `posted` исходящим за 90 дней до `as_of`, кроме помеченных `exceptional`, переводов между своими счетами, налоговых платежей, аллокаций в резервы и ног обмена валют (v1.1, C-022; §12 X6); нет истории — `null`. Тот же набор исходящих — основа порога волны по умолчанию (`outflow_90`, `buffer_hint`, `default_wave_threshold` в `timeline.mjs`). Буфер не пересчитывается из будущих событий (иначе сдвиг платежа на день переворачивает вердикт). Q3 и «можно потратить» требуют **заданного** буфера (v1.1, C-018).

### D-04 Режимы расчёта: `plan`, `worse`, `expected`

Режим — **пакет параметров обработки дат**, не сценарий (сценарий — набор правок данных, D-14). Эффективная дата события:

```pseudo
base(e)  = max(e.plan_date, as_of)     # (v1.1, C-005) plan_date — дата события после правок сценария и до режима, без зажима; просроченное и ещё не просроченное (в пределах grace) вхождение «в прошлом» считается на as_of
# status ∈ {matched, skipped, cancelled} в поток не входят (D-06)
eff_date(e, plan)     = base(e)
eff_date(e, worse)    = base(e) + (e.kind == income ? (e.delay_days_worse ?? params.worse.income_delay_days) : 0)    # (v1.1, C-010) kind, не is_income
eff_date(e, expected) = base(e) + lag_p50(flow_key(e))   если n_obs ≥ 10, иначе как plan      # v2
если eff_date > horizon_end — событие вне горизонта (в ряд не входит)
```

Правила: расходы и обязательства даты не сдвигают ни в одном режиме; суммы одинаковы (`worse` не уменьшает часы и не увеличивает траты — это отдельные «чипы» сценария: `hours_min`, `fx_shock`, `expense_uplift`); внутридневной порядок «расходы раньше доходов» — во всех режимах. Свойство: для любого `i` `trough_worse[i] ≤ trough_plan[i]` (сдвиг дохода вправо никогда не повышает остаток). **Композиция со сценарием (v1.1, C-009):** сначала операции сценария меняют даты данных (`plan_date`), затем режим добавляет свой сдвиг — накопление: `delay_income 7` в `worse` даёт 7 + 14 = 21 день; `delay_income 14` в `plan` равен ряду `worse`. `build_events` кладёт в результат служебное `plan_date` (дата до режима, без зажима), а `date` — эффективную дату режима. Ключ потока для `expected`: `flow_key(e) = counterparty_id ?? stream_id ?? rule_id ?? cash_event_id` (C-025).

| Факт | `posted` | подтверждённое движение денег; исправляется только компенсирующим событием журнала | нет |
| План | `planned` | вхождения правил (виртуальные, не хранятся), разовые плановые записи, плановые доходы потока часов | да |
| Гипотеза | `hypothetical` | принадлежит сценарию (покупка, сдвиг, «что если»), в журнал фактов не попадает | да, внутри сценария |

`state(as_of) = opening + Σ posted после якоря`; `forecast = state + Σ planned_residual + Σ hypothetical(scenario)`; `planned_residual` — план за вычетом сопоставленного факта (D-06).

### D-06 Статус вхождения и сопоставление

```pseudo
expected --(факт найден по match)--> matched
expected --(date + grace_days < as_of)--> overdue
overdue  --(факт найден)--> matched
любой, кроме matched --(пользователь)--> skipped | cancelled
перенос = override(rule_id, nominal_date, date')  # статус остаётся expected
```

```pseudo
match(F, P):  тот же счёт, знак, валюта
   и  −win ≤ F.date − P.date ≤ +win           # win = match.window_days
   и  |F.amount − P.amount| · 10000 ≤ tol_bp · |P.amount|   # или внутри [amount_min, amount_max] плана
кандидатов ровно 1 и отклонение ≤ tol → автосопоставление;  кандидатов > 1, либо tol < отклонение ≤ 2·tol → очередь подтверждения («возможный двойник»);  отклонение > 2·tol → не сопоставлено
частичный факт: P.residual = P.amount − Σ F  (остаётся expected)
```

Инвариант после матча: при `d ≥ max(F.date, as_of)` баланс меняется ровно на `F.amount − P.amount`. Расчёт — ALG-13.

### D-07 Резерв (конверт) и перевод — разные вещи

| | Перевод (`transfer`) | Резерв / конверт (`Reserve`) |
|---|---|---|
| Что делает | двигает деньги между счетами: два `CashEvent` с общим `transfer_id`, сумма ног 0 | **виртуально** помечает часть денег операционных счетов как «не свободные»; `CashEvent` не создаёт |
| Влияние на `close`/`trough` | между operating-счетами нетто 0; на неоперационный — расход | нет |
| Влияние на `free` | нет (кроме ухода денег из operating) | уменьшает `free` на `R(t)` (D-08) |
| Примеры | 500 € с карты на накопительный счёт | налоговый конверт 20 % от поступлений; sinking «страховка» |

Резерв пополняется **аллокациями** (при поступлении по правилу; по расписанию взносов; вручную) и освобождается **релизом** при платеже, привязанном к резерву: `released = min(funded, |amount|)`; превышение (`true_up`) уходит из свободных денег. `Reserve.backed_by_account_id` (резерв физически лежит на неоперационном счёте) зарезервирован: в v1 всегда `null`, такие резервы в `R` не входят (деньги уже вне operating). Если пользователь физически переводит деньги резерва на отдельный счёт, он оформляет это переводом и привязывает резерв к счёту (v1.1) — иначе деньги вычтутся дважды.

### D-08 Свободный остаток (`free`)

```pseudo
# для каждого резерва r: funded_r — накопленная сумма; за день i:
funded_r += contributions_r(i)                         # взносы расписания sinking (виртуальные)
funded_r −= min(funded_r, Σ |платежей, привязанных к r, в день i|)     # релиз
R_trough[i] = Σ_r funded_r                             # резерв «на момент до доходов дня»
funded_r += Σ allocations от доходов дня i (по TaxRule, D-17)
R_close[i]  = Σ_r funded_r
free[i]     = trough[i] − R_trough[i]                  # может быть < 0: деньги есть, но они «чужие»
```

Аллокации от дохода дня `i` попадают только в `R_close` (иначе `trough` и резерв берутся в разном порядке и дают искусственный минус). Без резервов `free = trough`. Это **единственный** ряд для вердиктов, `S_max`, `earliest_date` и `STS`. **Начальное состояние резерва (v1.1, C-020):** в `reserve_series` входит `funded_open = funded_start + Σ записанных аллокаций с funded_as_of < date ≤ as_of` (функция `reserve_open`, в том числе аллокация по `posted`-доходу на `as_of`); будущие аллокации — только `date ≥ as_of` и без тех, чей `allocation_id` уже записан (идемпотентность). Проверка «валюта резерва и событий = валюте решения» — при построении и записи `reserve.set`, а не внутри функций ряда (C-098). Проверенная в расчётах инвариантность: резерв не меняет `close` и `trough`.

### D-09 Волна платежей (payment wave)

Обязательство — `CashEvent` с `is_obligation = true`, `amount_minor < 0`, `|amount_minor| ≥ θ` (`wave.threshold_minor`). Оценочные траты (`is_estimate`) и события ниже `θ` — фон, в волны не входят (но участвуют в потоках метрики).

```pseudo
O = obligations отсортированы по (eff_date, amount_minor, id)
for e in O:
   если w существует и e.date − w.end ≤ g и e.date − w.start < S:  w.add(e); w.end = e.date
   иначе: новая волна w = {start: e.date, end: e.date, events: [e]}
# g = wave.gap_days (3), S = wave.max_span_days (10)
```

Волна — это только состав и даты. Ручные правки (`WaveOverride`: `split`, `merge`, `pin`) применяются после алгоритма и переживают пересчёт. Различие режимов: в `worse` обязательства даты не меняют, поэтому состав волн в `plan` и `worse` совпадает. **Ручные правки (v1.1, C-014):** `split` режет волну перед указанным событием; `merge` объединяет волны с указанными событиями; `pin` извлекает события (и события в `pin_range`) в отдельную волну; порядок применения — порядок эффективных записей журнала (`seq`); ссылка на исчезнувшее событие — `W_OVERRIDE_STALE`.

### D-10 Метрики волны: нужно, покрытие, дефицит

```pseudo
window_w  = [w.start, e_ext],  e_ext = max(w.end, next_income_date(mode, после w.end) − 1)   # нет поступлений → horizon_end
cash_w    = close[w.start − 1]                         # деньги на конец дня перед волной (opening, если start = as_of)
R_w       = cash_w − min_{d ∈ window_w} trough[d]      # пиковая просадка в окне, включая фон и доходы окна
need_w    = R_w + B                                    # «нужно к волне»
gap_w     = max(0, need_w − cash_w) = max(0, B − min_{d∈window_w} trough[d])
coverage_pm = floor_div(1000 · cash_w, need_w)         # ‰, need_w > 0
reserved_w = R_close[w.start − 1]                      # справочно: сколько из cash_w уже зарезервировано
```

Смысл: сколько денег нужно иметь к началу волны, чтобы пережить её и дожить до следующего поступления с запасом `B`. Метрика считается по физическим деньгам; резервы показываются рядом справочно. **Уточнения (v1.1, C-012, C-013, C-022):** `cash_w` и `reserved_w` при `start = as_of` берутся из `series.opening_minor` и `series.reserve_opening_minor`; при `cash_w < 0` `coverage_pm` — отрицательное целое (пол), подпись — на экране; окно заканчивается на ближайшем поступлении **своего режима**, поэтому «`need_w` и `gap_w` в `worse` не лучше `plan`» верно только при `next_income_day(worse) ≥ next_income_day(plan)` (для `trough`, `free`, `S_max` монотонность безусловна).

### D-11 «Могу ли я это купить?» — три ответа

Покупка `Purchase = { parts: [(date_k, amount_k > 0)] }` в валюте решения, одно событие — частный случай. Для режима `m ∈ {plan, worse}`:

```pseudo
cum[i]         = Σ amount_k по частям с date_k ≤ as_of + i
free_after_m[i]= free_m[i] − cum[i]
m_after_m      = min_i free_after_m[i]                 # и дата argmin
margin_m       = m_after_m − B;   delta_m = min_i free_m[i] − m_after_m
cash_gap_m     = min_i (trough_m[i] − cum[i]) < 0

verdict = NO      если m_after_plan  < 0
        = TIGHT   если m_after_plan  < B
        = FRAGILE если m_after_worse < B            # plan уже ≥ B
        = OK      иначе
флаги: worse_gap = (m_after_worse < 0);  cash_gap = cash_gap_worse;  baseline_below_buffer = (min_i free_worse[i] < B)    # (v1.1, C-015) флаги — по более строгому режиму worse; по режимам — из by_mode
baseline_below_buffer_m = (min_i free_m[i] < B)       # (v1.1, C-015) признак режима m: при нём S_max_m(D) = 0, earliest_m = null;
                                                      # baseline_worse ⇒ вердикт ≠ OK;  baseline_plan ⇒ вердикт ∈ {TIGHT, NO}
```

Три ответа: **(а)** `verdict` + `narrowest_free` после покупки в обоих режимах + `margin`, `delta`; **(б)** максимальная сумма разовой покупки в день `D`:
`S_max_m(D) = baseline_below_buffer_m ? 0 : max(0, M_m[idx(D)] − B)`, где `M_m[i] = min_{j ≥ i} free_m[j]` (суффиксный минимум, O(N)); **(в)** самая ранняя дата для суммы `S`: `earliest_m(S, not_before) = baseline_below_buffer_m ? null : min{ d ≥ not_before : M_m[idx(d)] − S ≥ B }`, нет — `null` («в горизонте нет»). **(v1.1, C-015)** Защитный признак делает границы безусловными: `OK ⇔ S ≤ S_max_worse(D)`; `FRAGILE ⇔ S_max_worse < S ≤ S_max_plan`; без него суффиксный минимум не видел бы просадки `free` до даты покупки (проверено перебором на 20 000 случайных рядов; на G-001 `min free` 93500 / 71000 ≥ B, числа не меняются). **Ответ-объединение (v1.1, C-017):** `{kind: ok, …, warnings[], beyond_horizon_minor}` · `{kind: insufficient_data, reason, reasons[]}` · `{kind: outside_horizon, horizon_end}`; при `beyond_horizon_minor > 0` подпись вердикта обязана содержать «не все платежи учтены: X за горизонтом»; для покупки из нескольких частей `s_max` и `earliest` в v1 — `null`; даты частей в прошлом зажимаются на `as_of` (`W_DATE_CLAMPED`), части позже `horizon_end` отбрасываются (`W_PART_BEYOND_HORIZON`). **Гейт (v1.1, C-018)** — один для Q3 и «можно потратить»: `insufficient_data`, если `readiness < ready.q3`, либо уровень свежести `block` (`stale`/`no_anchor`, D-22), либо `buffer_minor` не задан (`no_buffer`), либо есть правило в статусе `disabled` (`rule_disabled`, D-17). Главные числа (б) и (в) — для `headline_mode` (`worse`), число режима `plan` показывается рядом. Подписи вердикта нейтральны («в заданных допущениях минимум после покупки — X при буфере Y»). Это ликвидность по правилам пользователя, не совет «покупать». Монотонность (property-тесты): `verdict` не улучшается с ростом `S`; `S_max_m(D)` не убывает с ростом `D`; `S_max_worse ≤ S_max_plan`. Алгоритм — ALG-04.

### D-12 Safe-to-spend («можно потратить»)

```pseudo
STS_m(T) = max(0, min_{i ≤ idx(T)} free_m[i] − B)
T по умолчанию = min{ eff_date(headline_mode, e) : e — доход в статусе expected/overdue, eff_date ≥ as_of }; нет такого — min(as_of + 30, horizon_end)
варианты T: «конец месяца» · «через N дней» · дата · horizon_end
```

`STS_m(horizon_end) = S_max_m(as_of)` (свойство для тестов). Если `min free − B < 0`, показывается не «0», а «до буфера не хватает X» (`X = B − min free`; метрика `short_to_buffer`, «с учётом резервов»). ALG-11. **(v1.1, C-018, C-019, C-058)** «Можно потратить» проходит тот же гейт, что Q3 (D-11); результат `safe_to_spend = {sts, short_to_buffer, at, min_free, sts_horizon}`, где `sts_horizon = STS(horizon_end) = S_max(as_of)`; если `sts_horizon < sts`, экран добавляет строку «до конца горизонта (дата) — X». Вариант **G-001-late** (§9.9) — golden-вектор, где `STS(T)` и `STS(horizon_end)` различаются.

### D-13 Q1: «хватит ли к дате D»

```pseudo
Q1_m(D, B) = { min: m = min_{i ≤ idx(D)} trough_m[i],  at: first argmin,
               ok_cash: m ≥ 0,  ok_buffer: m ≥ B,
               first_breach: min d: trough_m[d] < 0   (или null),

runway_with = первый d: trough[d] < 0 на всём горизонте (иначе null: «за горизонтом»);   runway_without = то же по ряду без доходов    # (v1.1, C-006) по trough, не по close
```

Q1 — свойство *пути* (минимум на `[as_of, D]`), а не точки на `D`; `first_breach` и `first_buffer_breach` ищутся на пути `[as_of, D]` (v1.1, C-006). Метрика `need = max(0, B − m)` называется «не хватает до буфера (деньги на счетах)» и не смешивается с `gap_w` и `short_to_buffer` (C-067). ### D-14 Сценарий и режим

Режим (D-04) — параметры обработки дат; **сценарий** (`Scenario`) — именованный набор операций над данными без копирования: `delay_income{event_ref, days}`, `add_purchase{parts}`, `add_flow`, `remove_flow{event_ref}`, `shift_flow{event_ref, days}`, `set_amount{event_ref, amount_minor}`; в v1.1 `fx_shock{currency, bp}`, `hours{stream_id, minutes}`. Результат — функция `(данные, режим, сценарий)`; **порядок: сценарий правит данные, затем режим добавляет сдвиг** (D-04, v1.1, C-009). Базовый сценарий пуст. Гипотезы не пишутся в журнал фактов. Аддитивность: `proj(base ⊕ Δ) = proj(base) + proj(Δ)` для дельт-потоков. **Ссылка `event_ref` (v1.1, C-008)** — одна строка: сначала точное совпадение `cash_event_id`/`occ_key`, затем `rule_id`/`stream_id`; нет совпадения — `E_SCHEMA`; `delay_income` и `set_amount` требуют одно событие, `shift_flow` и `remove_flow` допускают `rule_id` (все вхождения в окне). `apply_scenario(events, scenario, ctx)`, `ctx = {as_of, horizon_end, calendars, default_account_id}`; покупка — `purchase_to_events(purchase, account_id, scenario_id?)` в `timeline.mjs`. Налоговая ставка не операция сценария: «а что если 22 %» — предпросмотр правки правила без записи (C-073).

### D-15 Диапазон P10/P50/P90 (v2)

Для величины `x` по `n_paths` путям Монте-Карло (число путей — `n_paths`, число наблюдений — `n`, число дней сетки — `N`; v1.1, C-061): `P_q = sorted_asc[ ceil(q·n_paths/100) − 1 ]` (nearest-rank); низкие значения «хуже» (остатки). Подача: веер 80 % = `[P10, P90]`; при малом числе наблюдений параметров (`n_eff < 20`) вместо процентов — «в k из n прошлых случаев»; при `n_eff ≥ 20` — «≈ p % (95 %: lo–hi %)» по интервалу Уилсона (ALG-13), границы в ‰ округляются к ближайшему (C-049). `n_eff = min n_obs` по источникам на данных (`lag`, `ratio`, `fx`; `hours` данных не использует); для одного источника с ≤ 64 наблюдениями — полный перебор наблюдений (C-048). При `ceil(q·n/100) = n` подпись «наибольшее из n», при `= 1` и `q < 50` — «наименьшее из n».

### D-16 Вероятность разрыва (v2)

`p_gap_any = #{p: min_i trough_p[i] < 0} / n_paths` — **не** `max_i p_gap[i]`. Вероятностный Q3: `p_fail(S) = #{p: min_{i ≥ idx(D)} (free_p[i] − S) < B} / n_paths`; допуск риска `α`: `OK(α) ⇔ nearest_rank_α(m_p) − S ≥ B`, где `m_p = min_{i≥idx(D)} free_p[i]` (квантиль минимумов путей, не минимум квантилей). Пути используют общие случайные числа (CRN), `seed = H(engine_version, inputs_hash, user_seed)`; `H` — свёртка `mix32` по `engine_version`, 64 hex-знакам `inputs_hash` (без префикса) и `user_seed mod 2^32`, без `sha256` (v1.1, C-050).

### D-17 Налоговая аллокация

`allocation = mul_div(base_minor, rate_bp, 10000, rule.rounding)`, `base = gross` дохода, подпадающего под `applies_to`; правило выбирается по дате дохода: `rule_at(rule_id, d)` — версия с `valid_from ≤ d < valid_to` (при наличии нескольких — с наибольшим `recorded_at`). **(v1.1, C-016)** Для `planned`-дохода `d = base(e) = max(plan_date, as_of)` — **не зависит от режима**, поэтому аллокации в `plan` и `worse` равны, а при `Σ rate_bp ≤ 10000` (валидация: пустой `applies_to` — ошибка; `Σ` ставок на одно поступление `> 10000` — `E_RULE_INVALID`, C-032) безусловно `free_worse ≤ free_plan` и `S_max_worse ≤ S_max_plan`; для `posted` — фактическая дата. `applies_to.stream_ids` сопоставляется с `e.stream_id`, `tags` — с `e.tag` (C-025). Аллокация хранит `rule_version`: смена ставки прошлое **не переписывает**. Платёж, привязанный к резерву, высвобождает `min(funded, |amount|)`. **Срок годности правила (v1.1, C-023; единая формула вместо расхождения REQ-067 и X8):** `age = today − reviewed_at` (календарные дни); `fresh` при `age ≤ ttl`, `stale` при `ttl < age ≤ 2·ttl`, `disabled` при `age > 2·ttl`; без `reviewed_at`/`ttl_days` — `fresh` с пометкой «проверка не отмечена». Правило `disabled` (C-024): расчёт `free` продолжается (резерв остаётся), в `Result.warnings` — `W_RULE_DISABLED`, зависящие числа (`reserved`, `free`, `STS`, вердикты Q3) интерфейс заменяет текстом «правило не подтверждено с <даты>» через гейт D-11; Q1 и волны не затронуты. Налоговые числа — расчёт по правилам пользователя, не консультация. ALG-06.

### D-18 Взнос sinking fund

`c_k = min(ceil_div(rem_k, n − k), rem_k)`, `rem_0 = target − funded`, `rem_{k+1} = rem_k − c_k`, `k = 0..n−1`; `n` — число дат взносов строго **до** срока цели (`cadence`: по умолчанию 1-е число месяца). Сумма взносов равна цели, разброс соседних ≤ 1 minor. Режимы: `refill_to_target` (пересчёт каждый период) и `fixed` (взнос задан, цель достигается/не достигается — показывается разница). Пул делится `split_largest_remainder`. Взносы — виртуальные аллокации, не расходы. ALG-05. **(v1.1, C-030, C-059)** Плановые взносы в журнал автоматически не пишутся: `funded_open` растёт только от записанных аллокаций (`source = schedule`, подтверждение пакетом), пересчёт расписания от текущего `funded` даёт «догон», до подтверждения — `W_RESERVE_BEHIND`. После платежа в срок остаток резерва **остаётся** до ручной отрицательной аллокации (`source = manual`; `W_RESERVE_RESIDUAL`); резерв с прошедшим `due_date` без привязанного платежа — `W_RESERVE_OVERDUE`. Частота взносов в v1 — только `M`.

### D-19 Доход по ставке и часам

`gross = mul_div(rate_minor, min(m,T)·10000 + max(0, m − T)·mult_bp, 60·10000, rounding)` (без переработки — `mul_div(rate_minor, m, 60, rounding)`), `m` — минуты за период, `T` — порог переработки (если есть; относится к периоду потока, C-027). **Одно** округление за период (v1.1, C-028: формула с двумя `mul_div` отменена; `weighted_minutes` — справочная дробь). `rounding` — `params.rounding` (C-029). Для `biweek` обязательна `cutoff.anchor` (C-026). Ничья: `m = 2401`, `T = 2400`, ставка 3000, `mult_bp = 12500` → 120062,5 → `half_even` 120062, `half_up` 120063. Дата выплаты: `shift_by_policy(period_end + pay_lag_days, weekend, calendar)`. Диапазон дохода: `gross(min_minutes)`, `gross(exp_minutes)`, `gross(max_minutes)`; в расчёте участвует `exp`; `min` — чип сценария `hours_min`. «Недоработка» = `plan_to_date − actual_to_date` в минутах; эффект = `mul_div(недоработка, rate_minor, 60)`. Пересчёт ожидаемого дохода по темпу (`rho = 1`) в v1 — отображаемая оценка, `exp_minutes` не меняет (C-033). ALG-07.

### D-20 Курс, валюта решения, крипта

Обмен между собственными операционными счетами (в том числе в разных валютах) в агрегат решения не входит — обе ноги исключены, остатки счетов оцениваются по `spot`; разница выведенного курса обмена и `spot` показывается справочно («курсовая разница обмена») и в `trough` не входит. Курс `FxRate{base, quote, num, den}`: `1 base (основная единица) = num/den quote`. Перевод минорных сумм с разными экспонентами:
`convert_minor(a, base_exp, quote_exp, num, den, mode) = round_div(a · num · 10^quote_exp, den · 10^base_exp, mode)` (BigInt; результат — safe integer). Все умножения на курс — через `mul_div`. Политика курса v1: `spot` — последний введённый курс пары с датой ≤ `as_of` применяется ко всем будущим событиям; операция в чужой валюте хранит обе ноги и **выведенный** курс `leg_b/leg_a`. Сценарий курса `fx_shock{bp}` — v1.1. Крипта: счёт `kind = crypto`, `exponent = 8`; в `operating` не входит; в запас идёт `liquidity_bp / 10000` от оценки (по умолчанию 0). ALG-08. **Уточнения (v1.1):** `rate_at` допускает обратную пару (дробь переворачивается; при равной дате прямой курс приоритетнее), триангуляции нет — `E_NO_RATE` (C-036); введённый курс хранится как введён, производные (`implied_rate`, `apply_shock`) — несократимая дробь (C-037); `to_decision_events(events, accounts, rates, decision_currency, policy, as_of)`, `to_decision(amount_minor, currency, as_of, ctx)`, `opening_in_decision(accounts, balances, ctx, as_of)`, `implied_rate(leg_a, leg_b, base_exp, quote_exp)` (C-034); курс для аллокации резерва: `planned` — `spot` на `as_of`, `posted` — курс на дату дохода при записи; дальше резерв не переоценивается (C-038).

### D-21 Evidence, `inputs_hash`, результат

`inputs_hash = sha256(canon({ events: журнал окна, rules: версии правил, params, as_of, engine_version }))`; `canon` — детерминированный JSON (ключи по возрастанию кодовых точек, без пробелов, числа только safe-integer, строки NFC, порядок массивов задаёт производитель — множества сортируются); `state_hash(state) = sha256(canon(state))`, `state = reduce(effective_events(journal))` — свёртка, не лог, `recorded_at` в неё не входит (v1.1, C-071). Результат инструмента — `Result{ call_id, tool, engine_version, inputs_hash, as_of, scope{mode, scenario_id}, facts, evidence[], warnings[] }`; `evidence[i] = { id, kind: money|date|pct_bp|days|count|enum, v, cur?, dp?, event_ids[] }`; `call_id = sha256(tool | canon(args) | inputs_hash)[0:8]` (8 hex-знаков; в интерфейсе и в аргументе `since` — `c_` + hex; v1.1, C-054). Первые девять evidence `check_purchase` фиксированы порядком §9.14 (e1…e9), остальные — `e10…`. Каждое число в ответе ассистента/экрана обязано ссылаться на `evidence`. Недоверенный текст (`note`, `tag`, описания) в `Result` не попадает: группа «почему» в инструменте — идентификатор + `cause_class` (C-097). ALG-12, IDEA-74.

### D-22 Якорь и свежесть данных

`Anchor{account_id, date, amount_minor}` — подтверждённый остаток; `opening` = последний якорь ≤ `as_of` + Σ posted после него; `drift = anchor.amount − Σ posted(≤ anchor.date)` показывается, не скрывается. Скорость неучтённых трат: `unlogged_rate = median(|drift_i| / days_i)` по прошлым якорям (minor/день). `age = as_of − min(дата последнего якоря)` по **operating-счетам** — самый несвежий счёт определяет плашку; у счёта без якоря возраст неизвестен → уровень `block`, причина `no_anchor` (v1.1, C-010): `age > stale.banner_days` → плашка «остаток не сверялся N дн.: не учтено ≈ unlogged_rate · age»; `age > stale.block_days` → вердикт Q3 и «можно потратить» заменяются «данных мало». **Окно плана (v1.1, C-004):** развёртка планов счёта начинается с даты его последнего якоря включительно (`plan_from`), без якоря — с `as_of`; плановые вхождения раньше якоря в поток не входят (они учтены в якоре); между якорем и `as_of` без сопоставленного факта вхождение — `expected`/`overdue` и считается на `as_of` (D-04).

### D-23 Готовность данных

```pseudo
s = has_account + (count(obligations) ≥ 3 или has_wave) + has_income_within(45 дней) + daily_spend_set   # 0..4
уровни: 0 «пусто» · 1 «каркас» · 2 «рабочий» · 3 «рабочий+» · 4 «полный»
прогноз виден при s ≥ ready.q1 (3), вердикт Q3 — при s ≥ ready.q3 (4); при s < 4 над графиком плашка «не учтено: …»
```

Буфер и резервы в `s` не входят (v1.1, C-018, C-065): заданность буфера — отдельное условие гейта D-11; если есть доход, но нет ни одного `TaxRule` и `Reserve`, показывается плашка `W_NO_RESERVES` «налоговый конверт и накопления не заданы: вердикт и «можно потратить» посчитаны по физическим деньгам» (v0-калькулятор подписывает ответ «без учёта резервов»).

### 3.10 Инварианты модели

1. Сумма двух ног `transfer` в одной валюте равна 0; в разных — связана выведенным курсом.
2. `posted.date ≤ as_of` в любой проекции; `planned` без `rule_id` — разовая запись.
3. Журнал не мутирует: исправление — новая запись; `fold(все записи) = fold(снимок, хвост)`.
4. Идентификатор вхождения `occ_key` не меняется при сдвигах и переносах.
5. Любое число денег в хранилище — safe-integer; float в payload отвергается валидатором записи.
6. Аллокация хранит `rule_version`; правка правила не меняет прошлые аллокации.
7. (v1.1, C-025) `Id` — единое пространство имён рабочей области: `rule_id`, `stream_id`, `tax_rule_id`, `reserve_id` и др. не совпадают; `seq` записей журнала монотонен (C-072).

## 4. Соглашения псевдокода

**Формат.** Блоки ```` ```pseudo ````; комментарии `#`; индексы с 0; диапазон `a..b` — включительно, `a..<b` — полуоткрытый; запись `{ поле: значение }`; `null` — отсутствие; `Σ`, `min`, `max`, `argmin` разрешены; присваивание `=`, сравнение `==`. Новые функции — в `snake_case`, как в коде.

**Типы в сигнатурах:** `amount_minor: Minor` (int), `date: EpochDay`, `currency: Currency`, `rate_bp: Bp`, `minutes: Minutes`, `id: Id`; массивы — `T[]`; запись — `{a: T, b: U}`; «или» — `T | U`. Режим округления: `RoundMode ∈ half_even | half_up | floor | ceil`.

**Правила.** Деньги — только `int`; доли — в `bp`/`‰` (`floor_div(1000·a, b)`); деление денег — только через `round_div`/`mul_div`/`ceil_div`/`split_*`; сортировка стабильна, ключ `(date, amount_minor, id)`; ни `now()`, ни `random()`, ни обхода `Map` без сортировки. Float допускается только в статистике (`montecarlo`, `calibration`: интервал Уилсона, `sqrt`), результат — целые `bp`/`‰` с явным округлением; деньги из float не выводятся.

**Ошибки.** `fail(code, ctx)`: `E_NOT_INTEGER`, `E_OVERFLOW`, `E_BAD_DATE` (в том числе `T < as_of`), `E_FUTURE_POSTED`, `E_RULE_INVALID`, `E_CURRENCY_MISMATCH`, `E_NO_RATE`, `E_SCHEMA`. **Предупреждения (v1.1, C-021)** не прерывают расчёт и попадают в `Result.warnings`: коды `W_*` — реестр в §2.0 (`vocab.json`). Проверки согласованности валюты (событие и резерв = валюте решения) выполняются при построении `build_events` и записи `reserve.set`, а не в функциях ряда (C-098). Вспомогательная `gcd(a, b)` (BigInt) — в `money.mjs` (C-037).

**Вспомогательные функции (каноническая семантика).**

```pseudo
floor_div(a, b):  q = a div b, округление к −∞ (b > 0);   floor_mod(a, b) = a − b·floor_div(a, b)
ceil_div(a, b)  = −floor_div(−a, b)                       # b > 0

round_div(n, d, mode = half_even):          # d > 0; n может быть BigInt
  q = floor_div(n, d);  r = n − q·d         # 0 ≤ r < d
  half_even: 2r < d → q;  2r > d → q+1;  2r = d → (q чётно ? q : q+1)
  half_up (от нуля): 2r > d → q+1;  2r = d → (n ≥ 0 ? q+1 : q);  иначе q
  floor → q;   ceil → (r > 0 ? q+1 : q)

mul_div(a, num, den, mode = half_even):     # BigInt внутри, результат — safe-integer, иначе fail(E_OVERFLOW)
  return round_div(BigInt(a)·BigInt(num), BigInt(den), mode)

split_equal(total, n):                       # n ≥ 1; для total < 0 — по модулю с обратным знаком
  [ floor_div(total, n) + (k < floor_mod(total, n) ? 1 : 0)  для k = 0..n−1 ]      # лишние minor — первым частям

split_largest_remainder(total, weights):     # weights ≥ 0, Σ > 0
  base_k = floor_div(total·w_k, Σw);  rest = total − Σ base_k
  отдать по 1 minor первым `rest` индексам по убыванию дробной части (total·w_k mod Σw), при равенстве — по возрастанию k
```

```pseudo
# даты: алгоритм «days_from_civil» (Hinnant); работает для любых лет
days_from_civil(y, m, d):                    # → EpochDay (1970-01-01 = 0)
  y −= (m ≤ 2 ? 1 : 0);  era = floor_div(y, 400);  yoe = y − era·400
  doy = floor_div(153·(m + (m > 2 ? −3 : 9)) + 2, 5) + d − 1
  doe = yoe·365 + floor_div(yoe, 4) − floor_div(yoe, 100) + doy
  return era·146097 + doe − 719468
civil_from_days(z):                          # → (y, m, d)
  z += 719468;  era = floor_div(z, 146097);  doe = z − era·146097
  yoe = floor_div(doe − floor_div(doe, 1460) + floor_div(doe, 36524) − floor_div(doe, 146096), 365)
  y = yoe + era·400;  doy = doe − (365·yoe + floor_div(yoe, 4) − floor_div(yoe, 100))
  mp = floor_div(5·doy + 2, 153);  d = doy − floor_div(153·mp + 2, 5) + 1;  m = mp + (mp < 10 ? 3 : −9)
  return (y + (m ≤ 2 ? 1 : 0), m, d)
dow(d) = floor_mod(d + 4, 7)                 # 0 = воскресенье … 6 = суббота;  dow(0) = 4 (четверг)
is_leap(y) = (y mod 4 = 0 и y mod 100 ≠ 0) или y mod 400 = 0
days_in_month(y, m);  clamp_day(y, m, day) = min(day, days_in_month(y, m))
add_months(d, n):  (y, m, day) = civil_from_days(d);  t = y·12 + (m−1) + n;  y' = floor_div(t, 12);  m' = floor_mod(t, 12) + 1
                   return days_from_civil(y', m', clamp_day(y', m', day))        # день берётся из ИСХОДНОЙ даты
nominal(start, k, interval) = add_months(start, k·interval)                      # всегда от start, без дрейфа
is_business(d, cal) = dow(d) ∉ cal.weekend_dows  и  format_date(d) ∉ cal.holidays
next_business_day(d, cal) = min{ x ≥ d : is_business(x, cal) };   prev_business_day(d, cal) = max{ x ≤ d : is_business(x, cal) }
shift_by_policy(d, policy, cal):  keep → d;  next → next_business_day;  prev → prev_business_day;  skip → (is_business(d) ? d : null)
nth_business_day(y, m, n, cal):  n > 0 — n-й с начала месяца;  n < 0 — с конца (−1 = последний)
```

### 5.1 Каноническое имя и состав инструментов (`tools.mjs`, ADR-010)

Аргументы — только идентификаторы, числа, даты, перечисления; свободного текста нет (кроме `note` ≤ 200 символов у `propose_change`). Ответ любого инструмента — `Result` (D-21); ряды (`series_handle`) модель не получает.

Формат токенов A2 — только `{eN}` (C-080); в payload `A3` «min» — `min{amount_minor,date}` из `get_projection` или `m_after` из `check_purchase` с именем инструмента и `scope` (C-064). Нет и не будет: `delete_*`, `export_*`, `send_*`, любые сетевые инструменты. Раннер валидирует аргументы по схеме (мини-валидатор без зависимостей), ограничивает ≤ 12 вызовов на вопрос, ошибки возвращает как `isError` с кодом.

Правило зависимостей (без циклов): `money` ← `dates` ← {`recurrence`, `hourly`, `fx`, `tax`, `debt`} ← `timeline` ← `sinking` ← {`waves`, `afford`} ← `tools` ← `verifier`. Побочные ветки: `ledger` зависит только от `money`; `calibration` — от `money`/`dates`; `backtest` — от `index`, `afford`, `ledger`, `calibration` (§14 B4); `montecarlo` — от `timeline`, `sinking`, `afford`, `calibration`; `io` — от `ledger`, `dates`, `money` (без `timeline`, §14 B4: плановые события приходят портом `opts.planned`).

## 8. Срез v1: «делаем» и «не делаем»

**Принципы среза** (из красной команды): одна персона A (релокант-фрилансер/почасовик), одно устройство, ручной ввод, local-first **без сервера и аккаунтов**, **без LLM**. Движок и тесты — полностью; Q1+Q3 — ядро; при нехватке времени режем сначала часы, налоги и волны.
