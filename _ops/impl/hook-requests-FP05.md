# Запросы FP-05 к владельцам общих файлов

Автор: FP-05 (хранение, файл-копия, экспорт и удаление данных). Дата: 2026-10-05.
Код — `prototype/demo/{store,store_idb,backup,data_actions,data_runtime,data_view,rights,log,pack_fp05}.mjs`, `prototype/demo/i18n/data.mjs`, `prototype/demo/css/data.css`;
тесты — `tests/{store,backup,data_actions,data_pack,rights,log}.test.mjs`, фейк IndexedDB — `tests/fake_idb.mjs`.
`app.mjs` не менялся: «Продолжить с сохранённого» и секции экрана «Данные» подключены пакетом через слоты `overview.cards`, `data.sections` и хук `boot`.

## 1. FP-01: `ctx.refresh()` — перерисовка без записи

Пакету нужно перерисовать страницу, когда меняется состояние хранилища (закончилась запись, пришла запись другой вкладки, режим стал «пауза»).
Сейчас единственный путь — `ctx.set_ws(ctx.get_ws(), {reason})`, но он рассылает подписчикам событие, пересчитывает модель и дописывает журнал: лишняя работа и шум для чужих
подписчиков (`tests/ext_boot.test.mjs` проверяет, что после смены набора данных подписчик видит ровно `['adopt']`, — событие `fp05_refresh` его ломает).
Обход в `pack_fp05.mjs`: событие `hashchange` на `window` (приложение рисует заново в `route()`); в Node события нет — вызов пропускается.
Просьба: `ctx.refresh()` → `host.render()` без рассылки. Тогда `refresh` в `make_runtime` заменяется на `ctx.refresh`.

## 2. FP-01: `ctx.adopt(ws, {id})` — подмена набора данных пакетом

«Продолжить с сохранённого» и «Восстановить из файла» подменяют рабочую область через `ctx.set_ws(ws, {reason: 'restore'})`. Это правка, а не смена набора: журнал страницы (`ctx.journal`)
дописывается огромной разностью, `S.dataset_id` остаётся прежним (в списке наборов выбран «G-001», хотя показаны сохранённые данные), стопка отмены FP-04 не очищается.
Просьба: `ctx.adopt(ws, {name})` → `adopt_workspace(ws, 'custom')` из `app.mjs` (журнал пересобирается, подписчики получают `adopt`, подпись набора — «свои данные»).
Пакет FP-05 при `adopt` ставит запись на паузу (чтобы не затереть сохранённое), поэтому при переходе на `ctx.adopt` его `on_change` надо отличать по `reason`:
предлагаю `adopt` с полем `{source: 'restore'}` в событии, а пакет игнорирует такой `adopt`.

## 3. Интегратор: «Продолжить с сохранённого» до первой отрисовки

Сейчас плашка «в браузере есть сохранённые данные» появляется после `boot`-хука (то есть после загрузки учебного набора и первой отрисовки). Для пользователя это короткое мерцание:
сначала виден учебный набор, потом плашка. Если интегратор захочет решать до показа набора: в `app.mjs → boot()` перед `load_dataset` вызвать хук `pre_load` (в нём FP-05 откроет хранилище,
а при согласии сразу выдаст рабочую область из записей). Не критично; текущий вариант безопасен для данных (до выбора пользователя в хранилище ничего не пишется).

## 4. Интегратор: сервис-воркер и кэш (FP-12)

`eraseAll` уже снимает регистрации сервис-воркера и кэши через порты (`navigator.serviceWorker`, `caches`), но до FP-12 их нет — шаги выполняются вхолостую (счётчик 0).
Ключи localStorage приложения определяются префиксом `runway` (`LOCAL_PREFIX` в `data_actions.mjs`): новые ключи других пакетов должны начинаться с него (сейчас `runway-demo-*` у `app.mjs` и `runway-store/1` у запасного хранилища).
Если пакет FP-09/FP-10 заведёт ключ с другим префиксом, `eraseAll` его не удалит.

## 5. Интегратор: `tests/ext_boot.test.mjs` и реальные пакеты

Тест запускает настоящий `app.mjs` с реальными пакетами, в том числе с `pack_fp05`. После правок пакет в этом тесте проходит (подписчик видит `['adopt']`); хрупкость — те же 400 мс ожидания `boot`:
на нагруженной машине хук `boot` пакета (открытие хранилища, выбор IndexedDB → localStorage → память) может не успеть, и тест увидит событие позже. См. также запрос FP-04 №1
(лучше, если тест подменит `ext_manifest.LOADERS` пустым набором).
