# Аудит экранов и сценариев UX против демо

Дата: 2026-10-05. Метод: чтение `wiki/product/03-ux-screens.md`, `01-personas-jtbd.md`, `17-start-plan.md`, `wiki/ideas/proposal-product.md` (IDEA-30…58) и сверка с кодом `prototype/demo/` (`app.mjs`, `i18n.mjs`, `index.html`, `style.css`), `prototype/cli.mjs`, `prototype/engine/*.mjs`, `tests/demo.test.mjs`. Ничего в прототипе и вики не менялось. Рядом лежит более ранний аудит по REQ (`_ops/gap/req-ui.json`); здесь он использован как подсказка, а каждое утверждение перепроверено по коду.

Условные обозначения статуса: **есть** (код и проверка), **частично**, **нет**, **не код** (процесс или документация). Усилие: S ≤ 0,5 дня, M 1–2 дня, L 3+ дня. Все предложения аддитивные: новые файлы и экраны, существующие функции не переписываются.

## Главное

1. Демо — **экран ответов, а не экран ввода**. Весь «читающий» слой (Обзор, Купить, Волны, Резервы, Сценарии, Лента, Ассистент, Данные) покрыт хорошо и совпадает с вайрфреймами. Весь «пишущий» слой из документации (мастер «Старт», быстрый ввод `entry`, формы правил, часов, налога, sinking, якоря, настройки, счета, импорт CSV, метрики) в демо отсутствует: в `app.mjs` нет ни одного места, где пользователь создаёт или правит запись рабочей области. Единственный способ внести свои числа — выгрузить JSON, отредактировать руками и загрузить (`export_state` / `import_file`).
2. **Движок уже умеет большую часть того, чего нет в UI**: `buffer_hint` (`engine/timeline.mjs:1025`), `readiness`, `expand_stream_ex` и `resolve_hours` (`engine/hourly.mjs`), `allocation_range` (`engine/tax.mjs`), `match_plan_to_fact` и `assign_statuses` (`engine/calibration.mjs`), `parse_with_profile`, `dry_run`, `import_commit`, `export_csv`, `export_hledger`, `import_hledger` (`engine/io.mjs`), `run_paths` и `p_fail` (`engine/montecarlo.mjs`), `apply_wave_overrides_ex` (`engine/waves.mjs`). `app.mjs` не импортирует ни одну из них (проверено по списку импортов, строки 14–21). Поэтому большинство предложений ниже — тонкие слои DOM над готовыми функциями.
3. Часть сообщений в UI слабее, чем в документации: нет числа и суммы у `W_RESERVE_BEHIND`, нет курса и возраста у `W_RATE_STALE`, нет даты у `W_RULE_STALE`, перечень недостающего в «готовности» всегда один и тот же. Это исправляется строками i18n плюс чистыми функциями, без перестройки.
4. Нашлось место, где дизайн страдает от пробела: сообщения «Задайте буфер» (`gate.no_buffer`), «введите курс в настройках» (`err.E_NO_RATE`) и «подтвердите или измените правило» отправляют пользователя в экран, которого нет.

## Что стоит проверить отдельно (сомнения)

- **Телефонная навигация**: `style.css:158–161` делает нижнюю панель, но проверка прокрутки 8 пунктов в 375 px и наложения последнего пункта на контент (`padding-bottom: 96px`) в этом аудите была только по коду; ручная проверка в браузере указана в 16-prototype-findings (строка 320, ширины 375/617/900/1280).
- **Достижимость `ov.empty`**: утверждение «набора с `s < 3` в демо нет» основано на списке `DATASETS` (`i18n.mjs:70`, четыре G-001-набора) и на отсутствии теста с `ov.empty` в `tests/demo.test.mjs` (есть только проверка наличия ключа). Если кто-то загрузит JSON с `s < 3` через «Загрузить JSON», состояние покажется; это нужно проверить руками.
- **Подсказка буфера в сквозном примере (490,00 €)**: функция `buffer_hint` есть, но в UI не подключена; точное совпадение числа с примером из 01-personas проверяется тестом движка, а не демо.
- **Замена чисел текстом при `disabled`** на экране «Резервы»: по коду числа остаются; в 03-ux-screens сказано «заменены текстом». Проверить на наборе с правилом старше `2·ttl` (в четырёх наборах такого нет).
- **Лента: «8 последних фактов»** — ограничение `slice(0, 8)`; в документации оно не оговорено.
- **Не покрыто тестами в демо** (по поиску в `tests/demo.test.mjs`): рассрочка из набора, сохранённые сценарии, загрузка JSON с ошибкой формы (есть косвенно), отрисовка пустых состояний.
