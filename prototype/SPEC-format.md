# Форматы файлов Runway: `runway-journal/1`, `runway-metrics/1`, `runway-shell/1`

Предварительная спецификация (REQ-187, REQ-186): описывает то, что читает и пишет прототип сейчас, а не обещание на будущее. Источник истины для данных пользователя — **журнал событий**
(`runway-journal/1`, ADR-004, решение владельца № 2); рабочая область, CSV и hledger — проекции или выгрузки журнала. Расчёт по введённым данным и правилам, не консультация.
Подробности модели данных — `../wiki/product/04-data-model.md`; форматы импорта и экспорта — `../wiki/product/09-import-export.md`. Этот файл ничего не добавляет к канону, а фиксирует
форму файлов так, чтобы их можно было прочитать без приложения и проверить независимо (`tools/verify.mjs`). Юридическое ревью формулировок и вычитка людьми не выполнены.

## 1. Общие правила

| Правило | Значение |
|---|---|
| Кодировка | JSON в UTF-8 без BOM, переводы строк LF |
| Деньги | целые числа в минимальных единицах валюты (`amount_minor`, `*_minor`), код валюты ISO 4217 строкой; дробных чисел нет |
| Числа | только целые в диапазоне ±(2^53 − 1); `1.5`, `NaN`, `1e21` в файле недопустимы (код `E_NOT_INTEGER`) |
| Даты | календарные `ГГГГ-ММ-ДД` без часовых поясов; момент ввода записи — `ГГГГ-ММ-ДДTЧЧ:ММ:СС[.ддд]Z` (только аудит, в арифметике не участвует) |
| Канонический вид | `canon`: ключи объектов по возрастанию кодовых точек, без пробелов, строки в нормализации NFC, `undefined` опускается; повторных ключей нет. Хэши считаются от канонического вида |
| Хэш | SHA-256, 64 знака hex в нижнем регистре |
| Идентификаторы | непустые строки; `__proto__`, `constructor`, `prototype` — обычные данные, а не служебные ключи |

## 2. `runway-journal/1` — файл-копия журнала событий

Файл — один объект (в каноническом виде ключи идут в таком порядке):

```json
{"engine_version":"0.1.0","events":[ … ],"format":"runway-journal/1"}
```

| Поле | Смысл |
|---|---|
| `format` | строка `runway-journal/N`; читатель знает N = 1. `runway-journal/2` и новее — отказ `E_SCHEMA` (`newer_format`): файл можно показать, но не свернуть |
| `engine_version` | версия движка, записавшего файл (`ENGINE_VERSION`); при чтении нужна только для сообщений |
| `events` | массив записей журнала, по возрастанию `seq`; пустой массив допустим |

### 2.1 Запись журнала

```json
{"actor":"user","entity_id":"acc_main","event_id":"ev-001","payload":{"account_id":"acc_main","currency":"EUR","exponent":2,"kind":"bank","liquidity":"operating","name":"Основной счёт","opened_on":"2026-01-01"},"recorded_at":"2026-09-10T09:01:00Z","seq":1,"type":"account.opened","v":1}
```

| Поле | Обязательно | Правило |
|---|---|---|
| `event_id` | да | уникальная непустая строка в пределах файла |
| `type` | да | один из видов ниже; неизвестный вид — `E_SCHEMA` (`unknown_type`) |
| `v` | да | версия схемы `payload` этого вида (целое ≥ 1); сейчас у всех видов 1 |
| `entity_id` | да | сущность записи; если не задан при создании, берётся из поля `payload` по таблице ниже |
| `payload` | да | объект: целые, строки, булевы, `null`, массивы, объекты; дробных чисел нет |
| `recorded_at` | да | момент ввода (см. выше) |
| `seq` | да | неотрицательное целое; строго возрастает по файлу (повторы — `E_SCHEMA`, `seq_not_monotonic`) |
| `actor` | нет (по умолчанию `user`) | `user`, `system`, `import:<batch_id>` или `assistant:<draft_id>` |
| `causation_id` | нет | `event_id` более ранней записи-причины |
| `supersedes_id` | нет | `event_id` более ранней записи, которую эта заменяет |

### 2.2 Виды записей и сущность

| `type` | Поле `payload`, из которого берётся `entity_id` | Что делает при свёртке |
|---|---|---|
| `account.opened` / `account.closed` | `account_id` | открыть счёт / проставить `closed_on` (счёт должен существовать) |
| `anchor.set` | `anchor_id` | опорный остаток счёта на дату |
| `tx.posted` | `entity_id` задаётся при записи | проведённый факт (в состоянии получает `event_id` записи) |
| `plan.set` | `plan_id` | разовый плановый платёж |
| `rule.set`, `override.set`, `calendar.set` | `rule_id`, `rule_id` (+ `nominal_date`), `calendar_id` | повторяющееся правило, исключение вхождения, календарь выходных |
| `stream.set` | `stream_id` | поток почасового дохода |
| `taxrule.set` | `tax_rule_id` | версия налогового правила пользователя (версии добавляются, прошлые не правятся) |
| `reserve.set`, `allocation.recorded` | `reserve_id`, `allocation_id` | резерв; взнос в резерв (идемпотентно по `allocation_id`) |
| `fx.set` | `fx_id` | курс как дробь `num/den` |
| `scenario.set`, `purchase.saved` | `scenario_id`, `purchase_id` | сценарий; сохранённая покупка |
| `wave_override.set` | `override_id` | правка волн; порядок записей = порядок применения |
| `counterparty.set`, `profile.set`, `debt.set` | `counterparty_id`, `profile_id`, `debt_id` | контрагент; профиль (в том числе метаполя рабочей области `ws:meta`); долг |
| `match.set` | `fact_event_id` | привязка факта к плану (`plan_ref`) либо «не относится» (`no_plan`); факт не мутирует |
| `params.set` | задаётся при записи | значения параметров расчёта (слияние по ключам) |
| `import.started` / `import.rolled_back` | `batch_id` | реестр партий импорта; откат партии |
| `revert` | `target` | отмена действия записи `target` (см. ниже) |
| `consent.granted`, `consent.revoked`, `draft.proposed`, `draft.confirmed`, `assistant.call` | задаётся при записи | хранятся без интерпретации (резерв для v2) |

Формы `payload` для каждого вида — в `../wiki/product/04-data-model.md`; движок отвергает запись, у которой нет обязательного идентификатора (`E_SCHEMA`, `payload_id_required`).

### 2.3 Порядок, отмена и правка

* Порядок — по `seq`. Ссылки (`revert.target`, `supersedes_id`, `causation_id`) ведут только на **более ранние** записи; ссылка вперёд — `E_SCHEMA`; ссылка на неизвестную запись игнорируется (файл может быть срезом).
* `revert` отменяет действие записи `target`. Отмену можно отменить следующим `revert`: действие возвращается. Удаления записей нет — журнал только дописывается.
* Запись с `supersedes_id = X` заменяет `X`: в состояние идёт замена, а не оригинал. Цепочка замен `a ← b ← c` оставляет только последнюю «живую».
* Эффективные записи = все записи минус отменённые минус заменённые, без самих `revert`; свёртка применяет их по порядку `seq` (`reduce(effective_events(events))`).

### 2.4 Состояние и `state_hash`

Состояние — объект со словарями по идентификатору (`params`, `accounts`, `anchors`, `facts`, `plans`, `rules`, `overrides`, `calendars`, `streams`, `tax_rules`, `reserves`, `allocations`, `fx`,
`scenarios`, `purchases`, `counterparties`, `profiles`, `debts`, `matches`, `imports`, `extra`) и массивом `wave_overrides`. `state_hash = sha256(canon(состояние))`. Правило проверки файла:
**импорт фикстуры даёт заявленный `state_hash`** — так проверяется, что читатель понимает формат так же, как писатель (`node tools/verify.mjs --fixtures`).

### 2.5 Версии и совместимость

* Версия формата — число в `format`. Изменение формата = новое число + чистый апкастер `v → v+1` для затронутых видов + новая фикстура; старые фикстуры остаются и должны по-прежнему импортироваться.
* Запись без `v` — `E_SCHEMA`. Запись с `v` новее известной — `E_SCHEMA` (`newer_version`). Недостающий апкастер — `E_SCHEMA` (`no_upcaster`). На диске запись апкастером не переписывается.
* Новые виды записей в рамках версии 1 не добавляются: читатель версии 1 отвергает неизвестный вид, а не пропускает молча.

### 2.6 Фикстуры

| Файл | Формат | Записей | `state_hash` |
|---|---|---|---|
| `tests/fixtures/journal-v1.json` | `runway-journal/1` | 14 | `f4b11682044eb911add5a6223c88c67b0f07c504321081ac1bfcdfc8ad4dde88` |

Список с заявленными числами — `tests/fixtures/FIXTURES.json`; проверка — `node tools/verify.mjs --fixtures` и `tests/build_manifest.test.mjs` (REQ-187). Хэш `journal-v1.json` записан при создании фикстуры
(golden в `tests/hardening.test.mjs`, REQ-016) и не пересчитывается из вывода проверяемого кода.

### 2.7 Как прочитать без приложения

Файл — обычный JSON. Любой читатель может: проверить `format`; отсортировать `events` по `seq`; убрать отменённые и заменённые записи по правилам 2.3; применить оставшиеся по таблице 2.2.
Экспорт CSV (`runway-csv/1`) и hledger — выгрузки того же состояния; какие данные они теряют, приложение говорит перед выгрузкой (`data_actions.FORMAT_LOSSES`).

## 3. `runway-metrics/1` — добровольный файл метрик

Метрики считаются только на устройстве (`localStorage`, ключ `runway-metrics/1`) и никуда не отправляются; файл человек скачивает сам и видит его целиком до скачивания (REQ-185, решение № 5, предварительно).
В файле только агрегаты и порядковые номера: сумм, календарных дат, названий, заметок и идентификаторов нет. Схема строгая: `demo/metrics.mjs → validate_package` отвергает любое лишнее поле.

| Поле | Тип и границы | Смысл |
|---|---|---|
| `format` | строка `runway-metrics/1` | формат |
| `engine_version` | `ч.ч.ч`, числа до трёх знаков | версия движка |
| `sessions` | целое 0…1 000 000 | число сеансов |
| `active_days` | массив целых 0…3650, строго возрастающий, до 400 | дни использования как смещения от первого дня (0 — первый), не календарные даты |
| `steps` | до 200 объектов `{step, seconds, session, outcome}` | журнал шагов мастера «Старт»: `step` ∈ `account, obligations, income, daily, buffer`; `seconds` 0…3600 (активное время); `session` ≥ 1, не больше `sessions`; `outcome` ∈ `saved, skipped` |
| `first_forecast` | `null` или `{after_seconds, session}` | «первый прогноз»: `after_seconds` — целое 0…720 000 либо `null`, `session` ≥ 1 |
| `verdict_ready` | `null` или `{session}` | «вердикт доступен» (гейт пройден) |
| `counters` | объект «имя → целое 0…10^9» | имена только из списка: `accounts_saved, anchors_set, rules_saved, facts_added, scenarios_saved, imports_done, undo_used, wizard_opened` |
| `min_error_bp` | `{n, values}` | ошибка минимума в базисных пунктах `(факт − прогноз)/|прогноз|`; `n` — число окон, `values` — до 100 значений в диапазоне ±1 000 000, не больше `n` |
| `coverage` | `{k, n}` | покрытие «k из n», `k ≤ n` |

Страховка поверх структуры: в тексте файла не должно быть ничего, похожего на календарную дату (`ГГГГ-ММ-ДД`, `дд.мм.гггг`), и чисел длиннее девяти знаков. Пример пустого файла:

```json
{
  "format": "runway-metrics/1",
  "engine_version": "0.1.0",
  "sessions": 0,
  "active_days": [],
  "steps": [],
  "first_forecast": null,
  "verdict_ready": null,
  "counters": {},
  "min_error_bp": { "n": 0, "values": [] },
  "coverage": { "k": 0, "n": 0 }
}
```

Хранение и удаление: ключ начинается с `runway` и стирается «Удалить все данные»; после стирания метрики не воскресают до перезагрузки. Выключатель сбора хранится рядом и тоже стирается (счёт на устройстве по умолчанию включён).

## 4. `runway-shell/1` — манифест хэшей оболочки

Файл `demo/shell_manifest.json` публикует sha256 каждого файла, который страница и воркер загружают с хоста (REQ-154). Собирает его `tools/build_manifest.mjs`; проверяет `tools/verify.mjs`;
сервис-воркер сверяет с ним каждый файл при установке и не кладёт в кэш ничего, что не совпало.

| Поле | Смысл |
|---|---|
| `format` | `runway-shell/1` |
| `engine_version` | `ENGINE_VERSION` на момент сборки |
| `build_hash` | `sha256` от текста: строка `runway-shell/1\n`, затем для каждого файла из `files` в порядке путей строка `путь<TAB>sha256\n`, и последней строкой `demo/sw.js#core<TAB>core_sha256\n` (текст воркера без штампа; условный путь, файла с таким именем нет) |
| `files` | `[{path, sha256, bytes}]`: пути относительно `prototype/`, разделитель `/`, отсортированы побайтно; состав — всё, до чего доходит обход ссылок от `index.html`, `v0.html` и `sw.js` |
| `stamped` | те же поля для `demo/build_info.mjs` и `demo/sw.js`: их содержимое зависит от `build_hash`, поэтому они вне `files` (иначе круг). У записи `demo/sw.js` есть ещё `core_sha256` — sha256 текста воркера с обнулённым штампом (блок между `BUILD:BEGIN` и `BUILD:END` заменён нулевым хэшем): он входит в `build_hash`, поэтому правка логики воркера меняет хэш сборки и имя кэша `runway-shell-<16 знаков хэша>`. `demo/build_info.mjs` в хэш не входит (в нём только сам хэш и число файлов) и проверяется отдельно |

Воспроизводимость: меток времени и абсолютных путей нет; двойная сборка (в том числе из другой копии каталога) даёт побайтно тот же манифест. Для этого файлы хранятся с переводами строк LF
(`.gitattributes` в этом каталоге закрепляет `eol=lf`). Подписанных релизов нет: проверка хэшей — проверка целостности копии, а не подлинности хоста; при первой загрузке пользователь доверяет хосту.

## 6. Чего здесь нет

* Файла JSON Schema для `payload` нет: формы полей описаны в вики и проверяются кодом (`engine/validate_ws.mjs`, `demo/ws_edit.mjs`).
* Файл-копия и локальное хранилище **не шифруются** (защищённый паролем экспорт — версия 1.1, решение C-081).
* Лицензия на код не выбрана владельцем (REQ-186): без неё чтение формата допустимо, а распространение кода — нет.
