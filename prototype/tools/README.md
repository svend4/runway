# Инструменты прототипа (FP-12)

Инструменты запускаются вручную из каталога `prototype/`, не входят в оболочку приложения и не импортируются из `engine/`. Нужен только Node ≥ 24, зависимостей нет. **Один процесс за раз:** на машине с малой памятью

## Сборка и проверка оболочки

«Оболочка» — файлы, которые страница и воркер загружают с хоста. Её состав определяется обходом ссылок от `demo/index.html`, `demo/v0.html` и `demo/sw.js` (импорты модулей, `ensure_css`, наборы данных,
воркер расчёта, иконки). **После любой правки в `demo/`, `engine/` или `data/` (в пределах оболочки) запустите `npm run build`:** иначе `tests/build_manifest.test.mjs` покажет, что манифест устарел, а сервис-воркер
откажется устанавливать копию с несовпавшими хэшами. Порядок: правки → `npm run build` → `npm run verify` → тесты. Двойная сборка даёт тот же результат побайтно; метки времени в манифест не пишутся.
Файлы хранятся с переводами строк LF (`.gitattributes`); на машине с `core.autocrlf=true` без этого файла хэши разошлись бы.

Что входит в `demo/shell_manifest.json`: пути относительно `prototype/` и sha256 каждого файла, хэш сборки (sha256 от списка «путь + sha256» и от текста воркера `sw.js` без штампа — поле `core_sha256`: правка логики воркера меняет хэш и имя кэша, так что воркер новой версии никогда не пишет в кэш работающей), версия движка, два штампованных файла (`build_info.mjs`, `sw.js`; `build_info.mjs` в хэш не входит и проверяется `verify.mjs` отдельно).
Что не входит: `README_ext.md`, `promises.json`, `.htaccess`, сам манифест, `engine/vocab.json`, `engine/backtest.mjs`, зеркала данных (`data/golden-g001.json`, `data/profiles`, `data/templates`, `data/backtest-report.json`), тесты.

## Замеры (`bench.mjs`)

Дата — обязательный аргумент (инструмент часов не читает). Замеряются: `analyze` и «пересчёт страницы + ответ Q3» на рабочей области ≈ 10³ событий, горизонт 180 дней (n = 90 замеров, чередуются);
максимальная задержка цикла событий, пока расчёт идёт в потоке и в воркере (модель блокировки интерфейса: в Node это поток `worker_threads`, в браузере — Web Worker; браузерный замер не делался);
открытие журнала на 36 500 записей со снимком и без. Бюджеты — гипотезы ADR-014 (p95 ≤ 100 мс, блокировка ≤ 50 мс, журнал ≤ 2 с), а не обещания продукту; цифры с этой машины не переносятся на телефон.

### Сравнение с записанным замером (`bench.mjs --compare`, FP-23)

`node tools/bench.mjs --compare [--baseline ../_ops/bench.json] [--factor 2] [--attempts 3] [--samples 30] [--rounds 3]` заново замеряет p95 полного пересчёта (`analyze` и «страница + Q3») на том же наборе ≈ 10³ событий и сравнивает с записанным замером. Код выхода **1**, если p95 вырос более чем в `--factor` раза (по умолчанию вдвое; ровно вдвое ещё допустимо) относительно записанного или превысил бюджет-гипотезу из файла (100 мс); **2** — нет читаемого базового замера, в нём нет p95 или неверные ключи; **0** — в пределах. Замер повторяется до `--attempts` раз (по умолчанию 3, останавливаясь, как только уложился), и в сравнение идёт наименьший p95 по каждой метрике — как «лучший из раундов» в TST-54: разовая нагрузка машины не даёт ложного срабатывания, а настоящий регресс держится во всех попытках. Режим ничего не пишет и часов не читает (дата не нужна). Записанный замер — «зафиксированный бюджет» REQ-150, пока нет замеров на устройствах (FP-40). На загруженной машине рост бывает шумом: повторите замер, когда машина свободна. При обычной записи (`--date …`) массив `devices` файла замера, если он есть, сохраняется: в него люди вставляют записи со страницы `demo/bench.html` (формат — `../SPEC-format.md`).

Набор данных, процентили и сам замер лежат в `demo/bench_model.mjs` и общие со страницей `demo/bench.html` (в браузере тот же код считает те же наборы; время даёт `performance.now()`). Замеры на устройствах этими инструментами **не выполнялись**.

## Мутации (`mutate.mjs`)

Каталог — `MUTANTS` в самом файле: 61 порча одной строки `engine/money.mjs` и `engine/dates.mjs` (`<` ↔ `≤`, смена знака, режима округления, сдвиг константы). Мутант применяется **к копии** в `--work-dir`
(каталог внутри `prototype/` отвергается), запускаются файлы тестов по одному (сначала замок арифметики `tests/arith.test.mjs`), мутант убит, если хоть один красный. Контрольный прогон на неиспорченной копии идёт первым.
Неубитые мутанты попадают в `survivors` результата и в задачи; помеченные `equivalent` (порча не меняет поведения на достижимых входах) выживают по замыслу и перечислены отдельно с причиной.
Полный прогон занял около полутора минут на этой машине (2026-10-09); частичный — `--only M01,D03` (результат в файл не пишется).

### Мутации расчётного ядра (`mutate.mjs --catalog engine`, FP-24)

Каталог — `MUTANTS_ENGINE` в том же файле: 66 порч одной строки в `engine/timeline.mjs` (15), `afford.mjs` (14), `sinking.mjs` (9), `tax.mjs` (9), `fx.mjs` (7), `verifier.mjs` (12): граница `<` ↔ `≤`, смена знака, `min` ↔ `max`, подмена константы или переменной. Прежний каталог и его поля в `../_ops/mutation.json` не меняются; результат ядра пишется в раздел `engine` того же файла.
Копия кладётся в `<work-dir>/prototype` (engine/, ВСЕ tests/, tools/, data/ и рядом `<work-dir>/tools/lint_vocab.mjs`), мутанты идут по одному, каждый — отдельными процессами `node --test` по одному файлу (`KILLERS_ENGINE`): быстрый тест модуля, property-тесты на малом N (`PROP_N=40`, только девять инвариантов), golden G-001 и замок вывода движка (только проверка вывода 500 журналов). Мутант убит, если красен хоть один; предел на файл — `--timeout-s` (60), на мутанта — `--budget-s` (300). Тесты мутантов ядра идут в процессе раннера (`--test-isolation=none`): порча с бесконечным циклом убивается целиком по `--timeout-s` и не оставляет работающего процесса-сироты (прежний каталог money/dates запускается как раньше).

- Контрольный прогон на неиспорченной копии идёт первым; красный контроль останавливает прогон. Фильтр имён (`--test-name-pattern`), под который не подошёл ни один тест, — ошибка настройки, а не «зелёный» контроль.
- Результат: доля убитых считается среди неэквивалентных (порча, не меняющая поведения, помечается `equivalent: 'почему'` и в знаменатель не входит); норма — не менее 90 % (`ENGINE_KILL_RATE_MIN_PCT`). Выживший без пометки обязан иметь причину в поле `unkilled` каталога; `node tools/mutate.mjs --catalog engine --annotate` дописывает причины в файл результата без запуска тестов (поля `unkilled` и `equivalent` в хэш каталога не входят).
- Сухой прогон `--dry-run` только применяет каждую порчу к копии (фрагмент найден ровно один раз); синтаксис всех порч проверяет `tests/mutate_engine.test.mjs`. Первый полный прогон 2026-10-27 занял около семи минут (66 мутантов — 363 с, контрольный прогон и копирование — около минуты; один процесс node за раз): убито 64, выживший S04 назван с причиной, V07 — эквивалентный.
- **Матрица сетей (`--nets`, исправление 2026-10-28).** Без `--nets` мутант считается убитым на первом красном проверяющем (почти всегда это тест модуля), и по записи не видно, ловят ли его property-тесты, замок вывода и golden. С `--nets` каждый проверяющий (тесты модуля, а для каждого мутанта ещё и property-тесты на `PROP_N=40`, проверка вывода замка и golden G-001) запускается независимо; строка результата получает `nets` (какие сети убили: `module`, `properties`, `lock`, `golden`) и `invariants` (какие из TST-31…39 назвали property-тесты), а в разделе `engine` появляется `nets_summary`: сколько мутантов убила каждая сеть, кого не видит ни одна из трёх сетей поперёк модулей, итоги по модулям и по инвариантам. Прогон 2026-10-28 (≈ 11 минут, один процесс node за раз): убито 65 из 66 (S04 теперь убит `tests/hardening.test.mjs`, V07 эквивалентен); **property-тесты убивают 16, замок вывода — 19, golden — 23, тесты модулей — 65; 34 мутанта не видит ни одна из трёх сетей** (раздел `engine` файла `../_ops/mutation.json`, подробности и перечень — `../README.md`, «Матрица сетей»).

## Фаззинг (`fuzz_nightly.mjs`)

Короткий режим по умолчанию — `FUZZ_N = 2000`, `GP_SEEDS = 200`: проверяет, что ночной режим работает. Полный ночной режим — `--full` (`FUZZ_N = 100000`, `GP_SEEDS = 1500`, десятки минут и сотни мегабайт).
Три набора идут по одному: `tests/hardening.test.mjs`, `tests/validate_ws.test.mjs`, `tests/adversarial/golden_properties.test.mjs`.

**Полный прогон (FP-24).** `node tools/fuzz_nightly.mjs --full --date ГГГГ-ММ-ДД [--limit-min 60]` идёт под общим пределом времени (по умолчанию 60 минут): наборы — в порядке hardening → golden → validate_ws (самый долгий последним), каждому дают остаток времени; не уложившийся набор останавливается и записывается честно (`timed_out`, `complete: false`, список остановленных в `stopped_by_limit`). Ход длинных циклов пишет `tests/fuzz_progress.mjs` в файл из переменной `RUNWAY_FUZZ_PROGRESS` (раз в `of / 200` шагов): после остановки по пределу в результате видно, сколько повреждённых областей, журналов-копий, входов парсера и областей golden успели пройти (`loops`). ## Оракул hledger через Docker (`hledger_oracle.mjs`)

Зачем: тесты TST-44 сверяют экспорт hledger с мини-вычислителем, а настоящий `hledger` на этой машине не установлен — тест с оракулом пропускается. Скрипт выгружает G-001 тем же путём, что кнопка «Экспорт hledger»,
печатает команды `docker run` и ожидаемые остатки `assets:bank` из ряда `close` движка (на 1 ноября 2 055,00 €, на 1 декабря 3 400,00 €).

1. Ничего не запускается по умолчанию: `node tools/hledger_oracle.mjs --dir <каталог>` только записывает `g001.journal` и печатает команды.
2. Образ по умолчанию (`dastapov/hledger`) — **пример, не проверенный проектом (не подтверждено)**: прежде чем запускать, проверьте источник образа и закрепите его по хэшу (`--image имя@sha256:…`).
3. Контейнер получает каталог только для чтения (`-v …:/data:ro`) и работает без сети (`--network none`); точка входа задана явно (`--entrypoint hledger`).
4. `--run` запускает обе команды и сверяет остаток. Нужен Docker в `PATH`; без него скрипт сообщает об этом и ничего не делает. Результат сверки — в журнал релиза (`../CHECKLIST-release.md`), в `_ops/` он автоматически не пишется.

## Покрытие TST (`tst_coverage.mjs`, FP-51)

`node tools/tst_coverage.mjs [--report ../_ops/impl/run/verify-wave3a5.txt] [--out ../_ops/tst-coverage.json] [--check]` пересчитывает `../_ops/tst-coverage.json` по строкам `tests/…` сквозного прогона: `files` — число таких строк; `tests` — число вызовов `test(`, перед которыми нет точки, буквы, цифры, `_` или `$` (методы `t.test(…)` не считаются); `covered` — число упоминаний `TST-NN` в этих файлах для реестра NN = 01…60 (`TST-99` в фикстурах не считается); `missing` — номера реестра без упоминаний. Файлы на диске, которых не было в прогоне (например, файл проверяющего), не считаются и перечисляются в выводе. `--check` сравнивает с файлом и ничего не пишет (код выхода 1 при расхождении).

не проверяют типы (`jsconfig.json` готов, но `tsc` в проекте нет — зависимостей нет, REQ-155 не закрыт).
