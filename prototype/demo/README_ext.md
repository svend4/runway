# Каркас расширений демо (FP-01)

Для авторов пакетов FP-03…FP-10. Каркас даёт три вещи: **общий путь записи** («правка копии → проверка → пересчёт → показ»), **реестр**, в который пакеты подключают экраны, блоки и хуки, и **журнал**, который следует за правками. `app.mjs` не знает пакеты поимённо; пакет не импортирует `app.mjs`.

Расчёт по введённым данным и правилам, не консультация; налоговые формы — только «по правилам пользователя».

| `ext_manifest.mjs` | список пакетов `pack_fp03 … pack_fp16`, `pack_fp20`, `pack_fp22`, `pack_fp26`, `pack_fp28`, `pack_fp29` и загрузчики `import()`; отсутствие файла — норма | FP-01 (дополняют авторы пакетов: одна строка в `PACKS` и в `LOADERS`) |
| `dom.mjs` | `h`, `s`, `add_kids`, `table`, `open_dialog`, `close_dialog`, `announce`, `el_by_id` | FP-01 |
| `ws_edit.mjs` | чистые правки копии `ws`: `apply_edit`, `register_edit`, `register_validator`, `check_model` | FP-01 |

## Минимальный пакет

```js
// demo/pack_fp03.mjs
import { h } from './dom.mjs';
import catalog from './i18n/settings.mjs';          // { ru: { 'settings.nav': … }, en: { … } }

export function register(ext) {
  ext.register_i18n('settings', catalog);            // пространство имён = имя файла каталога
  ext.ensure_css('css/settings.css');                // только css/<имя>.css
  ext.register_view({
    id: 'settings', title_key: 'settings.nav', order: 45,
    render: (ctx) => h('div', { class: 'view' },
      h('h2', { id: 'view-title', tabindex: '-1', text: ctx.tr('settings.title') }),
      h('button', { type: 'button', class: 'btn', text: ctx.tr('settings.save'),
        onclick: () => ctx.edit({ type: 'set_param', key: 'buffer_minor', value: 60000 }) })),
  });
}
```

Файла пакета может не быть: загрузчик в `ext_manifest.mjs` это переживает (в браузере отсутствующий файл даёт строку 404 в консоли; интегратор вправе убрать из манифеста имена, которых в сборке нет). Тест пакета — `tests/<пакет>*.test.mjs`; в названии теста — `TST-NN` и `REQ-NNN`. Логику выносите в чистые модели (без DOM) и проверяйте в Node; DOM-часть — тонкая. Образец связки с настоящим `app.mjs` на заглушке DOM — `tests/ext_boot.test.mjs`.

## Реестр: `ext.register_*`

Падение `register` откатывает все регистрации этого пакета (экраны, блоки, хуки) и показывает сообщение; остальные пакеты и приложение работают. Ошибка описания (плохой `id`, неизвестный слот) — исключение `ExtError` внутри `register`.

| Вызов | Что делает |
|---|---|
| `register_view({id, title_key, order, render(ctx) → Node})` | экран `#id` в навигации. `id` — `[a-z][a-z0-9_]{1,24}`, не из экранов приложения (`overview buy waves reserves scenarios feed assistant data`). `title_key` — ключ строки «пакет.ключ». Места: экраны приложения — 10, 20, … 80; `order` по умолчанию 500; при равенстве — порядок регистрации |
| `register_slot_item(slot, {id, order, render(ctx) → Node \| Node[] \| null})` (у слота `waves.card` — `render(ctx, card)`) | блок в слоте: `overview.cards` (после сетки «узкая точка / Q1 / можно потратить»), `reserves.sections`, `data.sections`, `waves.actions` (один раз под календарём волн), `waves.card` (в конец КАЖДОЙ карточки волны на экране «Волны», S1.5; см. «Слот `waves.card`»), `assistant.extras`, `nav.actions` (кнопки действий в навигации — каждый узел слота лежит в своём `li.nav-action` второго списка навигации «Действия», `ul.nav-actions`, после списка разделов; см. «Навигация и порядок фокуса»), `banner.actions` (узлы в конец плашек «данные устарели» / «блок» в шапке: сверка прямо в плашке), `scenarios.after` (после таблицы сравнения на экране «Сценарии»), `banner.warning` (FP-15: в конец плашки КАЖДОГО предупреждения движка в шапке; `render(ctx, {warning})` — см. «Слот `banner.warning`»), `feed.head`, `feed.row`, `buy.form`, `buy.result` (FP-28: лента и экран «Купить», см. «Пакет FP-28») |
| `register_hook(name, fn)` | `scenario_ops`: `fn(ctx, sc, ws, income_ref) → ops \| null \| undefined` — новый вид сценария; первый ответ не `undefined` побеждает. `show_why`: `fn(ctx, mode) → Node \| Node[] \| null` — блоки в диалог «Почему». `boot`: `fn(ctx)` (может быть `async`) — после загрузки набора данных. `fmt`: `fn(ctx, lang, cur, as_of_iso, number_format) → форматтер | undefined` — формат чисел и дат отдельно от языка (REQ-112); первый ответ не `undefined` побеждает, иначе формат языка. `assistant` (FP-20): `fn(ctx, action, ...args)`, действия `chip` и `ports` — см. «Пакет FP-20»; для других действий вернуть `undefined`. `dataset_label` (FP-48): `fn(ctx, dataset_id) → {value, text} \| undefined` — подпись источника данных в переключателе «Набор данных» (см. «Пакет FP-48»); первый ответ не `undefined` побеждает. Возвращает функцию снятия |
| `register_i18n(pack, {ru, en})` | слияние каталога в одной точке (`i18n.mjs → register_strings`): паритет ключей RU/EN, одинаковые плейсхолдеры, ключи только `<pack>.*`, без пересечений с приложением и другими пакетами; нарушение — исключение, каталог не принят |
| `ensure_css('css/<имя>.css')` | подключает файл стилей (`<link>`), повтор безвреден; другие адреса — `ExtError` (CSP `style-src 'self'`) |
| `register_edit(type, fn)` | новый вид правки для `apply_edit` (см. ниже) |
| `register_validator(fn)` | общая проверка результата любой правки: `fn(ws_после, edit, env)` бросает `RunwayError` при отказе |

Экран, блок или хук, бросивший исключение, заменяется плашкой или пропускается; сообщение — через `ctx.notify`.

## Слот `waves.card`: блоки в карточках волн (этап S1.5)

`waves.actions` вызывается один раз на экран «Волны» (под календарём) и не знает, к какой волне относится кнопка. Слот `waves.card` нужен, когда действие относится к одной волне: приложение вызывает его **для каждой карточки** и кладёт узлы **в конец карточки** (после строки «зарезервировано»). Слоты с одним аргументом работают как прежде: `ext.slot_nodes(slot, ctx, ...extra)` передаёт `extra` в `render` после `ctx`, а без `extra` `render(ctx)` получает ровно один аргумент.

| Что | Как |
|---|---|
| Вызов приложения | `ext.slot_nodes('waves.card', ext.ctx, Object.freeze({wave, mode, index}))` — одна строка в `view_waves` (`app.mjs`); приложение пакет по имени не знает |
| `render(ctx, card)` | `card.wave` — волна движка («по плану»; карточки строятся по списку плана, метрики обоих режимов у каждой): `wave_id`, `event_ids`, `start`, `end` (эпохальные дни), `total_out_minor`; `card.mode` — режим страницы `'plan'` или `'worse'`; `card.index` — номер карточки в списке **с нуля** (номер волны на экране — `index + 1`). Объект заморожен: подменить карточку приложения блок не может. Чужую форму (нет волны, режима не `plan\|worse`, индекс не целое ≥ 0) блок должен молча пропускать, вернув `null` |
| Результат | узел, массив узлов или `null`, как у остальных слотов; порядок — по `order`, затем по порядку регистрации. Упавший блок пропускается (сообщение `ctx.notify`, запись в `diagnostics()` с меткой `slot:waves.card/<id>` — по одной на каждый вызов блока, то есть на карточку при каждой перерисовке); остальные блоки той же карточки, другие карточки и сами карточки целы. Текст исключения пользователю не показывается |
| Идентификаторы в DOM | уникальны на странице: берите режим и номер карточки (`wc-why-plan-0`, `wc-edit-worse-1`); поля диалога — свой префикс (`wcd-…`), чтобы не пересечься с идентификаторами страницы |
| Доступность | у кнопки видимый текст — начало доступного имени (`aria-label` = «Почему так: волна 1, 23 окт – 26 окт»); название и даты волны в имени обязательны, смысл не цветом, без inline-стилей |
| Регистрация | `ext.register_slot_item('waves.card', {id, order, render})`; пакет, упавший в `register` после регистрации блока, откатывается вместе с ним |

Кто использует. Пакет FP-07 (`pack_fp07.mjs` → `wave_edit.mjs`, блок `fp07_wave_card`, `order` 20) кладёт две компактные кнопки в `div.actions.wc-actions`: «Почему так» открывает штатный диалог «Почему волна N» (`open_wave_why` из `why_more.mjs`: разложение потребности волны, сумма строк равна пиковой просадке окна), «Править волну» открывает диалог с теми же правками, что блок `waves.actions`, — объединить с предыдущей/следующей волной (`plan_merge`), разделить перед платежом (`plan_split`), закрепить платёж отдельной волной (`plan_pin`). Запись — общая `apply_override` (проверка «уже записана» → `ctx.edit`), поэтому одна и та же правка с карточки и из блока «Правки волн» получает один идентификатор по содержимому и не плодит записи. Правки хранятся по платежам «по плану», а не по режиму страницы: на карточках режима «если хуже» те же правки. После успешной записи диалог закрывается (его кнопки устарели), итог читает скринридер. Прежний слот `waves.actions` и его поведение (в том числе идентификаторы `we-split-N`, `we-pin-N`) не менялись. Проверка — `tests/waves_card.test.mjs`.

## Контекст `ctx`

`ctx` один на приложение, заморожен; функции читают страницу в момент вызова.

| Поле | Смысл |
|---|---|
| `get_ws()` | текущая рабочая область (не мутировать: правка — только через `edit`/`set_ws`) |
| `get_model()` | модель расчёта страницы (`build_model`: `ctx.series`, `ctx.q1`, `inputs_hash`, …) |
| `edit(edit, {reason?, meta?, undo?})` | **основной путь записи**: `apply_edit` → пересчёт страницей → журнал → подписчики → перерисовка. Возвращает `{ok: true, ws}` или `{ok: false, error: {code, ctx}}`; при отказе данные не меняются, пользователь получает сообщение. `meta` и `undo` — как у `set_ws` |
| `set_ws(ws, {reason?, meta?, undo?})` | то же для готовой рабочей области (например, результат мастера). Отказ пересчёта страницей откатывает всё. `reason` — вид действия для подписчиков (по умолчанию `'edit'`); `meta` — необязательное язык-независимое описание действия для подписи «Отменить» (`{kind, amount_minor?, currency?}`); `undo: 'recorded'` — признак «стопка отмены уже записала это действие» (см. «Единая стопка „Отменить / Вернуть“») |
| `subscribe(fn)` | `fn({reason, ws, before, meta, undo})` после каждого успешного `edit`/`set_ws` (`reason` — вид правки или переданный; `before` — рабочая область до записи; `meta` и `undo` — переданные вызывающим или `null`) и после смены набора данных (`reason = 'adopt'`, без `before`; у него есть `source`, `dataset_id` и, если данные открыты из файла, `file_name` — FP-48); у `restore` есть необязательное поле `origin` (FP-48): `{kind: 'file', name}` для «Восстановить из файла», иначе `null`; возвращает отписку. Подписчики вызываются ДО перерисовки страницы. Сбой подписчика изолирован. Подписчикам, которым нужны только `reason` и `ws`, лишние поля не мешают |
| `refresh()` | перерисовать страницу без записи и без рассылки подписчикам (состояние хранилища изменилось); без страницы — пустой вызов |
| `adopt(ws, {source?})` | подменить набор данных целиком (восстановление из копии): журнал пересобирается, подписчики получают `adopt` с полем `source`; `{ok, error?}`. Подписчикам, которые не должны реагировать на восстановление, достаточно проверять `source` |
| `read_only()` | режим «только чтение» (FP-17): `null` или неизменяемое описание `{newer_format, format, format_version, known_version, skipped, source}`; пока он включён, `edit` и `set_ws` отклоняются (см. «Режим „только чтение“») |
| `journal` | журнал текущей рабочей области (создаётся при первом обращении из `ws_to_events`, дальше дописывается разностью); `null`, если страница ещё без данных |
| `tr(key, params)`, `lang()`, `mode()`, `fmt()` | строки (каталоги приложения и пакетов), язык `ru\|en`, режим `plan\|worse`, форматтеры денег и дат (`fmt().money`, `.date`, `.short`, `.bp`, `.days`) |
| `notify(msg, kind)` | сообщение пользователю (`aria-live` и заметка страницы); `kind` — `info\|error` |
| `new_id(prefix)` | идентификатор сущности `prefix_<12 hex>` (`rule`, `tx`, `anc`, `fx`, …); создаёт приложение, а не пользовательский текст |
| `ask(вопрос)` | «Спросить ассистента» (FP-28): страница открывает экран «Ассистент» с заготовкой вопроса в поле ввода (до 200 знаков; вопрос сам не отправляется, текст попадает только в значение поля); `true`, если страница это умеет, иначе `false`; не строка — `false`. Заготовку снимает отправка вопроса и уход с экрана |

## Правки: `ws_edit.mjs`

`apply_edit(ws, edit, env?) → {ok: true, ws', type, touched} | {ok: false, error: {code, ctx}}`. Чистая: исходная область не меняется (можно передать замороженную), неизменённые корзины разделяются. Результат принимается целиком или отвергается целиком. `env`: `as_of` (по умолчанию `ws.as_of`), `new_id`, `deep` (после правки вызвать `analyze` и вернуть его отказ).

Коды ошибок — канон (REQ-017): `E_NOT_INTEGER`, `E_OVERFLOW`, `E_BAD_DATE`, `E_FUTURE_POSTED`, `E_RULE_INVALID`, `E_CURRENCY_MISMATCH`, `E_NO_RATE`, `E_SCHEMA`. `ctx` ошибки — `{field, reason, value?}`; названий, заметок, меток и получателей в нём нет. Ключи `__proto__`, `constructor`, `prototype` отвергаются на любой глубине; неизвестные поля сущностей — `E_SCHEMA`; идентификаторы — единое пространство `Id` (`rule_id`, `stream_id`, `tax_rule_id`, `reserve_id`, счёт, сценарий… не совпадают, C-025).

| `type` | Поля | Особенности |
|---|---|---|
| `add_fact` | `fact: {event_id?, account_id, date, amount_minor, currency?, kind?, tag?, note?, counterparty_id?, …}` или `legs: [{…}, {…}], transfer_id?` | дата не позже `as_of` (`E_FUTURE_POSTED`); валюта счёта (`E_CURRENCY_MISMATCH`); иностранный operating-счёт без курса — `E_NO_RATE`; перевод — две ноги, одна валюта → сумма 0, разные → курс или `fx` |
| `void_fact` | `event_id` | убирает факт (обе ноги перевода); в журнале — `revert` |
| `set_anchor` | `anchor: {anchor_id?, account_id, date, amount_minor}` | сверка остатка одним числом; дата не позже `as_of` |
| `set_param` | `key, value` или `key, reset: true` | ключи — из `PARAM_SPECS` (сверены с `vocab.json`; `kdf.*` не редактируются); границы и типы; `null` только у необязательных (`buffer_minor`, `wave.threshold_minor`, `decision_currency`). `reset: true` («вернуть по умолчанию», FP-17) снимает собственное значение: ключ пропадает из `params` и действует умолчание словаря; у необязательных параметров ключ остаётся с явным `null`, как и при чтении журнала (`ws_bridge`); ключа нет — рабочая область та же (по ссылке); `reset` вместе с `value`, `reset` не `true` и `decision_currency` — отказ `E_SCHEMA` (`reset_with_value`, `reset_must_be_true`, `not_resettable`) |
| `upsert_account` | `account: {account_id, name, kind, liquidity, currency, exponent?, liquidity_bp?, opened_on?, closed_on?}` | смена валюты счёта с записями — `E_CURRENCY_MISMATCH` |
| `upsert_rule` / `delete_rule` | `rule: {…}` / `rule_id` | `validate_rule` движка (`E_RULE_INVALID`); правка существующего с изменённым содержимым повышает `version`; удаление убирает и правки вхождений |
| `upsert_stream` | `stream: {…}` | `validate_stream` движка |
| `upsert_tax_rule` | `tax_rule: {…}` | версия **добавляется**, прошлые не правятся; сумма ставок на один поток/метку ≤ 10000 bp (`E_RULE_INVALID`); `reserve_id` должен существовать. Расчёт по введённым правилам, не консультация |
| `upsert_reserve` | `reserve: {…}` | `tax` или `sinking` (режим, цель, срок — по виду) |
| `record_allocation` | `allocation: {allocation_id?, reserve_id, date, amount_minor, source, rule_version?}` | идемпотентна по `allocation_id`; `source = income` требует `rule_version` |
| `upsert_fx_rate` | `rate: {fx_id?, date, base, quote, num, den, source?}` | дробь `num/den` как введена |
| `add_purchase` | `purchase: {purchase_id?, name, currency?, parts: [{date, amount_minor}]}` | 1…120 частей |
| `save_scenario` / `delete_scenario` | `scenario: {scenario_id?, name, ops[]}` / `scenario_id` | операции проверяются по списку движка; журнал фактов не затрагивается (REQ-014) |
| `set_wave_override` | `override: {override_id?, action, event_ids[], pin_range?}` или `{override_id, remove: true}` | правка с тем же id уходит в конец списка: порядок применения = порядок записей |
| `add_counterparty` | `counterparty: {counterparty_id?, name, usual_delay_days?}` | |

Идентификатор в правке (`event_id`, `anchor_id`, …) можно не задавать, если в `env` есть `new_id` (через `ctx.edit` он есть). Сообщения об ошибках введённых значений идут раньше сообщения «нет идентификатора».

`check_model(ws)` — полная проверка рабочей области (файл, импорт, тесты): возвращает `{ok, errors}`, не бросает. `register_validator` — место, куда интегратор подключит `validate_ws` движка (FP-02).

## Мост `ws ↔ журнал`: `ws_bridge.mjs`

Рабочая область — массивы по видам сущностей (как `data/g001.json`), состояние движка — словари по идентификатору (свёртка журнала). Мост закрывает расхождение:

- `ws_to_events(ws, {next_id?, recorded_at?, start_seq?})` → записи `account.opened`, `rule.set`, `tx.posted`, … с `seq` от 1; по умолчанию идентификаторы детерминированы (`evt~000001`), время ввода — `as_of`;
- `events_to_ws(events, base?)` → `reduce(effective_events(events))` и `state_to_ws`; `base` важнее журнальных метаданных (например, «сегодня»);
- `ws_to_journal(ws)` / `journal_to_ws(text)` — файл-копия `runway-journal/1` (через `io.export_json`/`read_journal_json`);
- `sync_journal(journal, before, after)` — дописывает записи разности: новое — `set`, изменённое — запись с `supersedes_id`, удалённое — `revert` действующей записи **и всей цепочки её замен** (откат одной последней записи вернул бы исходную по канону C-070).

Круг без потерь проверен на четырёх наборах G-001: тот же `inputs_hash` и те же числа (`tests/ws_bridge.test.mjs`, TST-38, REQ-094). Что мост не переносит: `imports`, `extra` (согласия, черновики) и `matches` — их в `ws` нет (привязки вшиты в факты как `plan_ref` / `no_plan`; если у существующего факта изменились ТОЛЬКО они, `diff_ws_to_specs` пишет запись `match.set` вместо замены `tx.posted`, FP-11). Поля `ws` вне корзин (`workspace_id`, `name`, `locale`, `decision_currency`, `as_of`, любые прочие) хранятся одной записью `profile.set` с зарезервированным `profile_id = 'ws:meta'`. Элемент без идентификатора получает служебный `auto:<корзина>:<номер>`, при возврате в `ws` он снимается. Идентификатор факта в `ws` — `event_id` (в журнале — `entity_id` записи `tx.posted`).

## Единая стопка «Отменить / Вернуть» (`undo.mjs`, этап S1.3)

«Отменить» откатывает **любое** действие пользователя, записанное общим путём `ctx.set_ws` / `ctx.edit`: формы FP-08 (платежи и правила, пропуск вхождения, часы, налоговые правила, накопления, курсы, счета, рассрочка), настройки FP-03 (`set_param`, «Сегодня» — `set_as_of`, `set_number_format`), сценарии и правки волн FP-07, контрагенты и покупки, ввод и удаление факта. Автору пакета для этого ничего делать не нужно: стопку ведёт подписчик пакета FP-04 (`pack_fp04.mjs` → `auto_record`), а он получает от `ctx.set_ws` рабочую область «до» и «после» (поле `before` в событии `subscribe`) и сам строит единицу по разности.

**Единица отмены — один пользовательский шаг.** Это разность `before → after` по всей рабочей области: если шаг затронул несколько корзин (удаление правила убирает и его пропуски вхождений; форма «счёт + остаток» пишет счёт и якорь), единица всё равно одна. Один вызов `ctx.set_ws` = одна единица: не дробите шаг на несколько записей.

| Что отслеживается | Ключ в единице | Особенности |
|---|---|---|
| корзины-массивы с идентификатором (все корзины `ws_bridge.BUCKETS`: факты, якоря, аллокации, резервы, счета, календари, правила, потоки часов, налоговые правила, курсы, сценарии, покупки, долги, правки волн, контрагенты, планы, профили) | `{bucket, key, before, after}`, `before`/`after` — элемент или `null` | ключ элемента — правило моста `ws_bridge.item_key` (одно на мост и стопку; пустая строка — не ключ), составные ключи: `overrides` — `rule_id@nominal_date`, `tax_rules` — `tax_rule_id@version`; у правок волн поле `seq` (его ставит свёртка журнала) при сравнении не учитывается; элементы без идентификатора и вложенные массивы `tax_rules` (устаревшая форма) не отслеживаются |
| `params` (слот по ключу параметра) | `{bucket: 'params', key, before, after}`, значение — коробка `{value}` или `null` | значение `null` отличается от «ключа нет»; ключи `__proto__`, `constructor`, `prototype` не отслеживаются |
| метаполя верхнего уровня (`as_of`, `number_format`, `name`, `locale`, `decision_currency` и любые прочие не-корзинные поля, `ws_bridge.meta_of`) | `{bucket: 'meta', key, before, after}`, коробка `{value}` или `null` | поле можно добавить, сменить и убрать (`number_format` убирается правкой с `null`) |
| порядок и «не было вовсе» | необязательные поля единицы `order`, `presence` | `order` пишется, только если простое «заменить / добавить в конец / убрать» порядок не воспроизводит (удаление из середины списка, правка волн, уходящая в конец): тогда отмена возвращает элемент на прежнее место, а чужие элементы остаются при своём соседе. Чистая перестановка (по ключам ничего не менялось, изменился только порядок: правка волн, сохранённая заново с теми же значениями, уходит в конец списка, а порядок входит в `inputs_hash`) — тоже действие пользователя: единица с пустым `changes` и непустым `order`; её отмена проверяет сам порядок (изменённый помимо стопки — `undo_conflict`). `presence` — корзина или `params` отсутствовали до действия: после отмены нет пустого массива |

Для четырёх прежних корзин (`UNDO_BUCKETS`: факты, якоря, аллокации, резервы) формат записи не менялся. Корзины `UNDO_ARRAY_BUCKETS` совпадают с `ws_bridge.BUCKETS` (проверяет тест): новая корзина в мосте без отмены тест не пропустит.

**Что в стопку НЕ пишется** (константы `UNDO_CLEAR_REASONS` и `UNDO_SKIP_REASONS` в `undo.mjs`, общий список `UNDO_EXCLUDED_REASONS`; сверка по исходному коду — `tests/undo_all.test.mjs`):

| Причина записи (`reason`) | Что происходит | Почему |
|---|---|---|
| `undo`, `redo` | не пишется | это сами «отменить» и «вернуть»: единицу они переносят между стопками |
| `adopt` | стопка очищается (и память счёта, отказы по переводам) | набор данных заменён целиком (`ext.reset`, `ctx.adopt`) |
| `restore` | стопка очищается | «Продолжить с сохранённого», «Восстановить из файла», подтяжка записей другой вкладки (FP-05) заменяют набор целиком |
| `import`, `import_rollback` | не пишется, стопка не очищается | мастер импорта FP-06 имеет свой «Откатить партию» с реестром партий. Прежние единицы после импорта либо остаются валидными, либо дают честный `undo_conflict` |
| `undo_refresh`, `guard_answer` | не пишется | служебная перерисовка и ответ «оставить как есть» без изменения данных |

Исключить свою причину из стопки нельзя без правки списка в `undo.mjs`: он один на приложение. Новый мастер пакетной записи, у которого есть своя отмена, должен писать с причиной из этого списка (или добавить её туда).

**Признак «уже записано».** Действия FP-04 («+ Факт», «Сверить остаток», ответ о переводе) записывают единицу в стопку САМИ, ДО `ctx.set_ws`, чтобы кнопки навигации, которые страница перерисовывает внутри записи, уже видели новое состояние. Такие вызовы передают `ctx.set_ws(ws, {reason, undo: 'recorded'})` (константа `UNDO_RECORDED`), и подписчик вторую единицу не пишет. Признак ставится только если единица реально записана; без своей стопки (`deps.undo` не передан) действие запишет общий подписчик. Событие `subscribe` приносит `undo` как есть, поэтому другой подписчик может им пользоваться.

**Подпись действия.** `meta.kind` → строка `entry.u_*` (RU и EN, `UNDO_LABEL_KEYS`): расход, приход, перевод, сверка остатка, уменьшение резерва (подписи FP-04, с суммой), а также `settings`, `today`, `rule`, `stream`, `tax_rule`, `reserve_edit`, `account`, `rate`, `scenario`, `wave_override`, `counterparty`, `purchase`, `fact_removed`; неизвестный вид — общая подпись `entry.u_other`. Если вызывающий не передал `meta`, вид берётся по причине записи (`REASON_KINDS`: вид правки → вид действия), а для неизвестной причины — по изменённым корзинам. Названий, заметок и других пользовательских текстов в подпись не попадает. Новый вид правки (`register_edit`) стоит добавить в `REASON_KINDS` — иначе подпись будет определена по корзинам (тест `undo_all` ловит вид правки без подписи).

**Чужие правки между действием и «Отменить» (честный `undo_conflict` вместо битых данных).** Единица применяется, только если элементы такие, какими их оставило действие; сверх этого:

| Случай | Что делает стопка | Где |
|---|---|---|
| единица убирает элемент (счёт, правило, календарь, поток, накопление, контрагента, долг…), а на него ссылается запись, добавленная помимо стопки (например, импортом: счёт создан пользователем, выписка загружена на него) | отказ `undo_conflict` (`ctx.cause = 'dangling_ref'`, `ctx.bucket` — корзина записи-источника), данные не трогаются, единица снимается. Считаются только НОВЫЕ висячие ссылки: то, что висело до отмены (чужой файл), ей не мешает; если единица убирает и сам элемент, и ссылающиеся записи (форма «счёт + остаток»), конфликта нет | `UNDO_REFS` в `undo.mjs`: те ссылки, которые приложение проверяет само при записи (`ws_edit`) и чтении (`validate_ws`): `account_id` у фактов, якорей, планов, правил, потоков; `counterparty_id` у фактов и правил; `calendar_id` у правил и потоков; `rule_id` у пропусков вхождений; `reserve_id` у налоговых правил и аллокаций; `applies_to.stream_ids`; `backed_by_account_id`; `pay_account_id`. Непроверяемые приложением ссылки (`rule_id`/`stream_id`/`reserve_id` у факта, `tax_rule_id` у накопления, `reserve_id` у плана, `counterparty_id` у потока) не отслеживаются: иначе законная запись давала бы ложный конфликт |
| страница отказала в записи итога отмены, и расчёт на этой же рабочей области падает так же («Сегодня» нельзя вернуть раньше проведённой чужой записи, `E_FUTURE_POSTED`) | единица снимается как `undo_conflict` (`ctx.cause = 'refused'`, `ctx.code` — код канона), пользователь видит «данные изменились», следующая «Отменить» доходит до более ранней единицы (стопка не залипает) | `refusal_code(ws)` в `undo.mjs`: проба `analyze(ws, {as_of: ws.as_of})` — то же, что считает страница (`app.build_model`) |
| временный отказ (страница недоступна, исключение хозяина, расчёт на итоге проходит) | единица возвращается на место, как раньше; ошибка страницы отдаётся как есть | `create_undo_stack.run` |

**Что не менялось.** Предел `UNDO_LIMIT = 50`; конфликт (`undo_conflict`) снимает единицу без записи и не трогает данные; новое действие очищает «Вернуть»; журнал остаётся append-only (отмена — `revert` и `supersedes_id` через `ctx.set_ws` → `sync_journal`, префиксный хэш прежней части не меняется). Ограничение журнала: если параметра не было вовсе и его задали, отмена записывает в журнал `null` (журнал не умеет «удалить ключ») — рабочая область и `inputs_hash` возвращаются точно, а `state_hash` журнала может отличаться; при ЧТЕНИИ журнала (`ws_bridge.state_to_ws`: перезагрузка из хранилища, восстановление из файла) `null` необнуляемого параметра (все ключи `PARAM_RANGES`, кроме `buffer_minor`, `wave.threshold_minor`, `decision_currency`) снова становится «ключа нет», поэтому рабочая область и `inputs_hash` после перезагрузки равны сеансовым (`tests/undo_fix.test.mjs`); полное решение — запись «параметр снят» в самом журнале — потребует правки свёртки движка и в этот этап не входит; то же у факта, возвращённого отменой его удаления (в состоянии журнала у факта хранится идентификатор самой записи, а возвращённый факт — новая запись), и у правки волн, возвращённой отменой снятия или правки (в состоянии журнала у неё `seq` записи). Для остальных корзин (в том числе правил, сценариев, потоков, налоговых правил, настроек, метаполей) `state_hash` после отмены равен хэшу до действия — это проверяет `tests/undo_all.test.mjs`.

## Журнал: `journal_log.mjs`

`create_journal({events?, snapshots?, snapshot_every = 500, keep_snapshots = 2, ports?, verify?})`:

- `append(type, payload, {entity_id?, actor?, causation_id?, supersedes_id?})` — запись создаёт `make_event` (форма, `v`, `seq` обязательны; float отвергается); ссылки `revert`/`supersedes_id`/`causation_id` — только на известные ранние записи; запись замораживается. `append_many(specs)` — пачка «всё или ничего». `append_event(e)` — готовая запись (импорт): `seq` строго больше последнего;
- `prefix_hash(n)` — цепочка хэшей по первым `n` записям; после `append`, снимка, свёртки и экспорта хэш прежнего префикса не меняется;
- `state()` → `{state, used_snapshot, from_count}`: свёртка «снимок + хвост»; `state_hash()`; `take_snapshot()`; `export()` → `{events, snapshots}` (сериализует хранилище, FP-05);
- `snapshot_info()` → `{engine_version, held, stale}` (FP-17): версия движка журнала, используемые снимки (`engine_version: null` — снимок без метки) и снимки другой версии, отброшенные при открытии.

Версия движка в снимке (FP-17, REQ-016). Снимок несёт `engine_version` (и снимок самого журнала, и `take_snapshot(events, count, engine_version?)`). Снимок ДРУГОЙ версии (`opts.engine_version`, по умолчанию `ENGINE_VERSION`) при открытии не используется и не сверяется по `state_hash`: его арифметика могла отличаться, состояние досчитывается из записей, а новый снимок ложится по обычному правилу «хвост достиг `snapshot_every`». Записи журнала при этом не меняются; отброшенные снимки перечислены в `snapshot_info().stale`, а экран «Данные» показывает предупреждение, не отказ. Снимок без метки (сохранён до FP-17) принимается как раньше. `fold(снимок, хвост) = fold(журнал)` при любой метке проверяет `tests/engine_stamp.test.mjs` на 10^3 случайных журналах.

Правило снимка. Свёртка `fold(снимок, хвост)` равна `fold(всё)`, **если хвост не откатывает и не заменяет запись из префикса снимка**; иначе берётся более ранний снимок или полная свёртка (`used_snapshot = false`). Хвост с двойной привязкой факта (`match.set` и по ключу факта, и по `event_id` записи) тоже идёт полной свёрткой: порядок привязок канонический клон базы не сохраняет. Состояние из `state()` — только чтение (значения разделяются между снимками).

Замеры REQ-153 (Node v24.13.0, Windows 11, дата 2026-10-05, `tests/journal_log.test.mjs`): журнал **36 536 записей**, снимок взят на длине 36 236, в хвосте 300 записей; открытие файла (`JSON.parse` + `open_journal` + `state()`) **со снимком — 0,6–1,0 с** (цель ≤ 2 с; в тесте — лучшее из трёх замеров), **без снимка — 1,5–4 с** (полная свёртка всего журнала; разброс — от нагрузки машины, на свободной машине около 1,5–1,8 с); размер записи в JSON ≈ **274 байта** при допущении 250 (отклонение +10 %, в пределах ±50 %); файл без снимка ≈ 9,5 МиБ. Тест измеряет заново при каждом прогоне и печатает `n`, дату и числа через `t.diagnostic` (`node --test tests/journal_log.test.mjs`). Оценка «без снимка ≈ 2 с» значит: снимок обязателен на журналах порядка 10^4 записей и больше.

## Идентификаторы: `ids.mjs`

`make_id_gen({now_ms, random})` → `{next(), entity(prefix), instant()}`; порты внедряются, модуль сам не читает часы и случайность. `next()` — uuidv7 (48 бит времени, счётчик внутри миллисекунды), строго возрастает даже при замершем или идущем назад времени. `system_ports()` — часы и `crypto.getRandomValues` для страницы; `seeded_ports({seed, start_ms, step_ms})` — для тестов. `is_valid_id(x)` — допустимый идентификатор сущности (непустая строка до 128 знаков, без `|` и управляющих знаков, не `__proto__`/`constructor`/`prototype`).

## Навигация и порядок фокуса (этап S1.4)

`#nav` (`<nav aria-label="Разделы">`) содержит **два списка подряд** — именно в этом порядке на любой ширине окна:

| Список | Класс и подпись | Что внутри |
|---|---|---|
| 1 | `ul.nav-sections`, `aria-label` «Разделы приложения» / «App sections» | `li > a[href="#раздел"]` по реестру (`ext.nav_items`); у текущего раздела `aria-current="page"` |
| 2 | `ul.nav-actions`, `aria-label` «Действия» / «Actions» | `li.nav-action` — по одному на каждый узел слота `nav.actions` (в порядке `order` слота). Список рисуется только если пакеты что-то дали |

Порядок в DOM = порядок Tab = порядок на экране (WCAG 2.4.3). **CSS не переставляет эти списки**: в `style.css` и `css/*.css` на элементах навигации нет `order`, `flex-direction: *-reverse`, `float`, `direction` и размещения в сетке — менять можно только направление, перенос и прокрутку; стили пакета для своей кнопки в слоте (`.nav .nav-action .btn { … }`) допустимы, а прятать пункт (`display: none`, `position: absolute/fixed`, `opacity: 0`, нулевой размер) нельзя. Это проверяет `tests/nav_focus.test.mjs`. Раскладки:

- **от 1024 px** — левая колонка шириной 220 px, липкая к верху окна (`position: sticky`) и не выше окна за вычетом `--nav-gap` (запас на шапку, пока она видна: 8,5 rem от 1024 до 1279 px, где шапка переносится, и 6 rem от 1280 px). Разделы — прокручиваемая часть (`flex: 1 1 auto; min-height: 0; overflow-y: auto`), действия лежат **под** ними (`flex: 0 0 auto`) и видны без прокрутки списка из 18 разделов. Выбран порядок «разделы, затем действия», а не наоборот: в узких раскладках (полоса и нижняя панель) ссылки разделов — основная навигация, и действия первыми вытеснили бы их за край;
- **600–1023 px** — полоса разделов (прокрутка вбок) и под ней ряд действий с переносом;
- **до 599 px** — нижняя фиксированная панель в два ряда: разделы, под ними действия (ряд прокручивается вбок, не переносится). `.content` оставляет снизу 8,5 rem под панель. Панель в целом стоит внизу экрана, хотя в DOM она раньше `main` — как у любой нижней панели; к содержимому ведёт ссылка «К содержимому».

Фокус-кольцо: у ссылок раздела — внутрь (`.nav a:focus-visible { outline-offset: -3px }`), потому что списки прокручиваются и внешнее кольцо обрезал бы `overflow`; у кнопок действий — поля списка не меньше 5 px (кольцо 3 px + отступ 2 px). Цели касания прежние (ссылки ≥ 44 px, кнопки действий ≥ 36 px). Цвета — только токены тем. Кнопка слота, которая бывает недоступной (как «Отменить»), должна иметь причину и снимать `disabled`, когда причина исчезла; `tabindex="-1"` у пунктов навигации не ставится.

**Телефон (FP-26, U22): группа «Ещё».** В узком окне (≤ 599 px, `matchMedia`; `nav_more.mjs`) `render_nav` отдаёт построенные списки функции `group_nav`, и вместо двух списков панель содержит три узла подряд: `ul.nav-sections.nav-primary` (вкладки Обзор · Купить · Лента · Волны), `details.nav-more` (кнопка `summary#nav-more-sum` «Ещё» и `ul.nav-more-list` с остальными разделами в порядке реестра) и прежний `ul.nav-actions`; у `#nav` добавляется класс `nav-grouped`. Порядок DOM по-прежнему равен порядку на экране и порядку Tab, CSS его не переставляет; разделы и действия не прячутся и не дублируются (проверяет `tests/layout_fp26.test.mjs`). На широком окне и там, где нет `matchMedia` (заглушки DOM), списки остаются такими, какими их построило приложение, — два списка S1.4. Состояние «раскрыто» хранится в модуле и переживает перерисовку (страница перерисовывает навигацию целиком, в том числе поздней перерисовкой от хранилища); нажатие на раздел закрывает список (и сам узел `<details>`, даже если раздел уже открыт и перерисовки не будет; фокус уходит на «Ещё»), Escape закрывает его по состоянию узла и возвращает фокус на «Ещё»; перерисовка, уронившая фокус на `body`, возвращает его на вкладку или «Ещё» через `focus_keep.mjs` (`nav_keep_focus()` в конце `render()`). Тот же хранитель обслуживает кнопки плашки сценария, которые убирают или заменяют нажатую кнопку: `keep_focus_after_render(id)` (`sc-apply-N`, `sc-remove-N`, `view-title` для «Вернуться к базе»). Действия на телефоне в этом режиме **переносятся** (`flex-wrap: wrap`, отдельный блок `@media (max-width: 599px)` в `style.css`), а не прокручиваются вбок: «Вернуть» и «?» больше не уходят за край окна 375 px; нижний отступ содержимого под панель — 12 rem (запас на три строки действий). В низком узком окне (`@media (max-width: 599px) and (max-height: 480px)`: масштаб 200 % на телефоне, телефон набок) панель — обычный блок под шапкой (`position: static`) и отступа под неё нет. На широком окне (≥ 1024 px) колонка навигации — `min(13.75rem, 40vw)`, подписи переносятся (`white-space: normal`), а не обрезаются.

`register(ext, env)` принимает второй необязательный аргумент `env` (`ports`, `storage`, `metrics`) — только для тестов: загрузчик реестра его не передаёт. В приложении метрики берут `globalThis.localStorage` (если он недоступен — работают в памяти страницы), часы — `ids.clock_ports()`.

**Ключ хранилища.** Метрики лежат в `localStorage` под `runway-metrics/1` (`metrics.METRICS_KEY`). Любой новый ключ пакета тоже должен начинаться с `runway`: «Удалить все данные» (FP-05, `data_actions.erase_all`) стирает ключи по этому префиксу, а чужие ключи общего `localhost` не трогает (урок UI-2). Модуль метрик замечает исчезновение своего ключа и до перезагрузки ничего не пишет.

**Выключатель и очистка.** «Очистить метрики» (`metrics.clear()`) стирает собранное, но не отменяет отказ пользователя: если счёт выключен, вместо стирания ключа пишется пустой пакет с `enabled: false`, и `begin_session`/`bump`/`record_step` ничего не пишут и после перезагрузки страницы. Включённый счёт очищается стиранием ключа, как прежде. «Удалить все данные» (FP-05) стирает ключ целиком, поэтому выключатель возвращается в исходное положение (счёт на устройстве включён; наружу ничего не уходит) — так задумано, текст экрана «Метрики» об этом говорит. Если понадобится хранить отказ и после «Удалить все данные», он должен лежать вне префикса `runway`, что противоречит правилу общего `localhost` (урок UI-2): решение владельца.

**Схема `runway-metrics/1`.** `metrics.validate_package` — единственное место, где определено, что может попасть в файл: ровно десять ключей, целые числа в границах, строки только из закрытых списков (шаги, исходы, имена счётчиков), ни сумм, ни календарных дат, ни идентификаторов. Новое поле — правка схемы и теста (`tests/metrics.test.mjs`, независимый проверяющий код в самом тесте). Экран показывает `package_text()` и скачивает ровно этот текст.

**Фокус и время шагов мастера.** Хранилище FP-05 после каждой записи просит `ctx.refresh()` ещё раз (`data_runtime.ping`), и страница заменяет узел, на котором стоял фокус. Поэтому запрос фокуса мастера (`request_focus`) не снимается после первой отрисовки, а действует `FOCUS_WINDOW_MS` (3 с, по часам порта `now_ms`): каждая отрисовка в этом окне возвращает фокус на заданный узел (по `id`), но только если он «потерян» (`document.activeElement` — `body` или нет вовсе); чужой фокус не отбирается. Таймер шагов (`create_step_timer`): повторная отрисовка того же шага (возврат с другого экрана, смена языка, поздняя перерисовка) времени не засчитывает; время засчитывают действие пользователя (`touch`, в том числе отправка формы — `run_step` вызывает его до записи) и смена шага; пауза до действия — не больше `idle_cap_ms` (минута).

**Страница v0** (`demo/v0.html`) — не пакет и не экран приложения: отдельный документ со своим CSP (`connect-src 'none'`), без реестра, мастера, метрик и хранилища; тест `tests/v0.test.mjs` проверяет по графу импортов, что `v0.mjs` не тянет `app.mjs`, `ext.mjs`, `wizard.mjs`, `metrics*.mjs`, `store*.mjs`. Общее с приложением: движок, `ws_edit.apply_edit`, `ws_bridge.journal_to_ws`, `number_format`, `dom.mjs`, `rule_kit.make_rule`. Файл правится руками, поэтому форма из него проверяется до сборки (`v0.form_is_valid`: типы, закрытые списки, целые суммы, настоящие даты, виды резервов без повторов); непригодная форма не доходит до `form_to_ws` (он сам не бросает исключений), файл открывается как чужой, а при сбое отрисовки состояние страницы возвращается прежним. Введённое, но не принятое, не пропадает при добавлении или удалении строки (`keep_inputs`: черновики полей на одну отрисовку; поля отправленной формы очищаются).

**Тесты.** `wizard.test.mjs` (логика шагов, ошибки, экран на заглушке DOM, шаблон, a11y, RU/EN), `start_boot.test.mjs` (настоящий `app.mjs`: набор `g001-empty`, `ov.empty`, мастер, «Отменить», метрики, «Удалить все данные»), `v0.test.mjs`, `metrics.test.mjs`, `fp10_adv.test.mjs` (пробы независимого проверяющего: отказ от метрик переживает очистку, фокус после поздней перерисовке, испорченная форма v0, подсказка шага, время вне экрана, введённое в v0, числа v0 по независимому оракулу).

**Правило для авторов пакетов.** Любая правка файла из `demo/`, `engine/` или `data/`, который входит в оболочку, требует `npm run build` (из `prototype/`): иначе `tests/build_manifest.test.mjs` красный, а воркер откажется устанавливать копию с несовпавшими
хэшами. Новый файл попадает в оболочку, если на него есть ссылка (импорт, `ensure_css('css/…')`, `new URL('…', import.meta.url)`, строка `'../data/….json'`, ссылка из HTML); файл без ссылки в оболочку не входит.

**CSP.** К прежней политике (`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'none'`) добавлены только `manifest-src 'self'` и `worker-src 'self'` — в мета-теге
`index.html` и в заголовке `serve.mjs`. `v0.html` остаётся без сети и без воркера (`connect-src 'none'`).

**Сеть после загрузки (REQ-120).** Сетевые обращения приложения — один `fetch` набора данных в `app.mjs` (при загрузке и при выборе другого набора) и проверка обновления браузером (`sw.js`, `shell_manifest.json`). `fetch(` в остальных модулях `demo/` по-прежнему нет
(проверка `demo.test`). Инвентарь и сценарии Q1, Q3, импорт, экспорт — `tests/offline_inventory.test.mjs`.

## Слот `banner.warning`: действие в плашке предупреждения (волна 3а, FP-15)

Плашки предупреждений в шапке (`W_RESERVE_RESIDUAL`, `W_RULE_STALE`…) раньше были только текстом. Слот вызывается для **каждого** предупреждения из `Analysis.warnings` и кладёт узлы **в конец его плашки**; приложение пакет по имени не знает (одна строка в `render_summary`).

| Что | Как |
|---|---|
| Вызов приложения | `ext.slot_nodes('banner.warning', ext.ctx, Object.freeze({ warning: w }))` — по одному разу на предупреждение при каждой перерисовке шапки |
| `render(ctx, arg)` | `arg.warning` — объект предупреждения движка (`{code, reserve_id?, rule_id?, …}`), заморожен вместе с `arg`. Чужое предупреждение блок пропускает, вернув `null`; форму `arg` без `warning` тоже |
| Результат | узел, массив узлов или `null`, как у остальных слотов; перед узлами приложение ставит пробел. Упавший блок пропускается (сообщение `ctx.notify`, запись в `diagnostics()` с меткой `slot:banner.warning/<id>`), плашка остаётся текстом |
| Идентификаторы | уникальны на странице: возьмите номер сущности (`fp15-hdr-release-0`); шапка рисуется на любом экране |
| Фокус | кнопка исчезает вместе с предупреждением, а шапка перерисовывается на любом экране, где нет вашего хранителя фокуса: возвращайте фокус сами (`reserve_release.refocus_later([...])`: несколько попыток через 0 / 120 / 400 / 1200 мс, фокус отбирается только если он «потерян») |

Кто использует. Пакет FP-15 (`pack_fp15.mjs`, блок `fp15_release`): кнопка «Освободить остаток» в плашке `W_RESERVE_RESIDUAL` (остаток резерва после платежа в срок); для `W_RESERVE_OVERDUE` и правил кнопки в шапке нет — действие на экране «Резервы», в карточке резерва, где виден срок и объяснение.

### Режим «только чтение» (REQ-016)

Файл НОВЕЕ известного формата (`runway-journal/N`, N больше `KNOWN_FORMAT_VERSION = 1`) или с записями новее известных версий (`v` выше текущей, неизвестный тип) открывается для просмотра, а не отвергается кодом `E_SCHEMA`:

- `engine/io_readonly.mjs`: `open_readonly(text)` разбирает файл БЕЗ апкаста и БЕЗ записи — `{read_only, newer_format, format, format_version, known_version, engine_version, events, usable_events, skipped: {unknown_type, newer_version, bad_event, total}}`. Читаемые записи (`usable_events`) сворачиваются как обычно; пропущенные не угадываются. Запись без `v` в файле ТЕКУЩЕГО формата — повреждение (`E_SCHEMA`), в новом формате — пропуск. Прежние строгие пути (`read_journal_json`, `import_json`, `upcast`) остаются строгими. Также `format_status`, `workspace_format_info` (набор данных G-001 несёт то же поле `format`), `event_unreadable_reason`;
- `data_actions.inspect_import(text)`: для такого файла `ok: true`, `read_only: true`, `read_only_info: {newer_format, format, format_version, known_version, skipped, source: 'file'}`, `ws` из читаемых записей, `hash` — состояние по ним, `engine` — сравнение версии движка. Если читать нечего (читаемых записей нет), отказ прежний: `E_SCHEMA` с `newer_format`, `newer_version` или `unknown_type`;
- `data_runtime.open_readonly(parsed)`: страница показывает набор через `ctx.adopt(ws, {source: 'readonly', read_only})`, в хранилище и его метаданные НЕ пишется ничего; запись приостанавливается (`paused`, причина `readonly`) или остаётся в `fresh`. `restore(parsed)` для такого файла отвечает `{ok: false, error: 'read_only'}`; в диалоге «Восстановить из файла» вместо «Заменить данные» одна кнопка «Открыть только для просмотра»;
- реестр `ext.mjs`: `ctx.read_only()`; `reset(ws, {read_only?})` включает режим (набор с полем `format` новее известного определяется сам, источник `workspace`). Пока режим включён, `ctx.set_ws` и `ctx.edit` отклоняются ДО страницы и журнала (`{ok: false, error: {code: 'E_SCHEMA', ctx: {reason: 'read_only'}}}`) и сообщают понятный текст `ro.refused`; `edit` проверяет режим раньше самой правки (иначе пользователь увидел бы технический отказ `newer_format`). Исключение — `set_ws(ws, {reason: 'restore'})` («Продолжить с сохранённого», «Восстановить»): это не правка, а замена открытого набора сохранёнными данными; успешный `restore` режим снимает. Выход из режима — любой `reset`/`adopt` (выбор набора данных, мастер, загрузка файла);
- интерфейс: в шапке плашка `ro.banner` / `ro.banner_records` (формат файла и известный, число пропущенных записей), экран «Настройки» — заметка `ro.settings`, все поля и кнопки отключены; остальные формы отключает центральный отказ реестра (кнопки не гасятся по одной, отказ сопровождается текстом).
- исправления после независимой проверки (Д1–Д5, `tests/fp17_fix.test.mjs`; второй круг В1/С1, `tests/fp17_fix2.test.mjs`): `entry.error_text`, `forms.error_text`, `import_wizard.error_text`, `settings.error_text` и (С1) `wizard.error_message` мастера «Старт» при `error.ctx.reason === 'read_only'` возвращают `ro.refused` (формы пакетов и `reason_text` календаря/долга сходятся в `forms.error_text`); подтверждение правила на экране «Резервы» (`reserve_rules.mjs`) в этом режиме тоже показывает `ro.refused`, а не «Правило не подтверждено (код …)»; в `app.mjs` признак режима читается одной строкой `ro_now` (В1: слов `ext` в коде 24, предел `waves_card` — 25), кнопка «Выгрузить JSON», `export_state` и плашка шапки пользуются ею; среда хранения (`data_runtime`) учитывает просмотр — `replace_saved` отвечает `{ok: false, error: 'read_only'}` и ничего не стирает, `export_copy()` бросает ошибку с `code: 'read_only'` и не заводит `pending_backup`, `status().read_only`; `pack_fp05.make_runtime` передаёт `deps.read_only = ctx.read_only` (без него — признак, который ведут `open_readonly` и события `adopt`/`restore`); экран «Данные» показывает плашку `#fp05-ro-note` (`data_view.readonly_state_node`: формат, число пропущенных, что отключено), отключает «Скачать журнал» и «Выгрузить JSON» (`app.mjs`), скрывает напоминание о копии, а в карточке «В этом браузере есть сохранённые данные» — «Начать с текущего набора» (`data_view.read_only_info`); `inspect_import` помечает файл `unusable` / `read_only_info.unusable`, если по читаемой части прогноз не построить (`data_actions.forecast_probe` — `analyze` в `try`), диалог говорит причину словами (`data.readonly_unusable`) и не предлагает открыть, `open_readonly` отвечает `unusable`. Таблица «Все параметры» (Д4): `settings_defaults.NOT_YET_USED` — девять параметров словаря, которых расчёт из `ws.params` не читает (`crypto.liquidity_bp`, `backtest.h_days`, `backtest.min_window_days`, `calib.window|prior|k|alpha_bp|min_origins`, `mc.n_paths`); `default_row(...).used === false`, в таблице «не используется» вместо «Действует», состояние «пока не используется расчётом»; тест `fp17_fix` сверяет список с кодом в обе стороны. ### Версия движка в снимке и в копии (REQ-016)

Хук читается в `app.mjs` **одной строкой** через помощник `a0_hook` (строк со словом `ext` — 25 из 25 по пределу `waves_card`).

```js
// хук assistant: (ctx, action, ...args) → результат | undefined (первый ответ не undefined побеждает; null — «пакет не отвечает по существу»)
ext.register_hook('assistant', (ctx, action, ...args) => {
  if (action === 'chip') return render_answer_chip(ctx, args[0] /* Result */, args[1] /* 'c_…' */, args[2] /* open_numbers() */); // узел или null
  if (action === 'ports') return make_ports(ctx, view);   // { journal, call_log, last_call, record? } или null
  if (action === 'note') return 'строка пояснения' /* args[0]: info ответа ask_a0 */ ; // допущения ответа (какое поступление сдвинуто, чем ограничен журнал) или undefined
  return undefined;
});
```

| Действие | Кто вызывает | Что возвращает |
|---|---|---|
| `chip` | `app.mjs`, `calc_chip(result, ref)` — у каждого ответа ассистента и у вердикта Q3 на «Купить» | узел чипа происхождения (`span.a0-origin`: `details.sc-chip` из `render_origin_chip` + кнопки «Числа расчёта» и «почему?») или `null` — тогда приложение рисует прежнюю кнопку «числа из расчёта c_…». Третий аргумент — действие, которое открывает таблицу чисел (её показывает приложение, чтобы формат чисел пользователя применялся в одном месте) |
| `note` | `app.mjs`, `a0_note_node(m.info)` — под ответом ассистента | строка пояснения допущений (`answer_notes`): «Сдвигается поступление «имя», дата»; «Сравнение идёт по журналу этой страницы: он начинается {дата}…»; год даты, ушедшей на прошлый год. Или `undefined` — абзаца нет. Числа ответа пояснение не меняет: их сверяет верификатор |
| `ports` | `app.mjs`, обработчик вопроса на экране «Ассистент» | порты для `ask_a0(model, text, lang, income_ref, ports)`: `journal` (записи `ctx.journal.events()`), `call_log` (`call_id → день`), `last_call` (hex предыдущего вызова), `record(result, args)` — запись `assistant.call` (**только хэши**, `engine/call_log.mjs`). В режиме «только чтение» `record` нет |

Правила для авторов:
- Запись вызова — только `record_call`/`call_event` из `engine/call_log.mjs`: в журнал уходят `call_id`, `tool`, `args_hash`, `inputs_hash`, `engine_version`; текст вопроса, значения аргументов, суммы, даты и заметки в запись не кладутся (ADR-013). Хранить ли аргументы ради повтора по `call_id` — решение владельца (FP-34).
- Пакет подписывается на событие `adopt` и обращается к `ctx.journal`: журнал страницы создаётся сразу после открытия набора данных, а не при первом вопросе (иначе правки до первого вопроса попали бы в снимок открытия и пропали бы из «что изменилось»).
- «Что изменилось» получает не сырой журнал страницы, а `changes_view(events, since)` (`engine/call_log.mjs`): журнал страницы собирается из рабочей области при открытии, все записи набора стоят одним моментом `<as_of>T00:00:00Z` — это снимок, а не история. Основание раньше первого дня журнала — отказ `no_history`; снимок открытия изменением не считается; «с даты» — с начала дня, «с прошлого раза» — по порядку записей. Допущения ответа о сдвиге — шаблоны каталога (`EXT_NOTES` в `verifier.mjs`), а не дописанный текст: срок сдвига входит в эхо `q.shift_days`.
- Новый вид вопроса A0 — запись в `EXT_INTENTS` (`engine/verifier.mjs`), а не правка прежних правил `parse_assistant_command`: таблица опрашивается после прежних правил, так что прежние вопросы отвечают как раньше. Причина отказа новой записи (`reason`) должна иметь строку `as.<reason>` в `i18n.mjs` и строку в отображении причин в `view_assistant`.
- Узлы чипа и диалоги строятся `dom.mjs` (текст — `textContent`); пакет не импортирует `app.mjs`.
- Журнал вызовов — журнал страницы (`ctx.journal`, память вкладки), на диск не пишется; не опирайтесь на него как на хранилище.

Тесты: `tests/call_log.test.mjs` (журнал вызовов, порт `call_log`, CSV), `tests/assistant_ext.test.mjs` (таблица намерений, `ask_a0` с портами, чип и «почему», настоящий `app.mjs` на заглушке DOM), `tests/purity.test.mjs` (ранг `call_log`).

## Тексты пакетов: императивы и ставки (волна 3а-2, FP-25)

Правила для строк в `demo/i18n.mjs` и `demo/i18n/*.mjs` (проверяют `tests/imperatives.test.mjs`, `tests/no_default_rates.test.mjs` и обычный запуск `node ../tools/lint_vocab.mjs`; на `prototype/`: `npm run lint:words`):
- **Повелительное наклонение — только «проверьте», «введите», «сверьте»** (EN: check, enter, reconcile, compare). «Добавьте …», «Заполните поля», «Нажмите …», «Выберите …», «Откройте …», «Подтвердите …» и любые другие формы на -йте/-ьте/-ите — ERROR линтера: он называет файл, ключ и язык. Список — константа `ALLOWED_IMPERATIVES` в `tools/lint_vocab.mjs`, не в `vocab.json`.
- Вместо команды пишите состояние или возможность: «поля не заполнены», «поступление не внесено», «платёж можно отметить отменённым в «Сверке»», «счёт добавляется в разделе «Счета»», «числа скрыты до подтверждения или правки правила», «кнопка «Обновить» её применит». Подписи кнопок и ссылок по-русски — инфинитивы («Добавить», «Сохранить»).
- EN: предложение-указание (строка кончается точкой или «!») не должно начинаться с команды (любой переходный глагол перед артиклем или местоимением — «Adjust the buffer.» — тоже команда; отрицательные «Do not …», «Don't …», «Never share …» — тоже) и не должно содержать её после «:», «;», запятой и «and/or/then»; подпись кнопки без точки («Add to the forecast») и вопрос в названии окна допустимы. Те же правила действуют для шаблонов `engine/verifier.mjs` и `demo/start_template.mjs` (подписи операций черновика — «Moving / Skipping / Adding the payment …», как RU «Перенос / Пропуск / Добавление платежа»).
- Предупреждение, после которого пользователь может потерять данные, не должно утверждать, что приложение что-то сделает само, если этого код не делает: «Копию можно скачать до замены на экране «Данные»; это окно ничего не скачивает» (`data.restore_warn`, `data.replace_warn`), «файл нужно сохранить самостоятельно» (`v0.file_hint`). Нейтральная форма — это описание возможности или обязанности пользователя, а не пассив вместо команды. Названия элементов в тексте ставьте в кавычки («Undo» takes the entry back).
- Часть фразы, за которой код ставит ссылку или кнопку (`reconcile.pick_plan_none`, `reconcile.cancel_rule_hint`, `reconcile.queue_empty_hint`), остаётся незаконченной ровно как раньше: меняйте текст так, чтобы ссылка продолжала предложение.
- **Ставок и стран в строках нет**: ни «ставка N %», ни названий стран и налоговых режимов (IVA, НДС, VAT …) в каталогах, шаблонах и профилях; ставка — только то, что пользователь ввёл в `ws.tax_rules`. Литерал `rate_bp: N` в `engine/`, `demo/`, `tools/` — нарушение (сканер в `no_default_rates.test.mjs`); демо-правило 20 % набора G-001 — единственное исключение с причиной, и оно лежит в данных, не в коде.

Правила группы лежат в `style.css`, а не в `css/layout.css`: css пакетов раскладку навигации не меняет (guard `tests/s1_4_adv.test.mjs`).

## Известные ограничения и открытые вопросы

- `reduce(events, base)` движка клонирует базу целиком (канонический JSON состояния) — на 36 500 записей это дороже 2 с, поэтому свёртка хвоста в `journal_log.mjs` собрана из «частичной базы» (сам `reduce` при этом вызывает движок). Запрос к FP-02: режим `reduce` без клонирования — `_ops/impl/hook-requests-FP01.md`.
- Привязка факта в `matches` сразу по ключу и по `event_id` порядко-зависима в самом движке (клон базы теряет порядок ключей); для таких журналов снимок не используется.
- `validate_ws` (FP-02) подключён в конце `ws_edit.mjs` через `register_validator`: результат каждой правки проверяется целиком (`as_of` берётся из `env`); значения полей в отказ не попадают. Цена — один проход по рабочей области на правку (≈ 70 мс на 5 000 фактов), поэтому пакетный импорт (FP-06) пишет партией через `ctx.set_ws`, а не циклом `apply_edit`.
- `set_param` теперь умеет «вернуть значение по умолчанию» (`reset: true`, FP-17): ключ удаляется из `params`, у необязательных параметров остаётся явный `null`. Валюту решения вернуть нельзя (она задаётся при создании рабочей области); `kdf.*` не редактируются.
- Метаданные рабочей области лежат в профиле `ws:meta` (`profile.set`): отдельного вида записи в каноне нет. Если канон v1.2 введёт его, достаточно поправить `ws_bridge.mjs`.

## Хвосты волны 3а-5 (FP-50): часы страницы v0 и матрица часов

Реестр расширений и пакеты не менялись. Страница v0 берёт «сегодня» из порта часов: `boot_v0(ports)` принимает `{now_ms, tz_offset_min}` (`ids.clock_ports()` по умолчанию; порт без `tz_offset_min` дополняется смещением устройства, D-4); тесты подставляют фиксированные часы. Хвост после независимой проверки: мастер импорта (`import_wizard.mjs`) — чтение выбранного файла (CSV, профиль, журнал hledger) рисует результат через `redraw_live` и отбрасывает его, если набор данных сменили (правило 10; тесты D-1…D-3 в `tests/fp50_adv.test.mjs`). Матрица часов и поясов (`tools/clock_matrix.mjs`, `tools/clock_shift_preload.mjs`) подменяет часы процессу только при переменных `RUNWAY_CLOCK_*`; раздел «Матрица часов и поясов» — в `../README.md`. Новых чтений часов в `demo/` и `engine/` нет: страница v0 читает часы через порт `ids.clock_ports()`, как и раньше читала устройство напрямую.
