# Движок налоговых правил

Страница описывает арифметику по правилам, которые вводит пользователь. **Это расчёт по введённым правилам, не консультация.** В продукте нет ставок, сроков подачи, налоговых календарей и шаблонов стран; примеры ниже — иллюстрации с параметрами вымышленного пользователя «Ян» (G-001, **горизонт 57 дн.**, `as_of` 2026-10-04) и ничего не утверждают о действующем законодательстве. Юридическое ревью формулировок обязательно до публичной беты; если оно признает налоговую часть консультацией, она удаляется (REQ-183, [ADR-015](../decisions/adr-015-v1-slice.md)). Алгоритм — [ALG-06](../algorithms/alg-06-tax-envelope.md), решение — [ADR-009](../decisions/adr-009-tax-rules-as-data.md); суммы — minor units (279000 = 2 790,00 €).

## Принципы

| Движок делает | Движок не делает |
|---|---|
| Считает аллокацию `mul_div(gross, rate_bp, 10000, rounding)` по правилу пользователя | Не знает ставок, лимитов, сроков и режимов налогообложения стран |
| Выбирает версию правила по плановой дате поступления `base(e)` (для проведённого — по фактической) | Не определяет налоговый статус пользователя |
| Держит резерв и высвобождает его при платеже, который ввёл пользователь | Не создаёт платежей сам, не подаёт деклараций |
| Показывает возраст правила и предупреждает о его устаревании | Не комментирует законность и «оптимизацию» |

Правило — **данные**, а не код: в сборке 0 предзаполненных `rate_bp` и 0 шаблонов стран (REQ-068). Смена ставки не переписывает прошлое: версии вместо правок. Налоговый платёж — обычное плановое обязательство «на дату X сумма Y»; оно попадает в волны и в прогноз. Каждое налоговое число сопровождается оговоркой и возрастом правила.

## Модель правила (v1)

| Поле `TaxRule` | Тип | Смысл и ограничение |
|---|---|---|
| `tax_rule_id`, `version` | Id, int | строки с одним `tax_rule_id` — версии одного правила |
| `name` | string | название пользователя |
| `kind` | enum | v1: только `percent_of_income` |
| `rate_bp` | Bp | целое 0…10000 (2000 = 20 %) |
| `base` | enum | v1: только `gross` |
| `applies_to` | `{stream_ids[], tags[]}` | к каким поступлениям: `stream_ids` сопоставляются с `e.stream_id` события потока, `tags` — с `e.tag` (C-025); пустое — ошибка |
| `valid_from`, `valid_to?` | IsoDate | действует при `valid_from ≤ d < valid_to` |
| `rounding` | enum | `half_even` (по умолчанию), `half_up`, `floor`, `ceil` |
| `reserve_id` | Id | в какой резерв идёт аллокация |
| `reviewed_at?`, `ttl_days?` | IsoDate, int | дата проверки и срок годности; задаются парой |
| `source_note?` | string | свободная заметка пользователя; недоверенный текст |
| `recorded_at` | Instant | когда введено; в арифметике не участвует |

Связанные сущности: `Reserve{kind: tax, funded_start_minor, funded_as_of, tax_rule_id?}` (`mode` у налогового резерва не обязателен, C-020; `funded_open` для движка — проекция `reserve_open`) и `Allocation{reserve_id, date, amount_minor, source, source_event_id?, rule_version?}`. В v1 резерв всегда виртуален (`backed_by_account_id = null`): деньги не двигаются, `close` и `trough` не меняются, уменьшается `free` ([ADR-016](../decisions/adr-016-reserves-and-safe-to-spend.md)).

Что из «полного» налогового набора где живёт:

| Аспект | v1 | v2 (данные со схемой, сроком годности и ревью) |
|---|---|---|
| Ставка | `rate_bp` с версиями по датам | ступенчатые ставки |
| База: брутто и нетто | `base = gross`; нетто после резерва — справочно (`gross − Σ аллокаций`) | `net_of_levy` и другие базы |
| Вычеты, лимиты | нет: учитывает пользователь в проценте или платеже | параметры схемы режима |
| Квартальные авансы с датами | правило повторения + `reserve_id`; даты и суммы вводит пользователь | режимы с окнами дат |
| Валюта | аллокация и резерв — в валюте решения; `planned` — `spot` на `as_of`, `posted` — курс даты факта при записи `allocation.recorded`; далее не переоцениваются (X4, C-038) | резерв в валюте платежа, переоценка |

## Выбор версии и аллокация

```pseudo
rule_at(rules, rule_id, d):                       # d = base(e) = max(plan_date, as_of) для planned (не зависит от режима, C-016); для posted — фактическая дата
  C = [r для r в rules: r.tax_rule_id == rule_id и r.valid_from ≤ d и (r.valid_to == null или d < r.valid_to)]
  return C пуст ? null : argmax по (recorded_at, version) из C
allocation(e, r) = mul_div(e.amount_minor, r.rate_bp, 10000, r.rounding)       # одно округление на поступление
day i:  релиз платежей дня → reserve_trough[i] → аллокации от доходов дня → reserve_close[i]
release_on_payment(funded, p) = {released: min(funded, p), true_up: p − released}
```

Порядок дня важен: аллокация от дохода дня попадает только в `reserve_close`, иначе `trough` и резерв берутся в разном порядке и дают искусственный минус. G-001, правило `TR-20` (2000 bp от `gross` потока `S-HOURLY`, `valid_from` 2026-01-01):

| Поступление | Расчёт | Результат |
|---|---|---|
| Выплата за сентябрь 288000 (уже в `funded_start`) | `mul_div(288000, 2000, 10000)` | 57600 |
| Выплата за октябрь 279000 (`plan` 2026-11-05, `worse` 2026-11-19) | `mul_div(279000, 2000, 10000)` | 55800 |
| Границы часов: 80 ч / 110 ч | 240000 / 330000 | 48000 / 66000 |
| Округление: 123457 при 2100 bp, `half_even` | 259,2597 € | 25926 (259,26 €) |
| Ничья: 4900 при 2250 bp | 1102,5 | `half_even` 1102, `half_up` 1103, `floor` 1102, `ceil` 1103 |

## Версии во времени

| Версия | `rate_bp` | `valid_from` | Применяется к доходу 300000 |
|---|---:|---|---|
| 1 | 2000 | 2026-01-01 | на 2026-06-30: 60000 |
| 2 (введена позже) | 2200 | 2026-07-01 | на 2026-07-01 и позже: 66000 |

Версия 1 без `valid_to` остаётся применимой и после 2026-07-01, но версия 2 введена позже (больший `recorded_at`) и побеждает: на 2026-07-02 аллокация — 66000. Проведённая аллокация хранит `rule_version`. Если 2026-10-04 пользователь вводит версию 3 «2200 bp с 2026-05-01» задним числом, проведённая аллокация за 2026-05-15 (60000, версия 1) не меняется, а плановые считаются по новой; запрос «что мы знали тогда» (`known_at`) — v2.

**Плановая дата, а не дата режима (C-016).** Версия выбирается по `base(e) = max(plan_date, as_of)` — дате, которая от режима не зависит; в `worse` доход сдвигается на 14 дней, но версия правила остаётся той же. Иллюстрация (синтетика): версия 2 (2200 bp) с `valid_from` 2026-11-10. Октябрьская выплата `plan_date` 2026-11-05 → версия 1 → 55800 и в `plan` (приход 11-05), и в `worse` (приход 11-19); прежняя привязка к сдвинутой дате дала бы 61380 в `worse` и расхождение рядов не только из-за сдвига дохода — она отменена. `reserve_close` на конец горизонта — 167800 в обоих режимах, свободный остаток на конец — 172200 в обоих. Версия 2 применится к поступлениям с `plan_date ≥ 2026-11-10`; проведённый доход — по фактической дате. Благодаря равенству аллокаций при `Σ rate_bp ≤ 10000` безусловно `free_worse ≤ free_plan` ([ALG-11](../algorithms/alg-11-safe-to-spend.md), инвариант 8).

## Платежи и высвобождение

Платёж — обязательство пользователя с `reserve_id`. G-001, `P-TAX1` −50000 на 2026-10-23: `reserve_trough` 150000 → 100000, `trough` 377500 → 327500, `free` 227500 до и после; `released` 50000, `true_up` 0. При `funded_start` 30000: `released` 30000, `true_up` 20000, `free` падает 347500 → 327500. Платёж входит в волну W1 вместе с арендой и ЖКХ (`total_out` 152000, [ALG-03](../algorithms/alg-03-payment-waves-detection.md)).

Квартальные авансы — обычное правило повторения ([ALG-01](../algorithms/alg-01-recurrence-expansion.md)) с параметрами пользователя. Иллюстрация: `R-TAXQ`, `freq M`, `interval 3`, `start_date` 2026-10-23, сумма −50000, `weekend = next`, `is_obligation`, `reserve_id = RES-TAX`. Номинальные даты считаются от начала без дрейфа: 2026-10-23 (пятница), 2027-01-23 (суббота → 2027-01-25), 2027-04-23 (пятница). Даты и суммы — выбор пользователя; продукт не утверждает, что они соответствуют чьим-либо срокам.

## Доход и «чужие деньги»

**Доход** — то, что остаётся пользователю. **«Чужие деньги»** — часть поступления, которую он передаст дальше: удержание у источника или НДС-подобный сбор, включённый в счёт. Деньги приходят на счёт целиком (`close` и `trough` — физические), но свободна не вся сумма. В v1 `base = gross`, и разделения нет: пользователь подбирает процент либо заводит второе правило с другим `applies_to` и резервом.

Иллюстрация вне G-001: счёт на 110000, из них условный сбор 1000 bp включён в сумму. Справочная формула `levy = mul_div(gross, r_bp, 10000 + r_bp)` = `mul_div(110000, 1000, 11000)` = 10000; собственная часть 100000; правило пользователя 2000 bp от неё — 20000; откладывать 30000. Единый процент от `gross` даёт 30000 / 110000 = 2727,27 bp: 2727 bp → `mul_div(110000, 2727, 10000)` = 29997 (−3), 2728 bp → 30008 (+8). Для одного счёта ошибка — единицы minor; но если сбор есть не в каждом счёте, единый процент систематически смещён, поэтому счета с сбором и без него разводят метками `applies_to.tags` в два правила. Точное разделение (`base = net_of_levy`) — v2. Платёж «чужой» части вводится как обычное обязательство и высвобождает свой резерв; пока он не наступил, эти деньги не входят в `free`.

## Аудит-след

Журнал не мутирует: правка — новая запись (`supersedes_id`), откат — `revert`. Следы: `taxrule.set` (каждая версия), `reserve.set`, `allocation.recorded` (со `rule_version`), `revert`. `inputs_hash` включает версии правил, поэтому расчёт воспроизводим; `state_hash` защищает круг «экспорт → импорт». Пример записи после проведения октябрьской выплаты:

```json
{"type":"allocation.recorded","v":1,"entity_id":"RES-TAX","payload":{"reserve_id":"RES-TAX","date":"2026-11-05","amount_minor":55800,"source":"income","source_event_id":"<id проведённой выплаты>","rule_version":1},"recorded_at":"2026-11-05T09:12:00Z","actor":"system"}
```

У каждого налогового числа есть панель «как посчитано»: правило и версия, период действия, поступление и его `gross`, формула, округление, результат, возраст правила.

| Поле | G-001 |
|---|---|
| Правило | `TR-20`, версия 1, 2000 bp, `base = gross`, с 2026-01-01 |
| Поступление | `S-HOURLY@2026-11-05`, `gross` 279000 |
| Формула | `mul_div(279000, 2000, 10000, half_even)` |
| Результат | 55800 → резерв `RES-TAX` (558,00 €) |
| Проверка правила | `reviewed_at` 2026-10-04, `ttl_days` 120: свежее |

Ассистент ставок не называет; инструмент `get_tax_envelope` отдаёт `reserved`, `by_rule`, `next_due` и `notice` ([спецификация ассистента](06-ai-assistant-spec.md)); `reserved` — сумма только резервов `kind = tax` (ряд `reserve_close` на дату `as_of` аргумента, режим `headline_mode`), `by_rule[].amount` — накоплено по резерву правила; G-001 на 2026-11-30: 155800 (с `RES-INS` всего 167800; C-077).

## Валидация правил

| Проверка | Условие | Реакция |
|---|---|---|
| Вид и база | `kind = percent_of_income`, `base = gross` | `E_RULE_INVALID` |
| Ставка | целое от 0 до 10000; 0 — допустимая пауза | `E_RULE_INVALID` («ставка от 0 до 100 %») |
| Округление | из четырёх значений | `E_RULE_INVALID` |
| Период | `valid_to` пуст или позже `valid_from` | `E_RULE_INVALID` |
| Резерв | `reserve_id` задан; существование проверяет слой журнала (проект) | `E_RULE_INVALID` |
| Область | `stream_ids` или `tags` не пусты (C-032) | `E_RULE_INVALID` |
| Единое пространство `Id` | `tax_rule_id`/`rule_id` не совпадает со `stream_id` рабочей области (C-025) | `E_SCHEMA` |
| Срок годности | `reviewed_at` и `ttl_days` — вместе; `ttl_days ≥ 1`; дата проверки не позже сегодняшней | `E_RULE_INVALID`, `E_BAD_DATE` |
| Сумма ставок на одно поступление | Σ `rate_bp` ≤ 10000 | `E_RULE_INVALID` при сохранении по событиям горизонта и при расчёте |
| Пересечение версий | допустимо; побеждает больший `recorded_at`, затем `version` | предупреждение в форме |
| Дата дохода раньше всех `valid_from` | правила нет — аллокации нет | предупреждение в `Result.warnings` |

Текст ошибки не повторяет введённую строку. Векторы: 10001 bp, `valid_to` = `valid_from`, пустой `applies_to`, `reviewed_at` без `ttl_days` — отказ; 0 bp — принято.

## Экран «Налоги и часы»

Экран `tax_hours` ([экраны](03-ux-screens.md), REQ-108): блок потока доходов (ставка, часы, ожидаемая выплата) и блок конверта: правило, ставка, `valid_from`, возраст и состояние, остаток резерва, ближайший платёж, список версий. Форма правки: название, процент (ввод «20» → 2000 bp), «применять к» (потоки и метки), «действует с» и «до», округление, резерв, дата проверки и срок в днях. Подсказок ставок и советов «как снизить налог» нет. Под каждым числом: «Расчёт по введённым правилам, не консультация» (EN: “Calculated from the rules you entered; not tax or legal advice”).

**Предпросмотр «что будет с конвертом»** — эфемерная правка рабочей области в памяти, без записи в журнал (REQ-108); это не операция сценария и не «сценарий 22 %»: новой операции над ставкой в наборе D-14 в v1 нет (C-073). G-001, правка 20 % → 22 % с 2026-11-01:

| Величина | Было | Стало |
|---|---:|---:|
| Аллокация с выплаты за октябрь | 55800 (558,00 €) | 61380 (613,80 €) |
| `RES-TAX` на конец горизонта | 155800 | 161380 |
| `reserve_close` на конец горизонта | 167800 | 173380 |
| `free` на конец горизонта (`plan`) | 172200 | 166620 |
| `S_max(2026-11-20)` | 122200 | 116620 |
| Вердикт дорожки 300,00 € на 12 октября | `FRAGILE` | `FRAGILE` (минимум 41000 наступает до выплаты) |
| «Можно потратить» до 19 ноября (`worse`) | 21000 | 21000 |

Правка влияет только на часть горизонта после прихода дохода. Сохранение пишет `taxrule.set`; отмена — `revert`. Состояния: пусто («Правило не задано: конверт не считается»; если в рабочей области есть доход, но нет ни одного `TaxRule` и `Reserve`, — плашка `W_NO_RESERVES`: «налоговый конверт и накопления не заданы: вердикт и «можно потратить» посчитаны по физическим деньгам», C-065), свежее, устаревшее (`W_RULE_STALE`, пометка у каждого зависимого числа), не подтверждённое (`disabled`: зависящие числа заменены текстом, `W_RULE_DISABLED`), ошибка валидации.

**Срок годности** (X8, v1.1, C-023): одна формула, без скрытых констант. `age = today − reviewed_at` в календарных днях; `fresh` при `age ≤ ttl`, `stale` при `ttl < age ≤ 2·ttl`, `disabled` при `age > 2·ttl`. Константа «ttl + 120» отменена. Без `reviewed_at`/`ttl_days` правило `fresh` с пометкой «проверка не отмечена».

| `reviewed_at` 2026-10-04, `ttl_days` | `fresh` по | `stale` с — по | `disabled` с |
|---:|---|---|---|
| 120 | 2027-02-01 | 2027-02-02 — 2027-06-01 | 2027-06-02 |
| 90 | 2027-01-02 | 2027-01-03 — 2027-04-02 | 2027-04-03 |

**Поведение `disabled`** (C-024): расчёт `free` **продолжается** (аллокации и резерв остаются: иначе вердикт стал бы оптимистичнее), в `Result.warnings` — `W_RULE_DISABLED`; числа, зависящие от правила (`reserved`, `free`, `STS`, вердикты Q3, `S_max`, `earliest`), интерфейс заменяет текстом «правило не подтверждено с <даты>: подтвердите или измените» — через общий `gate` Q3 и «можно потратить» (причина `rule_disabled`, C-018); скрывается показ, а не вычисление. Q1 и волны физические и не затронуты. Это решение арбитра, помеченное как требующее взгляда владельца: блок числа может раздражать пользователя, не обновившего правило за `2·ttl`.

Берём: процент при поступлении, версии по датам, платёж в волнах, диапазон и оговорку. Не берём: зашитые ставки и сроки.

## Не в v1

Именованные режимы (накопительный аванс от прибыли с начала года, чистый НДС-подобный сбор), `base` кроме `gross`, вычеты, лимиты, окна дат и шаблоны стран — v2, только как данные со схемой параметров, сроком годности и обязательным ревью (REQ-072). `known_at` в интерфейсе, резерв в валюте платежа с переоценкой — v2. Привязка резерва к реальному счёту — v1.1; пока перевод «в конверт» при действующем резерве вызывает предупреждение о двойном вычитании (REQ-063). «А что если 22 %» в v1 — предпросмотр правки без записи (C-073); операции правила в наборе сценариев нет.
