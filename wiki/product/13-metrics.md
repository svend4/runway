# Метрики успеха и качества

> Страница фиксирует, что мы измеряем, по каким формулам, как — без слежки за пользователем, и какие цели считаем гипотезами. Определения исходов (FRR, cry-wolf, MAE, покрытие) согласованы с [ALG-13](../algorithms/alg-13-plan-vs-actual-calibration.md); гейты и критерии остановки — из [ADR-014](../decisions/adr-014-testing-approach.md) и [ADR-015](../decisions/adr-015-v1-slice.md). Числа примеров — G-001 «Ян» (**горизонт 57 дн.**, буфер 500,00 €) либо учебные векторы ALG-13, это указано. Любое «цель» — гипотеза, пока не измерено: публично заявляется только измеренное с `n` и датой (REQ-178). О Budget Guru известны лишь заявления лендинга, политики и условий: вход в приложение не выполнялся, функции не проверялись, аккаунтов нет ([разбор](../tools/budget-guru.md)).

## Принципы

1. **Метрика служит решению:** гейту релиза, критерию остановки или правке экрана; без решения метрика не заводится.
2. **Всегда с `n` и датой.** При `n < 20` доля подаётся как «в k из n» (REQ-055); публичная цифра старше 90 дней снимается (REQ-178).
3. **Считается на устройстве;** в v1 наружу не уходит ничего (REQ-185, REQ-120).
4. **Различаем три вида порогов:** гейт (условие релиза), критерий остановки (условие закрытия направления) и гипотеза (ориентир без последствий).
5. **Не оптимизируем «приятные» числа** (раздел «Метрики-ловушки»). Метрики считаются вне движка: движок не читает часы ([ADR-003](../decisions/adr-003-civil-dates.md)).

## Северная звезда

[Видение](00-vision.md) задаёт её словами: «честный прогноз, к которому возвращаются» — вердикту можно доверять, и привычка ввода жива. Операционная формула — **предложение этой страницы** (не из канона):

```pseudo
honest_week(ws, w) = anchor_age(ws, конец w) ≤ stale.banner_days      # 7: плашки «остаток не сверялся» нет
                     и readiness(ws, конец w) ≥ ready.q1              # 3: прогноз показывался
                     и «Обзор» или Q3 открыт хотя бы раз в w
ns = round_div(10000 · #{ws: Σ_{w ∈ последние 4 недели} honest_week(ws, w) ≥ 3},
               #{ws: прошёл онбординг и старше 28 дней})              # bp
публикуется только пока гейт доверия пройден (frr, cry_wolf) и не старше 90 дней
```

Порог «3 из 4 недель» — гипотеза; целевого значения до первой когорты нет. Свежесть входит в определение: открытое приложение со старым остатком — не «честная неделя».

## Формулы

**Активация** (REQ-110, [IDEA-31](../ideas/proposal-product.md)):

```pseudo
t_first_forecast(ws) = t(первое readiness ≥ ready.q1) − t(created)       # секунды; публикуется медиана с n и датой
onboarded(ws)        = readiness_max(ws) ≥ ready.q1                       # «прошёл онбординг»: s ≥ 3 (C-066)
activated(ws)        = показан первый вердикт Q3 (kind = ok, s = 4)       # C-066: готовность s ≥ 3 без вердикта — слишком мягко
activation_7d(ws)    = onboarded и activated в первые 7 дней после created
activation_rate      = round_div(10000 · #{ws: activation_7d}, #{ws: created})
```

**Ошибка прогноза и доверие** (окна не пересекаются: `origins = t0 + j·h`, соседние дни зависимы; исход «пробой буфера» и окно `H` фиксирует REQ-176 (C-055): для покупки `e` на момент `t` — `min` фактического `free` на `[e.date, e.date + H] < B(t)`, `H = backtest.h_days = 30` (гипотеза); пробы — реальные расходы без `is_obligation` и `is_estimate` с `|amount| ≥ θ`):

```pseudo
min_error_bp = round_div(10000 · (min_fact − min_pred), abs(min_pred))   # REQ-185, C-055: режим plan, физический trough, окно backtest.min_window_days = 14; min_pred ≠ 0; «−»: факт ниже прогноза
mae_minor    = round_div(Σ |F_t − A_t|, n)                               # F_t = plan.close на t+h, A_t — факт
bias_minor   = round_div(Σ (F_t − A_t), n)
skill_pm     = 1000 − floor_div(1000 · Σ |F_t − A_t|, Σ |N0_t − A_t|)    # N0_t — наивно: баланс не меняется
coverage     = { k: #{t: min(F_t, W_t) ≤ A_t ≤ max(F_t, W_t)}, n }       # W_t = worse.close; в v2 коридор P10–P90
frr          = round_div(10000 · k_ok, n_ok)    # k_ok: вердикты OK с последующим пробоем буфера
cry_wolf     = round_div(10000 · k_al, n_al)    # k_al: вердикты FRAGILE/NO без пробоя
gate         = len(журналов) ≥ 10 и ΣN1 > 0 и ΣN2 > 0 и 10000·ΣK1 ≤ 500·ΣN1 и 10000·ΣK2 ≤ 5000·ΣN2   # по сумме счётчиков (C-055)
```

| Величина | Вход | Результат |
|---|---|---|
| `min_error_bp` | прогноз 120000 (1 200,00 €), факт 109000 | −917 bp (−9,2 %) |
| MAE, bias, skill (ALG-13, TV-6; учебные окна `h = 7`, не G-001) | `F = [340000, 300000, 280000, 250000]`, `A = [335000, 310000, 280000, 241000]` | 6000 (60,00 €), 1000 (10,00 €), 845 ‰; покрытие «в 3 из 4» |
| `frr` (REQ-176) | 200 вердиктов «выдерживает», 9 с пробоем | 450 bp (4,5 %): проходит |
| `cry_wolf` (REQ-176) | 120 «хрупко» и «не хватает», 66 без пробоя | 5500 bp (55 %): не проходит |

Четыре замечания к арифметике:

- **Синтетика.** На 22 синтетических журналах прототипа (12 «обычных», 10 «стресс») гейт отрабатывает в обе стороны: у «обычных» `frr` 85 bp (1 из 117) и `cry_wolf` 3889 bp (7 из 18) укладываются в пороги 500 и 5000 bp, у «стресс» `frr` 2188 bp (7 из 32) — нет. Это проверка механики гейта, а не качества прогноза на реальных людях; значения порогов остаются гипотезами.
- **Малый `n`.** При `n_ok < 20` гейт допускает только 0 пробоев: 1 из 19 — 5,26 % (`10000 > 500·19`), 1 из 20 — ровно 5,00 % и проходит. Число вердиктов на журнал не оценено.
- **Гейт — минимальная проверка, не доказательство.** Для 9 из 200 интервал Уилсона — 2,4–8,3 % (ALG-13, TV-4); при `n ≥ 20` публикуются доля и интервал, при меньшем — «в k из n».
- **Покрытие в v1.** Коридор `plan`–`worse` детерминирован и вероятностной интерпретации не имеет, поэтому цель «80 ± 10 п.п.» из предложения (IDEA-54) к нему не относится; в v1 публикуется «k из n» без цели (вывод). Пример G-001 (ALG-13): вердикт «хрупко» по дорожке 300,00 € — тревога зря, если выплата пришла вовремя (минимум 635,00 € ≥ 500,00 €), и не зря при задержке на 14 дней (410,00 € < 500,00 €).

**Удержание.** Главный риск продукта — усталость ввода (RISK-01), поэтому «активен» означает ввод, а не открытие:

```pseudo
active(ws, d)        = в окне [d − 6, d] есть ввод пользователя (записи журнала с actor = user): факт, якорь, подтверждение или пропуск плана, правка плана   # C-066; для d = created + 28 это дни 22…28
d7                   = round_div(10000 · #{ws: active(ws, created + 7)}, #{ws: onboarded})
d28                  = round_div(10000 · #{ws: active(ws, created + 28)}, #{ws: onboarded})     # остановка: d28 < 2500
active_weeks_28d(ws) = #{w ∈ последние 4 недели: active(ws, конец w)}
anchor_stale_share   = round_div(10000 · #{ws: anchor_age > 14}, #{ws: onboarded})
backup_gap_share     = round_div(10000 · #{ws: старше 30 дней и без копии}, #{ws: старше 30 дней})
```

**Наблюдаемые индикаторы ввода:** медиана записей в неделю (ниже 3 — ранний признак усталости, красная команда), `entry_time_median_s` (ввод факта, REQ-090), доля автосопоставлений `auto_match_bp = round_div(10000 · auto, auto + queue)` — низкая доля говорит, что параметры `match.window_days = 3` и `match.tol_bp = 500` (гипотезы) не подходят пользователю; для волн — доля волн из одного платежа и чувствительность к `gap_days ± 1`, `max_span_days ± 3` (REQ-188).

**Качество системы** измеряется в CI и тестовой лаборатории, а не на устройствах пользователей:

| Метрика | Порог | Источник |
|---|---|---|
| golden G-001, G-001-low, G-001-gap | 100 % ключей совпадает; расхождение блокирует релиз | REQ-170 |
| property-инварианты | 9 инвариантов × не менее 10^3 журналов | REQ-171 |
| `arith.lock` | 0 отличий без коммита «ARITH-CHANGE» и повышения `engine_version` | REQ-172 |
| фаззинг | 0 необработанных исключений на 10^5 журналов | REQ-158, 174 |
| шаблоны `A0` | все проходят верификатор чисел на evidence G-001 | REQ-130 |
| пересчёт, холодный старт, Q3, ввод факта | p95 ≤ 100 мс; ≤ 2 с; ≤ 1 с на 24 мес.; медиана ≤ 5 с — цели до замера | REQ-150, 152, 105, 090 |

**Факт прототипа на 2026-10-27.** Пороги таблицы — цели v1; прототип выполняет их так (подробнее по каждому TST — [стратегия тестирования](11-testing-strategy.md)):

- golden G-001, -low, -gap, -late — зелёные; property — девять инвариантов TST-31…39 на 1000 журналах общего генератора (FP-24);
- замок арифметики — 574 случая `money`; замок вывода движка — `analyze` на 500 журналах (`tests/engine.lock.json`), правка расчёта без повышения версии движка красит тест (REQ-172);
- фаззинг — полный запуск на 10⁵ входов и 1 500 областей без необработанных исключений (2026-10-28; повтор 2026-11-09 на текущем коде, `_ops/fuzz-nightly.json`);
- шаблоны `A0` проходят верификатор на evidence G-001 (TST-45);
- p95 пересчёта: `analyze` на 1084 событиях и горизонте 180 дней — p50 10,57 мс, p95 17,34 мс в Node на одной машине (бюджет-гипотеза ≤ 100 мс; `_ops/bench.json`, 2026-10-09); журнал на 36 500 записей открывается за 116 мс со снимком (цель ≤ 2 с). На устройствах и в браузере замеров нет: страницы `bench.html`, `coldstart.html`, `compat.html` готовы, но не запускались; публикуемых p95 и холодного старта нет.

Из метрик этой страницы в коде есть расчётные: `backtest.mjs` — `mae_minor`, `bias_minor`, `skill_pm`, `coverage`, `frr`, `cry_wolf`, ошибка минимума и `release_gate` (на синтетических журналах); `timeline.mjs` и `calibration.mjs` — `anchor_age`, уровень свежести, готовность данных. **Локальные счётчики и файл `runway-metrics/1` реализованы** (волна 2, FP-10): экран «Метрики на устройстве» (`prototype/demo/metrics_view.mjs`), логика и схема (`prototype/demo/metrics.mjs`), формат — [`prototype/SPEC-format.md`](../../prototype/SPEC-format.md), раздел 3. Спрос v0 и D28 прототип измерить не может: у него нет пользователей, а на странице-калькуляторе `prototype/demo/v0.html` счётчиков нет.

## Измерение без слежки

| Источник | Что | Где живёт | Чего нет |
|---|---|---|---|
| Локальные счётчики (v1) | `created`, `readiness_max`, `t_first_forecast`, дни активности в относительном счёте, `anchor_age`, `q3_opened`, `auto/queue`, возраст копии | отдельное хранилище на устройстве, не в журнале; экран `metrics` показывает значения и `n`; удаляется вместе с данными (`eraseAll`, вывод) | сумм, календарных дат, описаний, получателей, идентификатора устройства или человека |
| Журналы добровольцев (гейт REQ-176) | не менее 10 журналов для backtest | пользователь передаёт сам; даты сдвинуты на число дней, кратное 7, суммы умножены на общий k ∈ [0,5; 2] | автоматической отправки |
| Файл-пакет метрик (принят, C-066; реализован в прототипе, состав — ниже) | агрегаты: значения таблицы выше в корзинах | приложение готовит файл `runway-metrics/1`, показывает целиком; пользователь отправляет сам, добровольно | любого фонового запроса, сумм |
| Интервью и опросы | 8–10 интервью (REQ-189); 30 приглашённых в v0; локальный вопрос раз в 30 дней «доверяете прогнозу?» | вне продукта / на устройстве | — |

Пример пакета (формат принят решением C-066; значения иллюстративны):

```json
{ "format": "runway-metrics/1", "age_days": 28, "readiness_max": 4, "activated": true,
  "t_first_forecast_bucket": "10-20 min", "active_weeks_28d": 3,
  "anchor_age_days": 6, "backup_age_days": 12, "q3_opened": true, "auto_match_bp": 8300 }
```

**Состав `runway-metrics/1` в прототипе.** Пример выше — предложение вики (C-066) с корзинами и производными; реализованный формат строже и проще (`prototype/demo/metrics.mjs → validate_package`, любое лишнее поле отвергается): `format`, `engine_version`, `sessions` (число сеансов), `active_days` (дни использования как смещения от первого дня, не календарные даты), `steps` (журнал шагов мастера «Старт»: шаг, активные секунды, номер сеанса, исход `saved` или `skipped`), `first_forecast` (секунды до первого прогноза и номер сеанса или `null`), `verdict_ready` (номер сеанса, когда гейт Q3 пройден, или `null`), `counters` (закрытый список из восьми счётчиков действий: `accounts_saved`, `anchors_set`, `rules_saved`, `facts_added`, `scenarios_saved`, `imports_done`, `undo_used`, `wizard_opened`), `min_error_bp` (число окон и до ста значений ошибки минимума в bp) и `coverage` (`k` из `n`). В тексте файла нет сумм, календарных дат, названий и идентификаторов, чисел длиннее девяти знаков. Какой из двух форматов считать каноном — вики или реализованный — и что раздавать приглашённым (приложение или `v0.html` с добавленными счётчиками), решает владелец (пакет FP-32 дорожки 3б); до решения расчёт `d7`, `d28`, активации и `t_first_forecast` по корзинам не делается.

Правила: нет сторонней аналитики и скриптов (`connect-src 'self'`, REQ-121, 123); нет идентификаторов и календарных дат; значения грубые (корзины); выборка бета-пользователей и добровольцев смещена, и это оговаривается рядом с цифрой. Для сравнения: политика Budget Guru называет Vercel Web Analytics, «по умолчанию» без cookies (заявлено; приложение не проверялось). Как считать критерии, требующие данных когорты, если приложение ничего не отправляет (v0 и D28), решено (C-066): добровольный файл-пакет `runway-metrics/1` и опрос приглашённых; сетевых счётчиков в v1 нет.

## Цели и обоснования

| Метрика | Цель | Статус | Обоснование | Если не достигнута |
|---|---|---|---|---|
| `frr` | ≤ 5 % на ≥ 10 журналах | гейт (REQ-176) | «выдерживает», затем минус — самая дорогая ошибка; симметричные MAE и покрытие её не видят | заморозить новые функции; не лечится за 4 недели — остановить |
| `cry_wolf` | ≤ 50 % | гейт (REQ-176) | частые тревоги обесценивают вердикт; 55 % в примере — буфер велик или режим перестрахован | пересмотреть буфер и сдвиг `worse` (14 дн. — гипотеза) |
| Спрос v0 | ≥ 10 из 30 вводят свои числа и ≥ 5 возвращаются через 7 дней | остановка (REQ-180) | без сигнала спроса v1 строится на догадках | v1 не строить |
| `d28` | ≥ 25 % | остановка (REQ-181) | порог красной команды; внешнего бенчмарка нет (не подтверждено); ввод — главный риск | пересмотреть ввод; два цикла без улучшения — остановить |
| `activation_rate` | ≥ 40 % (`activated` среди `onboarded`) | гипотеза | выбрано без данных; определение — C-066 | уточнить порог по первой когорте |
| `t_first_forecast` | медиана ≤ 10 мин | гипотеза, не публикуется (REQ-110) | бюджет проектирования 7,5 мин; красная команда допускает «30+» | измерить на ≥ 5 пользователях; публиковать «N мин (n, дата)» |
| `abs(min_error_bp)` | ≤ 1000 bp | гипотеза | допуск 10 %; −917 bp укладывается | наблюдать; правки буфера и режимов — при `n ≥ 20` окон |
| `coverage` | v1: цели нет | наблюдаем | коридор детерминирован | — |
| `anchor_stale_share`, `backup_gap_share` | цели нет | наблюдаем | индикаторы RISK-01 и RISK-05; порог 14 дней отличен от плашки (7) и блока (21) | уточнить текст плашки и напоминания о копии |
| Верификатор «с первого раза» | ≥ 9500 bp | v2, гипотеза | только для `A1`–`A3`; в `A0` ответ — шаблон | усилить шаблоны |

## Метрики-ловушки

| Не меряем как цель | Почему | Вместо |
|---|---|---|
| Доля вердиктов «выдерживает» | подталкивает к мягким порогам | `frr` и `cry_wolf` вместе |
| Время в приложении, число открытий | «один экран — один вопрос» должен быть коротким; открытие не равно доверию | `honest_week`, учитывающая свежесть |
| Число «одобренных» покупок | продукт не советует покупать | не считаем |
| Серии дней, уведомления для возврата | давление на человека в тревоге (RISK-12); бюджет внимания — REQ-115 | `active_weeks_28d` без наград |
| Средняя ошибка без `n` | ложная точность | «ошибка в среднем X за N окон» |

## Расписание проверок

| Когда | Что | Решение при провале |
|---|---|---|
| v0, около 10 рабочих дней | спрос: 10 из 30 и 5 из 30 | v1 не строить |
| неделя 12 / неделя 16 | Q1+Q3 на реальных данных автора / бета | срез вдвое / остановка |
| до беты | backtest ≥ 10 журналов, калибровка волн (REQ-188), юридическое ревью (REQ-183) | заморозка функций / удаление налоговой части |
| после беты | `d28`, два цикла | пересмотр ввода / остановка |
| каждые 90 дней | рынок (REQ-190); срок давности публичных цифр (REQ-178) | пересмотр позиционирования / снятие цифры |

Каждое срабатывание фиксируется записью `decision` (REQ-181).
