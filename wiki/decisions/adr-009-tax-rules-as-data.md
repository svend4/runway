# Решение: налоговые правила как данные

## ADR-009 Налоговые правила как версионируемые данные

### Контекст

Принцип статьи: налоги — «виртуальный конверт», который считается в момент поступления дохода (пример: пришло 3 000 €, условные 20 % уходят в конверт) ([статья](../../raw/01-tj-salkov-article.md)). Страна и режим автором не названы; аббревиатуры IVA/IRPF намекают на Испанию (вывод). Среди изученных инструментов налоговый конверт полноценно есть только у налоговых сервисов: Found (Taxes Pocket) и метод Profit First откладывают процент от поступлений, но связи с прогнозом остатка нет; Hurdlr и QuickBooks оценивают налог, а платёж не попадает в общий график ([налоги фрилансеров](../tools/freelancer-tax-tools.md)); у [PocketSmith](../tools/pocketsmith.md) — ручной перевод процента на отдельный счёт; у [Actual Budget](../tools/actual-budget.md) — шаблон «процент от дохода». Лендинг Budget Guru заявляет «налоговые правила по датам» без модели ([разбор](../tools/budget-guru.md)). Предложения проекта описывали режимы `CUM_PROFIT_ADVANCE` и `VAT_NET` и шаблон «Autónomo (ES)» с окнами подачи из коммерческого сервиса, а не регулятора. Красная команда сочла это нарушением принципа «правила — данные»: в продукт зашита логика, срок годности которой неизвестен, а ошибка станет «налоговым советом».

### Решение

1. **Правило — данные пользователя**: `TaxRule{ tax_rule_id, version, kind, rate_bp, base, applies_to, valid_from, valid_to?, rounding, reserve_id, reviewed_at?, ttl_days?, recorded_at }`. Ставок, лимитов, налоговых календарей и шаблонов стран по умолчанию в продукте нет.
2. **v1: единственный вид — `percent_of_income`.** При поступлении, подпадающем под `applies_to`, создаётся виртуальная аллокация `mul_div(gross, rate_bp, 10000, rule.rounding)` в резерв ([ADR-016](adr-016-reserves-and-safe-to-spend.md)); баланс счёта не меняется. Налоговые платежи — обычные плановые обязательства «на дату X сумма Y», которые вводит пользователь и которые высвобождают резерв; они попадают в волны и в прогноз.
3. **Версии и время**: выбирается версия с `valid_from ≤ d < valid_to` (при нескольких — с наибольшим `recorded_at`); аллокация хранит `rule_version`, поэтому смена ставки прошлое не переписывает; новая ставка — предпросмотр правки правила без записи (поправка v1.1, C-073). Запрос `known_at` («что мы знали тогда») — v2.
4. **Срок годности**: `reviewed_at` и `ttl_days` хранятся; интерфейс показывает возраст правила рядом с каждым зависящим числом (`fresh` → `stale` → `disabled`).
5. **Именованные режимы** (накопительный аванс от прибыли с начала года, чистый НДС-подобный сбор) — v2 и только как данные со схемой параметров и проверкой, а не как зашитые функции.
6. Любое число про налоги сопровождается оговоркой «расчёт по введённым правилам, не консультация»; ассистент не называет ставок.

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не он |
|---|---|---|---|
| Зашитые правила стран | готово из коробки | устаревают, ответственность за совет | нарушает «правила — данные» |
| Шаблоны стран с TTL | быстрый старт | источник окон — коммерческий сервис, поддержка | v2, с проверкой специалистом |
| Плагины-скрипты на страну | гибко | исполняемый чужой код | риск безопасности |
| Только постоянный процент (как Found, Profit First) | просто | не отражает версии и платежи | недостаточно для Q2 |
| Внешний API ставок | актуальность | сеть, доверие к источнику | противоречит local-first |
| Версионируемый процент + пользовательские платежи | честно, проверяемо | пользователь вводит правила сам | **выбрано** |

### Последствия

- В примере G-001 пришедшие 2 790,00 € дают аллокацию 558,00 € (2000 bp); платёж 500,00 € 23 октября высвобождает резерв, а `true_up` — разницу, если резерва не хватило ([ALG-06](../algorithms/alg-06-tax-envelope.md)).
- Шаблон-подсказка для пользователя содержит пустые поля; пример с конкретной страной — только как иллюстрация в документации с оговоркой.
- Юридическое ревью формулировок обязательно до публичной беты; если оно признает налоговую часть консультацией — она удаляется ([ADR-015](adr-015-v1-slice.md)).
- Изменение правил — запись журнала со ссылкой на версию ([ADR-004](adr-004-event-journal-projections.md)).

## Поправка v1.1

- C-073: вместо «сценария а что если 22 %» в v1 — **предпросмотр правки правила без записи** (эфемерная правка рабочей области в памяти, REQ-108); новой операции сценария для ставки нет.
- C-023: срок годности — одна формула: `age = today − reviewed_at`; `fresh` при `age ≤ ttl`, `stale` при `ttl < age ≤ 2·ttl`, `disabled` при `age > 2·ttl`; без `reviewed_at`/`ttl_days` — `fresh` с пометкой «проверка не отмечена».
- C-024: при `disabled` расчёт `free` продолжается (резерв остаётся), в `Result.warnings` — `W_RULE_DISABLED`; зависящие числа интерфейс заменяет текстом «правило не подтверждено с <даты>: подтвердите или измените», Q3 и «можно потратить» не отвечают через общий гейт; Q1 и волны не затронуты.
- C-016: версия правила для `planned`-дохода выбирается по `base(e) = max(plan_date, as_of)` — дате, не зависящей от режима; для `posted` — по фактической дате.
- C-032: правило с пустым `applies_to` — ошибка; сумма `rate_bp` правил на одно поступление не больше 10000 (иначе `E_RULE_INVALID`); `rate_bp ∈ 0..10000`.
