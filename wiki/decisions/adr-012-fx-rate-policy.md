# Решение: политика курсов и валюта решения

## ADR-012 Политика курсов и валюта решения

### Контекст

Целевой пользователь живёт в EUR, получает USD и иногда крипту; будущий USD-доход на EUR-счёт — самая волатильная часть прогноза. Продукты справляются разно: Actual «currency agnostic» и мультивалютность не поддерживает; YNAB ведёт отдельный план на валюту ([Actual](../tools/actual-budget.md), [YNAB](../tools/ynab.md)); Monarch, Copilot и Simplifi показывают «$» для всего, Lunch Money держит дневные курсы ([SaaS-трекеры](../tools/modern-saas-trackers.md)); PocketSmith пересчитывает бюджеты по текущему курсу ([PocketSmith](../tools/pocketsmith.md)); hledger — лучшая модель (цена операции `@`/`@@`, база цен `P`, оценка `-V`/`-X`), но без прогноза ([plain-text](../tools/plain-text-accounting.md)); Firefly III хранит иностранную сумму рядом с основной ([Firefly III](../tools/firefly-iii.md)). Лендинг Budget Guru заявляет «фактический курс каждой операции» (не проверено). Красная команда указала на дыру проекта: минимум — скаляр, а остатки — вектор EUR/USD/RUB; без «валюты решения» вердикт Q3 не определён.

### Решение

1. **Хранение**: сумма всегда в валюте счёта; обмен — два события-ноги с общим `transfer_id` и **выведенным** курсом `leg_b/leg_a` как рациональное число; курс не вводится, а наблюдается.
2. **Курс** — `FxRate{base, quote, num, den}`: `1 основная единица base = num/den единиц quote`; конверсия минорных сумм с разными экспонентами: `round_div(a · num · 10^quote_exp, den · 10^base_exp, mode)` на BigInt. Источник курсов — ручной ввод; сетевых запросов в движке нет; пакеты курсов — позже.
3. **Валюта решения** `decision_currency` — настройка рабочей области (по умолчанию валюта первого операционного счёта); `trough`, `free`, волны, вердикты и `STS` считаются в ней. События в других валютах переводятся политикой `spot` — последним введённым курсом пары с датой не позже `as_of` для всех будущих событий; каждая пересчитанная сумма в интерфейсе подписана курсом и датой.
4. **Сценарий курса** `fx_shock{currency, bp}` (например, −500 bp) — v1.1; политика `adverse` (доходы × (1 − h), расходы × (1 + h), `h` из истории) и вектор остатков по валютам — v2.
5. **Крипта**: счёт `kind = crypto`, экспонента 8 (BTC в сатоши), в `operating` не входит; в запас идёт только `liquidity_bp / 10000` оценки; значение по умолчанию — 0, никаких haircut-процентов от продукта.
6. Платёж в чужой валюте — событие в валюте счёта, в ряд решения попадает по курсу `spot`. Обмен между собственными операционными счетами в агрегат решения не входит (обе ноги исключены), остатки счетов оцениваются по `spot`; разница между выведенным курсом обмена и `spot` — «курсовая разница обмена» — показывается справочно и в `trough` не входит.

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не он |
|---|---|---|---|
| Одна базовая валюта для всего | просто | теряет реальную экспозицию, перерасчёт прошлого | не годится для EUR+USD |
| Вектор остатков по валютам без вердикта | честно | минимум — вектор, ответ «можно/нельзя» не определён | вердикт нужен скаляром |
| Курс на дату каждой будущей операции | точнее для прошлого | будущих курсов нет | используем `spot` и сценарий |
| Haircut крипты 30 % по умолчанию | осторожно | значение придумано продуктом, воспринимается как совет | параметр пользователя, по умолчанию 0 |
| Автоматическая подгрузка курсов | удобно | сеть и доверие к источнику, нарушает local-first | ручной ввод плюс пакеты позже |
| Валюта решения + `spot` + выведенный курс | определённость, воспроизводимость | курс — допущение пользователя | **выбрано** |

### Последствия

- Все умножения на курс идут через `mul_div`: в 10¹² минорных единиц × 10¹⁰ делителя без BigInt точность теряется ([ADR-002](adr-002-money-minor-units.md)).
- Пример: 2 000,00 $ при 0,9250 → 1 850,00 €; при −5 % → 1 757,50 € (−92,50 €); обмен 2 000,00 $ на 1 842,40 € даёт курс 0,9212; 0,0015 BTC при 50 000,00 €/BTC — 75,00 € ([ALG-08](../algorithms/alg-08-fx-conversion.md)).
- Подпись курса и даты в каждом пересчитанном числе — условие честности вердикта; курс не подаётся как совет.
- Риск неоднозначности вердикта в мультивалюте отражён в реестре рисков (RISK-15, [риски](../product/12-risks.md)).
- Тесты: TST-27, TST-28.

## Поправка v1.1

- C-034: сигнатуры — `to_decision_events(events, accounts, rates, decision_currency, policy, as_of)`, `to_decision(amount_minor, currency, as_of, ctx)`, `opening_in_decision(accounts, balances, ctx, as_of)`, `implied_rate(leg_a, leg_b, base_exp, quote_exp)`.
- C-036: `rate_at` допускает обратную пару (дробь переворачивается, подпись «обратный»; при равной дате прямой курс приоритетнее); триангуляции в v1 нет — `E_NO_RATE`.
- C-037: курс, введённый пользователем, хранится как введён (`9250/10000`); производные курсы (`implied_rate`, `apply_shock`) — несократимая дробь (`gcd`).
- C-038: курс для аллокации и резерва: `planned` — `spot` на `as_of`, `posted` — курс на дату дохода в момент записи `allocation.recorded`; дальше резерв не переоценивается; при сопоставлении план → факт аллокация пересчитывается от фактической суммы. Решение помечено для владельца: заморозка накапливает разницу между резервом и обязательством в валюте платежа; переоценка — v2.
- C-096: `fx.stale_days` = 30 (гипотеза) — параметр §2.0; плашка свежести курса, расчёт не блокируется.
