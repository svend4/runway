# Решение: неопределённость, сценарии и Монте-Карло

## ADR-008 Неопределённость: сценарии в v1, seeded Монте-Карло в v2

### Контекст

Главный источник кассового разрыва у почасовика — задержка выплаты и колебание курса; статья неопределённость не описывает ([статья](../../raw/01-tj-salkov-article.md)). У личных продуктов интервалов нет: у PocketSmith — дельта-сценарии без авто-итога ([PocketSmith](../tools/pocketsmith.md)); у Float — скалярный Forecast Confidence, границы которого не опубликованы ([бизнес-инструменты](../tools/business-cashflow-tools.md)); сторонний DzenAnalytics строит коридор оптимист/реалист/пессимист, но без вероятностей ([Дзен-мани](../tools/zenmoney-coinkeeper.md)); Monte Carlo в [Actual Budget](../tools/actual-budget.md) — про пенсионные накопления, не про даты платежей. Предложение по движку описало детерминированный Монте-Карло с общими случайными числами и вероятностный Q3, но красная команда указала на ложную точность: «12,5 % ± 0,7 п.п.» — ошибка симуляции, а не модели, потому что вероятность выведена из восьми лагов (один из восьми; интервал Уилсона 2,2–47,1 %); `p90` при `n ≤ 9` — просто максимум; `λ = n/(n+3)` и prior 7 дней взяты с потолка.

### Решение

1. **v1 — детерминированно.** Неопределённость выражается режимом `worse` (все ожидаемые поступления позже на заданное число дней) и сценариями-правками данных («платёж клиента на 21 день позже», «курс −5 %» в v1.1). Вероятностей, процентов риска и слов-порогов в интерфейсе нет.
2. **v2 — seeded Монте-Карло** как надстройка над тем же движком (те же события с возмущениями): `seed = H(engine_version, inputs_hash, user_seed)`; случайные числа не потоком, а функцией `u = hash(seed, ключ события, номер пути)` (счётчиковый хэш), поэтому правка одного события не перемешивает остальные, а сценарии сравниваются на общих путях (CRN).
3. **Распределения — из данных пользователя**: лаг клиента — бутстрап его наблюдений, без истории — широкий prior с пометкой «оценка»; часы — треугольное по `min/exp/max`; курс — бутстрап исторических приращений в `bp`. Допускаются только операции, точные в IEEE 754 (`+ − × ÷`, `sqrt`); `exp`, `log`, тригонометрия не используются, чтобы результат не зависел от движка JavaScript.
4. **Честные малые выборки**: любая вероятность или квантиль показывается с `n`; при `n < 20` — только счёт «в k из n прошлых случаев»; при `n ≥ 20` — интервал Уилсона; квантиль при `ceil(q·n) = n` подписывается «наибольшее из n».
5. **Вероятность разрыва** — доля путей с минимумом `trough < 0`, не максимум дневных вероятностей; допуск риска `α` берётся по квантилю *минимумов путей*, а не минимуму квантилей.
6. **Качество измеряется асимметрично**: доля вердиктов `OK` с последующим пробоем буфера (FRR) и доля тревог без пробоя (cry-wolf) на журналах добровольцев — гейт релиза ([ADR-014](adr-014-testing-approach.md)).

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не он |
|---|---|---|---|
| Только точечный прогноз | просто | ложная уверенность | расходится с задачей Q1 для почасовика |
| Один пессимистичный сценарий | понятен | единственная гипотеза | это и есть режим `worse`, но дополняется чипами |
| Монте-Карло с первого релиза | диапазоны, `p_gap` | малые выборки, ложная точность, нет данных | v2 и только с оговорками |
| Аналитические формулы (нормальное приближение) | быстро | распределения лагов тяжелохвостые | не соответствуют данным |
| Скалярный «индекс доверия» (как у Float) | лаконично | формула закрыта | нужна открытая формула |

### Последствия

- Прототип реализует `montecarlo.mjs` и `calibration.mjs` (в том числе интервал Уилсона и nearest-rank), продукт v1 их не включает ([ADR-015](adr-015-v1-slice.md)).
- Пример на сквозном примере: восемь лагов `[0, 3, 7, 5, 14, 6, 2, 9]`; покупка 300,00 € нарушает буфер в двух случаях (лаги 9 и 14) — «в 2 из 8 случаев»; интервал Уилсона 7,1–59,1 % не показывается при `n < 20` ([ALG-10](../algorithms/alg-10-uncertainty-monte-carlo.md)).
- Калибровка лагов и backtest «как знали тогда» требуют истории не меньше 2–3 месяцев; до того метрики скрыты ([ALG-13](../algorithms/alg-13-plan-vs-actual-calibration.md)).
- Подача: ответ + одна причина; красный только при детерминированном разрыве в `worse` ([ALG-10](../algorithms/alg-10-uncertainty-monte-carlo.md)).

## Поправка v1.1

- C-057: красный цвет — только детерминированный разрыв `trough < 0` в режиме `worse`; условие «`p_fail ≥ 20 %`» отвергнуто, слова-пороги вероятностей — гипотеза v2 при `n_eff ≥ 20`.
- C-009: сценарий «платёж клиента на N дней позже» правит данные, затем режим добавляет свой сдвиг (накопление); в `plan` задержка на 14 дней даёт ряд `worse`.
- C-061: обозначения — `n_paths` (число путей), `n` (число наблюдений), `N` (число дней сетки); `n_eff = min n_obs` по источникам на данных, для одного источника с ≤ 64 наблюдениями — полный перебор (C-048).
- C-049: подпись «наименьшее из n» для P10 при `ceil(q·n/100) = 1` и `q < 50`; границы Уилсона в ‰ округляются к ближайшему.
- C-068: цель покрытия коридора «80 ± 10 п.п.» относится к v2; в v1 коридор `plan`–`worse` детерминирован, метрика покрытия — «k из n» без цели.
