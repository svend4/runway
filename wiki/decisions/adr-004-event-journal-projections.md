# Решение: журнал событий и проекции

## ADR-004 Журнал событий и проекции

### Контекст

Изменяемые записи («обновить сумму») теряют историю: нет отмены, нельзя воспроизвести «что мы знали месяц назад», нельзя доказать, откуда взялось число. Модель данных Budget Guru не раскрыта ([страница](../tools/budget-guru.md)). У PocketSmith сопоставление события и транзакции при сдвиге даты приводит к двойному учёту, потому что слои факта и плана не разделены ([PocketSmith](../tools/pocketsmith.md)). hledger — журнал append-only с balance assertions, но без слоёв, версий правил и журнала действий ассистента ([plain-text](../tools/plain-text-accounting.md)). Дзен-мани синхронизирует diff с надгробиями, а побеждает «более новая версия» ([Дзен-мани](../tools/zenmoney-coinkeeper.md)); экспорт Firefly III нельзя импортировать обратно ([Firefly III](../tools/firefly-iii.md)). Нужны также воспроизводимость (golden-тесты, backtest) и будущая синхронизация без пересчёта чужих данных.

### Решение

1. **Журнал** — append-only последовательность `LedgerEvent` (`event_id` uuidv7, `type`, `v`, `entity_id`, `payload` из целых и ISO-дат, `recorded_at`, `actor`). Сущности (счета, правила, потоки, резервы, курсы, сценарии) — **проекции**, вычисляемые сверткой журнала; снимок каждые ~500 записей, свертка снимка с хвостом равна свертке всего журнала.
2. **Слои** временной шкалы: `posted` (факт, неизменяем), `planned` (вхождения правил — виртуальные, не хранятся), `hypothetical` (принадлежат сценарию). Факт и план не смешиваются; сопоставление — отдельный шаг ([ALG-13](../algorithms/alg-13-plan-vs-actual-calibration.md)).
3. **Откат и правка**: `revert{target}` отменяет запись, откат отката возвращает её; правка — новая запись с `supersedes_id`. Эффективность записи: `effective(e) = not exists r ∈ reverts(e): effective(r)` и нет эффективной записи-замены `x` с `x.supersedes_id = e.event_id` (поправка v1.1, C-070); связи только на более ранние записи, циклов нет.
4. **Воспроизводимость**: `canon(x)` — детерминированный JSON (ключи по кодовым точкам, только safe-integer, строки NFC); `inputs_hash = sha256(canon({events окна, версии правил, params, as_of, engine_version}))`; `state_hash` для round-trip экспорта.
5. **Версии схемы**: запись несёт `v`; чтение пропускает её через чистые апкастеры `v → v+1`; на диске старое не меняется; неизвестная более новая версия — только чтение. Фикстуры настоящих экспортов каждой версии входят в тесты.
6. **Компакция** истории — только явным действием пользователя ([ADR-005](adr-005-local-first-optional-sync.md) для удаления); автоматической нет.
7. Время ввода (`recorded_at`) нужно для аудита и backtest, но не для расчёта ([ADR-003](adr-003-civil-dates.md)).

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не он |
|---|---|---|---|
| Изменяемая таблица с CRUD | просто, привычно | нет отмены и аудита, нет backtest | история — часть продукта |
| Журнал + CRDT-библиотека целиком | встроенное слияние | тяжёлая зависимость, рост истории (не проверялось) | нужна только объединяемая по `id` последовательность |
| Файловый журнал hledger как хранилище | независимость от формата | нет слоёв и версий, неудобно в браузере | hledger — экспорт и оракул, не хранилище ([ADR-011](adr-011-manual-entry-csv-hledger-import.md)) |
| SQL с триггерами аудита | запросы | схема меняется миграциями на месте, хэши нестабильны | журнал + проекции чище |
| Журнал append-only с проекциями | отмена, аудит, backtest, синхронизация | растёт, нужны снимки и апкастеры | **выбрано** |

### Последствия

- Рост: порядка 10 событий в день по 250 байт — около 0,9 МиБ в год (допущение из [предложения](../ideas/proposal-architecture.md)); снимки и явная компакция.
- Каждое число имеет происхождение: события-источники, версия правил, `inputs_hash` — основа «почему так» ([ALG-02](../algorithms/alg-02-timeline-projection.md)).
- Свойства для тестов: свертка снимка с хвостом, сохранение суммы, идемпотентность импорта, round-trip (TST-31…38).
- Изменение формата — апкастер и фикстура, а не миграция на месте; экспорт несёт `format: runway-journal/N`.
- Синхронизация в v2 — объединение множеств по `id` без переписывания ([ADR-005](adr-005-local-first-optional-sync.md)).

## Поправка v1.1

- C-070: тип `tx.voided` удалён (дублировал `revert`). Эффективность записи: `effective(e) = not reverted(e) and not exists effective x: x.supersedes_id = e.event_id`; откат записи-замены возвращает исходную.
- C-072: поле `seq` (монотонный номер записи в рабочей области) **обязательно в v1** — порядок записей с одинаковым `recorded_at`, порядок `WaveOverride`, `supersedes`; `hlc` и `device_id` — v2.
- C-071: `state_hash(state) = hex(sha256(canon(state)))`, где `state = reduce(effective_events(journal))` — свёртка, а не лог (`recorded_at` в неё не входит); `canon`: ключи по возрастанию кодовых точек, без пробелов, только safe-integer, строки NFC, порядок массивов задаёт производитель (множества сортируются).
- C-069: добавлены типы записей `plan.set`, `counterparty.set`, `profile.set`, `match.set` (ручная привязка факта к плану, факт не мутирует, C-051) и `debt.set` (v1.1).
