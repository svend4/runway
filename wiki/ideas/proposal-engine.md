# Предложение: движок — модель, алгоритмы, семантика прогноза

> Исторический документ (проектирование 2026-10-04): формулировки здесь — предложения, не канон; запрещённые обороты и числа Датасета R/«Elena» остались как иллюстрации. Канон — design-brief и ADR.

> Линза «ДВИЖОК»: детерминированное ядро Runway для Q1 «хватит ли к дате», Q2 «волна платежей», Q3 «могу ли купить». Налоговые числа — иллюстрации правил, введённых пользователем: расчёт по введённым правилам, не консультация. Это предложения, не решения; решения оформляются как ADR.

## Контекст и выводы исследования

- **Рынок тонкий** по осям Q3, «волны», «почасовой доход», AI (полной поддержки нет ни у кого); «налоговый конверт» полноценен лишь у налоговых сервисов ([матрица](../comparisons/feature-matrix.md)).
- **Budget Guru** — заявления лендинга: «кластеры» платежей, «сколько нужно к волне», вердикт «Да, спокойно». Пример в тексте (€300 → минимум €7 600) противоречит скриншоту (120 EUR); алгоритм, пороги и неопределённость не раскрыты ([страница](../tools/budget-guru.md), [досье](../../raw/02-budgetguru-landing.md)). Подтверждён лишь паттерн «движок → снимок цифр → LLM» ([политика](../../raw/03-budgetguru-privacy-terms.md)).
- **Статья** задаёт три вопроса и пять принципов (ручной ввод, лента «прошлое+будущее», амортизация редких трат, налоговый конверт, часы в прогнозе); неопределённость — задержка клиента, курс — не описана ([статья](../../raw/01-tj-salkov-article.md)).
- **PocketSmith** — ближайший аналог (дневной прогноз, дельта-сценарии), но без авто-минимума и «нужно к волне»; двойной учёт при сдвиге дат ([страница](../tools/pocketsmith.md)). **Actual Budget**: зрелые расписания (допуск ≈7,5 %, сдвиг выходных без праздников), Balance Forecast экспериментален ([страница](../tools/actual-budget.md)). **hledger**: `~`-правила и `--forecast` без метрик ([страница](../tools/plain-text-accounting.md)).
- **Float**: сценарии-слои, низшая точка, runway/buffer, непрозрачный Forecast Confidence ([страница](../tools/business-cashflow-tools.md)). **Firefly III**: прогноз исключён, но ценны статусы expected/matched/overdue и `amount_min/max` ([страница](../tools/firefly-iii.md)). **Налоговые сервисы**: резерв не связан с прогнозом ([страница](../tools/freelancer-tax-tools.md)).

### Датасет R — единый числовой пример

Все примеры посчитаны на одних данных: EUR, `as_of` = 2026-10-04 (воскресенье), горизонт до 2026-11-30; в тексте суммы в единицах, в псевдокоде — в minor units.

| Дата | Событие | Сумма |
|---|---|---|
| 10-04 | якорь остатка | 4 200,00 |
| каждая суббота (10-10 … 11-28) | продукты (estimate) | −210,00 |
| 10-15 | оплата счёта клиента А (planned) | +1 800,00 |
| 10-20 | налоги «130» 620,00 и «303» 410,00 (суммы введены пользователем) | −1 030,00 |
| 10-26 (25-е — воскресенье → следующий рабочий) | аренда 1 250,00 + ЖКХ 180,00 | −1 430,00 |
| 10-28 | страховка | −480,00 |
| 11-05 | почасовая выплата за октябрь (64 ч × 45,00) | +2 880,00 |
| 11-25 | аренда + ЖКХ | −1 430,00 |

Режимы: **plan/expected** — даты как введены (сдвиг на медиану лага клиента, 5 дн, минимум не меняет); **conservative** — оплата клиента А на 14 дн позже (10-29, p90 его лагов), внутри дня расходы раньше доходов. Минимум остатка: 2 220,00 (10-31) против 630,00 (10-28). Расходы 05.10–03.11 = 3 780,00 → `burn` = 126,00/день, буфер `B` = 7 дн = 882,00.

## Принципы

1. **Деньги — целые minor units, даты — календарные.** Сумма движений обязана точно равняться изменению остатка; «25-е» — гражданская дата, а не момент.
2. **Движок — чистая функция** от (журнал, правила, параметры, `as_of`, seed); `now()` и `random()` внутри запрещены — иначе нет воспроизводимости, golden-тестов и проверяемого AI.
3. **Факт неизменяем, план виртуален.** Правила порождают вхождения в памяти, гипотезы живут в сценарии; слои не смешиваются (иначе двойной учёт).
4. **Каждое число имеет происхождение (evidence):** события-источники, версия правил, `inputs_hash` — опора для «почему так» и для верификатора ответов ассистента.
5. **Один движок для факта, прогноза, сценариев и Монте-Карло:** вероятностный слой — те же события с возмущениями, а не отдельная модель.
6. **Консервативность в опасную сторону, но видимая:** расходы раньше доходов, задержка поступлений, неблагоприятный курс; параметры показаны и настраиваются.
7. **Правила — данные пользователя** (налоги, праздники, буфер, допуски); зашитых юрисдикций и ставок нет.
8. **Диапазон вместо точки, но точка остаётся:** детерминированная траектория объяснима, MC — надстройка, подаваемая без паники.

## Идеи

Конвейер движка (все стрелки — чистые функции):

```pseudo
журнал(posted, append-only) + правила(повтор, налоги, доход, резервы, долги; версии)
   → materialize(окно) → reconcile → слои{posted, planned, hypothetical}
   → project(режим) → {close[d], trough[d]} → анализы{Q1, волны, Q3, safe-to-spend}
   → Monte Carlo(seed) → {P10, P50, P90, p_gap} → evidence + explain
```

### IDEA-01 Три слоя событий: posted / planned / hypothetical

**Проблема.** Инструменты смешивают факт, план и «что если»: PocketSmith применяет бюджеты к прогнозу целой суммой, hledger стартует прогноз «после последней транзакции» (вывод: будущая запись сдвигает старт), Firefly материализует плановые операции в срок.
**Идея.** Одна таблица событий с полем `layer`: `posted` (факт, неизменяем, исправления — компенсирующей записью), `planned` (виртуальные вхождения правил и разовые планы), `hypothetical` (принадлежат сценарию, в журнал не попадают).
**Как работает.**

```pseudo
Event { id, layer, account, date, amount_minor(±), currency, kind, rule_id?, occ_key?,
        amount_min?, amount_max?, scenario_id?, recorded_at }
state(as_of)    = last_anchor(≤ as_of) + Σ posted после якоря
forecast(as_of) = state + Σ planned_residual + Σ hypothetical(scenario)
posted с date > as_of → ошибка валидации (или превращение в planned)
```

**Чем лучше.** [PocketSmith](../tools/pocketsmith.md) и [hledger](../tools/plain-text-accounting.md) слоёв не разделяют; у [Budget Guru](../tools/budget-guru.md) модель событий не раскрыта. Один агрегатор на все слои — паттерн Bluecoins ([трекеры](../tools/open-source-mobile-trackers.md)).
**Риски/цена.** Больше понятий: UI показывает два цвета («было/будет»), гипотезы — только в режиме «а что если».
**Приоритет** P0 · **Сложность** M · **Вопросы** Q1, Q2, Q3

### IDEA-02 Сопоставление план↔факт (reconciliation) с допуском

**Проблема.** При сдвиге даты или суммы факт и план считаются дважды; у PocketSmith кнопка «Fix this bill» появилась лишь в июне 2026.
**Идея.** Факт ищет не более одного плана в окне допуска; совпавший план перестаёт влиять на будущее, отклонение уходит в калибровку (IDEA-27).
**Как работает.**

```pseudo
match(F, P): тот же счёт, знак, валюта
  и -win_before ≤ F.date − P.date ≤ win_after            # по умолчанию 3 дня
  и |F.amt − P.amt| ≤ max(abs_tol, pct_tol·|P.amt|)      # по умолчанию 5 %
score = |ΔD|/win + |ΔA|/tol; жадно по возрастанию (tie: дата, id)
частичный факт: P.residual = P.amt − ΣF  (остаётся expected)
промах в пределах 2×допуск: P не снимается, пометка «возможный двойник»
```

Пример: план аренды −1 250,00 на 25.11, факт −1 250,00 на 27.11 → Δдата 2 ≤ 3, совпало. Страховка −480,00: факт −499,00 → 19,00 ≤ 5 %·480 = 24,00, совпало (+19,00 в калибровку); факт −520,00 → 40,00 > 24,00, но ≤ 48,00 → «возможный двойник», до подтверждения учитываются оба. Инвариант: после матча баланс при d ≥ max(F.date, as_of) меняется ровно на F.amt − P.amt.
**Чем лучше.** PocketSmith — двойной учёт; допуск ≈7,5 % у [Actual](../tools/actual-budget.md) есть только у расписаний; у нас окно по дате и сумме, частичные оплаты, видимый двойник.
**Риски/цена.** Две одинаковые суммы в окне → tie-break и подтверждение.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q1, Q2

### IDEA-03 Жизненный цикл ожидаемого: expected → matched → overdue

**Проблема.** «Клиент не заплатил» — главный источник разрыва у фрилансера; просроченный план висит в прошлом или молча исчезает.
**Идея.** Конечный автомат; прогноз использует *условное* распределение лага («уже просрочен на a дней»).
**Как работает.**

```pseudo
expected --факт в окне--> matched;  expected --date+grace < as_of--> overdue   (grace: расход 0, доход 3 дн)
overdue --факт--> matched (лаг → калибровка);  любое --пользователь--> skipped | moved(d') | cancelled
расход overdue: на as_of;   доход overdue: P.date + q_p({лаги ≥ возраст})   # p50 в expected, p90 в conservative
```

Пример (если 10-20 счёт А ещё не оплачен, возраст 5 дн): лаги клиента [0,3,7,5,14,6,2,9]; из них ≥ 5: [5,6,7,9,14] → p50 = 7, p90 = 14 → ожидание 10-22, консервативно 10-29.
**Чем лучше.** Firefly (ff3e) даёт статусы без прогноза ([страница](../tools/firefly-iii.md)); Float Smart Expected Dates закрыт и без диапазона ([страница](../tools/business-cashflow-tools.md)).
**Риски/цена.** Мало истории → prior (IDEA-27).
**Приоритет** P0 · **Сложность** S · **Вопросы** Q1, Q3

### IDEA-04 Календарные даты без часовых поясов и якоря остатка

**Проблема.** «25-е» — гражданская дата; перевод в моменты сдвигает аренду путешествующего пользователя на сутки, а «сегодня» неявно зависит от часов.
**Идея.** Дата — целое `epoch_day`; `as_of` — явный параметр (локальная дата устройства); баланс — «на конец дня». Якорь (как assertion в hledger) — подтверждённый остаток; проекция стартует от последнего якоря, расхождение показывается, а не прячется.
**Как работает.**

```pseudo
Date = дни с 1970-01-01;  dow(d) = (d + 4) mod 7  (0 = вс);  интервал = d2 − d1
Anchor { account, date, amount_minor };   drift = anchor.amount − Σ posted(≤ anchor.date)
```

Почему часовые пояса не нужны: срок платежа, дата валютирования и налоговое окно — гражданские даты юрисдикции; разность двух дат — целое, а пояс и DST способны лишь сломать «ровно N суток». Время есть только в `recorded_at` (аудит, backtest IDEA-28) и в арифметике не участвует. Граница: planned на `as_of` ещё «впереди», posted уже в остатке.
**Чем лучше.** hledger стартует после последней транзакции ([страница](../tools/plain-text-accounting.md)); PocketSmith сверяет прогноз флагами коррекции ([страница](../tools/pocketsmith.md)).
**Риски/цена.** «Сегодня» берётся с устройства — фиксируется в `inputs_hash`.
**Приоритет** P0 · **Сложность** S · **Вопросы** Q1

### IDEA-05 Правила повторения (RRULE-подобные) и стабильный ключ вхождения

**Проблема.** Firefly создаёт реальные транзакции cron'ом без динамических сумм; расписания Actual зрелы, но без агрегаций; у Budget Guru модель повторов не раскрыта.
**Идея.** Подмножество RFC 5545 плюс расширения; вхождение имеет ключ `(rule_id, nominal_date)`, неизменный при сдвигах; исключения — таблица override по ключу.
**Как работает.**

```pseudo
Rule { freq: D|W|M|Y, interval, by_weekday[], by_monthday[](±), by_workday[](±), start, until|count,
       month_end: clamp|skip|next_first, weekend: keep|prev|next|skip, calendar_id, exdates[] }
nominal(n) = add_months(start, n·interval) с clamp от ИСХОДНОГО дня;   W: start + 7·interval·n
occ(rule,[a,b]): n0 = первый n с nominal(n) ≥ a − shift_max  →  O(k), не O(история)
effective  = overrides[(rule, nominal)] ?? shift(nominal)
```

«Каждые 2 недели» от 2026-10-02: 10-02, 10-16, 10-30, 11-13; «1-е и 15-е» — два правила, а не «раз в 2 недели».
**Чем лучше.** Правило + виртуальные вхождения — у ff3e и Дзен-мани (Reminder/ReminderMarker, [страница](../tools/zenmoney-coinkeeper.md)); override по ключу — как исключение серии в PocketSmith; сумма = центр + коридор (`amount_min/max`, как subscriptions в Firefly).
**Риски/цена.** Размер DSL: держать подмножество, расширять по тестам.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q1, Q2

### IDEA-06 Конец месяца, праздники и n-й рабочий день как данные

**Проблема.** Наивное «+1 месяц от предыдущей даты» даёт дрейф; Actual праздников не учитывает.
**Идея.** Политики конца месяца и сдвига плюс календарь-пакет `Calendar{id, weekend_mask, holidays[]}` — данные, не код.
**Как работает.**

```pseudo
shift(d, policy, cal): keep→d;  next→ min{x ≥ d: is_business(x)};  prev→ max{x ≤ d: is_business(x)};  skip→ drop если не рабочий
is_business(x) = dow(x) ∉ cal.weekend_mask  и  x ∉ cal.holidays
```

31-е от 2026-01-31 → 01-31, 02-28, 03-31, 04-30, 05-31, 06-30 (2028-02-29); наивно — 31→28→28→28. 25.10.2026 — воскресенье: next → 10-26 (пн), prev → 10-23 (пт). «3-й рабочий день» ноября 2026 = 11-04; «последний рабочий» октября = 10-30 (31-е — суббота). Два вхождения в один день суммируются, а не теряются.
**Чем лучше.** Actual — сдвиг без праздников ([страница](../tools/actual-budget.md)); у Firefly 4 варианта выходных, праздничного календаря в docs не найдено ([страница](../tools/firefly-iii.md), не подтверждено).
**Риски/цена.** Кто обновляет календари — пакеты данных с override, без сети (ADR).
**Приоритет** P0 · **Сложность** S · **Вопросы** Q1, Q2

### IDEA-07 Прогноз по дням: два ряда (close и trough) и семантика «к дате»

**Проблема.** Остаток «на конец дня» прячет провал (аренда утром, оплата вечером); PocketSmith и Actual показывают линию, узкую точку ищут глазами.
**Идея.** На каждый день — `close[d]` и `trough[d]` (расходы раньше доходов). «Хватит ли к дате D» — свойство *пути* (минимум на [as_of, D]), а не точки на D.
**Как работает.**

```pseudo
for d in as_of..as_of+H:  trough[d] = bal + Σ out(d);  bal += Σ out(d) + Σ in(d);  close[d] = bal
Q1(D,B) = { min: m = min_{d≤D} trough[d], at: argmin, ok: m ≥ B, first_breach: min d: trough[d] < B, need: max(0, B − m) }
runway_with = первый d с close < 0;   runway_without = то же без входящих
```

Пример (Датасет R, plan): минимум 2 220,00 (10-31); runway_with > 57 дн (горизонт); runway_without: первый минус 2026-11-21 (−210,00), через 48 дн.
**Чем лучше.** Float: низшая точка и runway/buffer, но закрытое B2B, скаляр ([страница](../tools/business-cashflow-tools.md)); Actual узкую точку не выделяет; горизонт не привязан к тарифу, как у PocketSmith.
**Риски/цена.** `trough` пессимистичен, если приход реально утром: режим `intraday` настраивается.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q1

### IDEA-08 Корректность и производительность: инварианты, property-тесты, детерминизм

**Проблема.** «Без округлений и галлюцинаций» у Budget Guru — слова (у автора упомянут Vitest); для денег нужны опубликованные, проверяемые инварианты.
**Идея.** Каждый инвариант — свойство, проверяемое на случайных журналах.
**Как работает.**

| № | Инвариант |
|---|---|
| 1 | Сохранение: `close[d] − close[d−1] = Σ событий дня`; переводы между своими счетами в сумме 0 |
| 2 | Идемпотентность: повторный импорт (id/hash) не меняет состояние; `reconcile∘reconcile = reconcile` |
| 3 | Детерминизм: (`inputs_hash`, `engine_version`, seed) → побайтово тот же вывод; запрещены float для денег, `Date.now`, `Math.random`, порядок обхода Map (сортировка по id) |
| 4 | Локальность: правка события на дату t не меняет `close[d<t]` |
| 5 | Монотонность: добавленный расход не повышает ни один баланс; вердикт Q3 не улучшается с ростом S |
| 6 | Аддитивность дельта-сценариев: `proj(base+Δ) = proj(base)+proj(Δ)` |
| 7 | Волны: каждое значимое обязательство ровно в одной волне; `Σ need_w = Σ обязательств` |
| 8 | Roundtrip: экспорт → импорт даёт тот же `state_hash` |

Реализация: собственный мини-генератор с seed (без зависимостей, по CLAUDE.md), 10³ случайных журналов; дифференциальный тест против `hledger --forecast` на простых журналах (идея, не проверено); суммы ≤ 2⁵³, умножение на курс — BigInt (`assertSafe`).
Сложность (N событий, H дней, M путей): разворот правил O(N), проекция O(N+H) бакетизацией, суффиксные минимумы O(H), ответы Q3 — O(1)/O(log H); правка события — range-add на дереве отрезков за O(log H), ползунок «сумма/дата» без пересчёта; MC — O(M·(N+H)), при M = 2 000, H = 180 порядка 10⁶ операций плюс квантили O(H·M·log M).
**Чем лучше.** Actual держит прогноз за флагом experimental; опубликованных инвариантов расчёта нет ни у кого ([матрица](../comparisons/feature-matrix.md)).
**Риски/цена.** Дисциплина: любой «быстрый хак» с float ломает п. 3.
**Приоритет** P0 · **Сложность** M · **Вопросы** прочее

### IDEA-09 Волны платежей: формальное определение

**Проблема.** У Budget Guru «кластеры» — заявление без правила; PocketSmith, Actual, YNAB дают календарь или список.
**Идея.** Волна — максимальная группа *значимых обязательств*, соседние даты которых разделяет ≤ g дней, а размах < S. Оценочные траты (`estimate`) — фон (burn), события ниже порога — шум.
**Как работает.**

```pseudo
θ = max(abs_min, 1.5 % · O_30);   O = sort_by_date(обязательства ≥ θ)       # O_30 — обязательства за 30 дн
for e in O: если wave и e.date − wave.end ≤ g и e.date − wave.start < S: wave.add(e) иначе new_wave(e)   # g=3, S=10
значима: κ_w = (need_w / O_30) / (span_w / 30) ≥ 2;   устойчива: ≥ 2 из 3 последних месяцев с тем же окном дней
```

Пример (Датасет R): обязательства 10-20 (1 030,00), 10-26 (1 430,00), 10-28 (480,00), O_30 = 2 940,00; разрыв 20→26 = 6 > g → W1 = {10-20}, W2 = {10-26, 10-28}. κ(W1) = (1 030/2 940)/(1/30) = 10,5; κ(W2) = (1 910/2 940)/(3/30) = 6,5. Подписка 12,00 на 10-23 < θ = max(30,00; 44,10) — шум, W1 и W2 не склеивает. «Зарплатный цикл» при нерегулярном доходе: [крупное поступление i, i+1) со своим `cycle_need`.
**Чем лучше.** Правила кластеризации нет нигде; у Float — недельная сетка 13-week ([страница](../tools/business-cashflow-tools.md)).
**Риски/цена.** g, S, θ — настройки; нужна проверка на реальных журналах.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q2

### IDEA-10 Метрики волны: нужно к волне, покрытие, дефицит

**Проблема.** «Сколько нужно к каждой волне» заявлено лендингом, но не определено; числа «нужно к дате» нет ни у кого.
**Идея.** «Нужно к волне» = пиковая просадка внутри волны + буфер, сравнение с деньгами на начало.
**Как работает.**

```pseudo
R_w = max_{d∈[s,e]} Σ_{u=s..d} (out(u) − in(u))      # все потоки внутри волны, включая фон
need_w = R_w + B;   cash_w = close[s−1];   coverage_w = ⌊1000·cash_w / need_w⌋ ‰;   gap_w = max(0, need_w − cash_w)
```

Пример (B = 882,00): W2 — R = 1 430,00 + 480,00 = 1 910,00, need = 2 792,00; plan: cash = 4 340,00 → 1 554‰, gap 0; conservative: cash = 2 540,00 → 909‰, gap = 252,00 (= B − 630,00). W1: R = 1 030,00, need = 1 912,00; plan: cash = 5 580,00 → 2 918‰; conservative: cash = 3 780,00 → 1 976‰. Рядом — состав «из них зарезервировано под волну» (IDEA-15).
**Чем лучше.** Float/Xero — низшая точка и buffer, не «нужно к дате»; PocketSmith — календарь.
**Риски/цена.** Налог и аренда подряд: границы подбирать по реальным данным.
**Приоритет** P0 · **Сложность** S · **Вопросы** Q2

### IDEA-11 «Могу ли я купить?»: вердикт и узкая точка

**Проблема.** Вердикт Budget Guru («Да, спокойно», минимум €7 600) — заявление с противоречием скриншоту; пороги неизвестны. У PocketSmith минимум читают глазами.
**Идея.** Покупка (D, S) — гипотетическое событие; ответ — структура. Классы: **NO** (expected: trough_after < 0), **TIGHT** (0 ≤ … < B), **FRAGILE** (expected ≥ B, conservative < B), **OK** (оба ≥ B). Это ликвидность по правилам пользователя, не совет «покупать».
**Как работает.**

```pseudo
M[d] = min_{t≥d} trough[t]                  # суффиксный минимум, один раз за O(H)
trough_after(D,S) = M[D] − S                # покупка влияет только на t ≥ D
ответ = { trough_before, trough_after, at, margin = trough_after − B, delta, verdict_exp, verdict_cons, verdict }
```

Пример: дорожка 1 100,00 на D = 2026-10-12, B = 882,00. plan/expected: до 2 220,00 (10-31), после 1 120,00 ≥ B. Conservative: до 630,00 (10-28, уже ниже B), после −470,00. Итог **FRAGILE**: «безопасно, только если клиент А заплатит не позже 10-28»; виновники — IDEA-29.
**Чем лучше.** PocketSmith — what-if без авто-минимума ([страница](../tools/pocketsmith.md)); Float — низшая точка без вердикта; Simplifi — what-if заявлен, в справке не описан ([страница](../tools/modern-saas-trackers.md)); класса FRAGILE нет нигде.
**Риски/цена.** Вердикт ≠ совет: формулировки нейтральны.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q3

### IDEA-12 Максимальная сумма «сейчас» и самая ранняя безопасная дата

**Проблема.** Да/нет заставляет перебирать суммы и даты руками; ответа «когда смогу» нет ни у кого.
**Идея.** Из того же `M[d]` — ответы (б) и (в).
**Как работает.**

```pseudo
S_max(D) = max(0, M[D] − B)                 # (б); D = as_of — «прямо сейчас»
d*(S)   = min{ d : M[d] − S ≥ B }           # (в); M не убывает по d → бинарный поиск; нет → «в горизонте нет»
```

Пример: S_max(сейчас) = 2 220,00 − 882,00 = 1 338,00 (expected) и 0 (conservative: 630,00 < B). d*(1 100,00): expected — сегодня; conservative — 2026-10-30 (на 10-29 режим trough даёт 630,00: расходы раньше прихода). Ползунок в UI — O(1) на сдвиг.
**Чем лучше.** Budget Guru — только да/нет (заявление); PocketSmith — перебор сценариев; Actual и hledger не умеют.
**Риски/цена.** «Дата» опирается на допущения о поступлениях — режим показывается рядом.
**Приоритет** P0 · **Сложность** S · **Вопросы** Q3

### IDEA-13 Буфер и режимы расчёта

**Проблема.** «Безопасный минимум» отсутствует или зашит; режимы «консервативный/ожидаемый» не определены.
**Идея.** `B = max(B_abs, B_days · burn)`, `burn` — средние расходы за окно без помеченных `exceptional`, `B_days` = 7. Режим — пакет параметров, одинаковый для Q1, Q2, Q3 и safe-to-spend.
**Как работает.**

| Параметр | plan | expected | conservative |
|---|---|---|---|
| Даты поступлений | как введены | + лаг p50 | + условный лаг p90 |
| Внутри дня | close | close | trough |
| Часы | план | план × ρ | минимум |
| Курс будущих поступлений | spot | spot | spot × (1 − h) |
| Оценочные траты | план | × ratio p50 | × ratio p90 |

Пример: расходы 05.10–03.11 = 3 780,00 → burn = 126,00; B = 7 × 126,00 = 882,00.
**Чем лучше.** Float/Xero показывают runway и buffer в днях ([страница](../tools/business-cashflow-tools.md)); у нас буфер — параметр запроса во всех формулах.
**Риски/цена.** Пустая история: burn берётся из обязательств.
**Приоритет** P0 · **Сложность** S · **Вопросы** Q1, Q3

### IDEA-14 Покупка как план платежей: рассрочка, части, карта

**Проблема.** Покупка редко одним платежом; Loan Planner YNAB — what-if только для долгов ([страница](../tools/ynab.md)).
**Идея.** `purchase` — список (дата, сумма); рассрочка 0 % делит сумму largest remainder; влияние — `min_t (bal[t] − cum[t])`, горизонт растягивается до последнего платежа.
**Как работает.** `part_k = ⌊S/n⌋ + (k < S mod n ? 1 : 0)` в minor units.
Пример: 1 100,00 / 6 = 183,34 ×2 + 183,33 ×4; первый платёж 11-01. Expected: минимум в горизонте 2 220,00 − 183,34 = 2 036,66 (11-01) ≥ B. Conservative: узкая точка 630,00 (10-28) раньше первого платежа — `delta` = 0, но исходная хрупкость остаётся → FRAGILE.
**Чем лучше.** `delta` отделяет вклад покупки от исходного состояния; what-if из графика платежей нет нигде.
**Риски/цена.** Проценты рассрочки — через IDEA-22.
**Приоритет** P1 · **Сложность** S · **Вопросы** Q3

### IDEA-15 Safe-to-spend: резервы, горизонт, без двойного счёта

**Проблема.** Safe Balance PocketSmith (beta с 2016) = факт + неполученный доход − неистраченные бюджеты категорий; YNAB отвечает «сейчас»; у Budget Guru не описан.
**Идея.** «Свободно» зависит от горизонта T и времени: обязательство — либо поток в окне, либо резерв за окном, но не оба.
**Как работает.**

```pseudo
Res(t) = Σ_{r: due_r > T} max(funded_r(t), required_r(t))     # sinking, налоговые конверты, долги за окном
STS(T) = max(0, min_{t∈[as_of,T]} (bal_mode[t] − Res(t)) − B)
required_r(t) = funded_r + просроченные взносы по графику (нельзя тратить «в долг у цели»)
```

Пример (T = 11-03, plan): резервы — цели 135,00 + налоговая аллокация 360,00 (20 % от 1 800,00 при поступлении 10-15) + взносы 01.11 (375,13) = 870,13; min(bal − Res) = 2 220,00 − 870,13 = 1 349,87; STS = 1 349,87 − 882,00 = **467,87**. Conservative: на 10-28 bal 630,00 − 135,00 = 495,00 < B → STS = 0, до буфера не хватает 387,00. Отложенное под налог 10-20 (в окне) не вычитается: оно уже поток. Горизонт: 30 дн / конец месяца / следующий *надёжный* доход (p80 лага).
**Чем лучше.** PocketSmith — по категориям, без дат; hledger — «факт минус виртуальные счета» без времени ([страница](../tools/plain-text-accounting.md)).
**Риски/цена.** Отрицательную «свободу» показывать как «не хватает до буфера X».
**Приоритет** P0 · **Сложность** M · **Вопросы** Q3, прочее

### IDEA-16 Налоговый конверт: версионируемые правила и резерв при поступлении

**Проблема.** Полноценно — только у налоговых сервисов (Found Taxes Pocket, Profit First), но резерв не связан с прогнозом; PocketSmith — ручной перевод процента; у hledger авто-проводки только с `--auto`; у Budget Guru — «правила по датам» (заявление).
**Идея.** Правило — данные пользователя с версиями; поступление порождает *виртуальную аллокацию* (баланс счёта не меняется); при уплате резерв высвобождается, разница (true-up) падает на свободные деньги.
**Как работает.**

```pseudo
TaxRule { id, version, kind, rate_bp, base: gross|net_of_vat|profit_ytd, valid_from, valid_to,
          windows[{from_md,to_md}], rounding: half_even|half_up|floor }
on income(e):  r = rule_at(e.date);  a = round(base(e)·r.rate_bp / 10000);  allocate(env[r], a, r.version)
on payment(p): released = min(funded, p.amt);  true_up = p.amt − released → свободные деньги
```

Пример (статья): пришло 3 000,00, `rate_bp` = 2000 → 600,00 (300000·2000/10000 = 60000). Дробно: 1 234,57 · 2100 bp = 259,2597 → 259,26 (half_up). История правилом задним числом не переписывается (`rule_version` в аллокации); смена ставки — сценарий «а что если 22 %». Почему аллокация, а не перевод: не нужен отдельный счёт, нет расхождения с банком; «зеркальный» перевод — обычный transfer, сверяемый с резервом. Расчёт по введённым правилам, не консультация.
**Чем лучше.** Found и Profit First откладывают без связи с прогнозом ([страница](../tools/freelancer-tax-tools.md)); у нас резерв входит в safe-to-spend, платёж — в волну.
**Риски/цена.** Риск «налогового совета»: поставлять только пустые формы правил (ADR).
**Приоритет** P0 · **Сложность** M · **Вопросы** прочее (налоги), Q3

### IDEA-17 Квартальные авансы и IVA: накопительные формулы, окна дат

**Проблема.** Аванс зависит от прибыли с начала года, IVA — не доход; в Испании окна 1–20 апр/июл/окт и 1–30 янв ([страница](../tools/freelancer-tax-tools.md)).
**Идея.** Режимы `CUM_PROFIT_ADVANCE` и `VAT_NET` как данные; платёж ставится в окно (`pay_on`: first / last / fixed, по умолчанию last), пересчёт после каждой операции, оценка диапазоном.
**Как работает.**

```pseudo
CUM_PROFIT_ADVANCE:  pay_Q = max(0, rate·profit_YTD − Σ prev_payments − withholdings − deduction)
VAT_NET:             due = collected − paid (+ перенос; минус переносится или возвращается по правилу)
```

Пример (суммы введены пользователем): прибыль с начала года 24 000,00 − 6 000,00 = 18 000,00; 20 % = 3 600,00; прошлые платежи 2 980,00 → 620,00. IVA: 1 960,00 − 1 550,00 = 410,00. Оба — события 10-20 (волна W1 Датасета R). Диапазон — по min/exp/max дохода (IDEA-18).
**Чем лучше.** Hurdlr и QuickBooks оценивают налог, но платёж не в общей волне; испанские сервисы называют модели 303/130, но не показывают их рядом с арендой.
**Риски/цена.** Правила меняются: версии и `valid_from/to`, никаких ставок по умолчанию.
**Приоритет** P1 · **Сложность** M · **Вопросы** Q2, прочее (налоги)

### IDEA-18 Почасовой и нерегулярный доход: ставка × часы с лагом выплаты

**Проблема.** Ни у одного продукта ставка × часы не питает прогноз; Budget Guru заявляет «ставку, норму часов» и показывает алерт «недоработка 8 ч» (маркетинговый скриншот).
**Идея.** `IncomeStream{rate, currency, hours{min,exp,max}, period, cutoff, pay_lag, overtime{threshold, mult_bp}, bonus[]}`; часы — целые минуты; выплата — planned-событие на `cutoff + pay_lag` со сдвигом по IDEA-06; факт часов заменяет план.
**Как работает.**

```pseudo
gross = round_half_even( rate · (min(h,T) + (h − T)⁺ · mult_bp/10⁴) / 60 )     # h в минутах, округление один раз за период
est_h = actual_h + remaining_plan_h · ρ        # ρ = EWMA(actual/plan), зажат в [0.5, 1.5]
range = { gross(min_h), gross(est_h), gross(max_h) }
```

Примеры: ставка 45,00; октябрь 64 ч → 2 880,00; min/max 48/76 ч → 2 160,00 / 3 420,00; счёт 31 окт, NET-5 → 5 ноября. Переработка: 46 ч за неделю, порог 40, ×1,5 → 1 800,00 + 405,00 = 2 205,00. Факт: к 20 окт план 38 ч, сделано 30 → «недоработка 8 ч» = 360,00; ρ = 0,9, остаток плана 26 ч → 30 + 26·0,9 = 53,4 ч → 2 403,00 вместо 2 880,00.
**Чем лучше.** Float моделирует счета, не ставки; PocketSmith — ручная правка события ([страница](../tools/pocketsmith.md)); hledger хранит часы (`timeclock`), но не переводит в деньги.
**Риски/цена.** Ввод часов — дисциплина пользователя; без факта работают план и диапазон.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q1, прочее (доход)

### IDEA-19 Мультивалютность: две ноги, курс операции, крипта

**Проблема.** Actual — «currency agnostic», YNAB — отдельные планы, Monarch/Copilot/Simplifi смешивают «$» ([страница](../tools/modern-saas-trackers.md)); Budget Guru заявляет «фактический курс операции» (не проверено).
**Идея.** Сумма хранится в валюте счёта; при обмене — две ноги и выводимый курс (рациональное число). Рыночные курсы — отдельно, оценка — политика `then/end/now`. Умножения — BigInt, округление half-even. Крипта: `exponent` 8 (BTC в сатоши), по умолчанию неликвидна: в прогнозе с haircut 30 %, из safe-to-spend исключена.
**Как работает.**

```pseudo
FxRate { date, base, quote, num, den };   implied = leg_b / leg_a
convert(a, r) = round_half_even( BigInt(a) · r.num / r.den )          # 10¹² · 10¹⁰ > 2⁵³ → без BigInt нельзя
```

Пример: продано $2 000,00, получено €1 842,40 → 184240/200000 = 0,9212. 0,0015 BTC = 150 000 сат при цене 50 000,00 (5 000 000 minor) → 7 500 = €75,00.
**Чем лучше.** hledger (`@`/`@@`, `P`, `--value`) — лучшая модель, но без прогноза ([страница](../tools/plain-text-accounting.md)); Firefly — foreign amount и пересчёт в primary ([страница](../tools/firefly-iii.md)); у нас всё внутри прогноза.
**Риски/цена.** Курсы без сети: ручной ввод и опциональные пакеты.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q1, прочее (валюты)

### IDEA-20 Политика курса будущих поступлений и сценарий курса

**Проблема.** PocketSmith пересчитывает бюджеты по текущему курсу; будущий USD-доход на EUR-счёт — самая волатильная часть прогноза.
**Идея.** Политика на поток: `native` (по умолчанию: вектор остатков по валютам, свёртка только для показа), `spot`, `adverse` (conservative: доходы × (1 − h), расходы × (1 + h), h — квантиль исторической волатильности горизонта), `scenario` (множитель в bp). Платёж в чужой валюте — событие в валюте счёта по курсу на дату оплаты.
**Как работает.** `eur = round(usd · rate · mult_bp / 10⁴)`.
Пример: $2 000,00 на 13 ноября, spot 0,9250 EUR/USD → 185 000 = €1 850,00; −5 % (9 500 bp) → 175 750 = €1 757,50 (−92,50).
**Чем лучше.** У PocketSmith и SaaS-трекеров курсового риска в прогнозе нет; у нас он — параметр режима и источник возмущения в MC (IDEA-24).
**Риски/цена.** h требует истории курсов; без неё — ручной коэффициент.
**Приоритет** P1 · **Сложность** M · **Вопросы** Q1, Q3

### IDEA-21 Sinking funds: ceil-взносы, догон, два режима

**Проблема.** Годовые платежи «удивляют» (статья); YNAB Targets, Monarch Non-monthly, шаблоны Actual зрелы, но взносы не поданы слоем прогноза, догона нет.
**Идея.** Взнос = ceil(остаток / оставшиеся периоды), пересчёт каждый период (сумма точно равна цели, разброс ≤ 1 ед.); режимы `refill_to_target` и `fixed`; пул делится largest remainder; взносы — виртуальные аллокации (IDEA-15), не расходы.
**Как работает.**

```pseudo
c_k = min(ceil(rem_k / (n − k)), rem_k);   rem_{k+1} = rem_k − c_k
largest_remainder(total, w): floor-доли, остаток r раздать по убыванию дробных частей (tie: id)
```

Пример (старт 04.10, взнос 1-го числа, периоды строго до due): зал 360,00 до 15.01 → 3 × 120,00; дни рождения 250,00 до 10.03 (есть 40,00) → 5 × 42,00; отпуск 1 800,00 до 01.07 (есть 95,00): 1 705,00 / 8 → 213,13 ×4 + 213,12 ×4. На 01.11: 120,00 + 42,00 + 213,13 = 375,13. Режим `fixed` 150,00/мес на отпуск: к 01.07 будет 95,00 + 8·150,00 = 1 295,00, не хватит 505,00; цель достигнется за 12 мес. Пул 375,00 по весам 12 000 : 4 200 : 21 313 → 119,96 / 41,98 / 213,06 (Σ = 375,00).
**Чем лучше.** YNAB — ceil и режимы ([страница](../tools/ynab.md)) без пулов и догона; Actual — `by/up to` в experimental ([страница](../tools/actual-budget.md)).
**Риски/цена.** Поздний старт даёт непосильный взнос → предупреждение с числами, без советов.
**Приоритет** P0 · **Сложность** S · **Вопросы** Q3, прочее (резервы)

### IDEA-22 Долги и рассрочки: график, не расходящийся с реальностью

**Проблема.** График калькулятора расходится с банком (округления, дата, комиссии); Budget Guru заявляет «долг и рассрочку с графиком».
**Идея.** Контрактный график (введён или рассчитан) + модельный; после каждого платежа — ре-якорение по наблюдаемому остатку; дрейф сверх допуска — алерт; последний платёж поглощает остаток округлений.
**Как работает.**

```pseudo
i = rate_bp/10⁴/12;  A = round(P·i / (1 − (1+i)^−n));  int_k = round_half_even(bal·i);  last = bal + int
после posted-платежа: bal ← observed_outstanding (если задан); перегенерировать будущие
prepay(X, d, shorten|lower_payment): bal ← bal − (X − accrued_interest(d)); перегенерировать
```

Пример: 1 200,00, 12 % годовых (1 %/мес), 6 мес.: A = 207,06 (точно 207,058); платежи 207,06 ×5 + 207,05; проценты 12,00; 10,05; 8,08; 6,09; 4,08; 2,05 = 42,35. Дифференцированный: 212,00; 210,00; 208,00; 206,00; 204,00; 202,00 (проценты 42,00). Досрочно 300,00 после 2-го платежа (остаток 807,93): shorten — 3 платежа вместо 4, проценты 9,16 вместо 20,30; lower_payment — 4 платежа по 130,17.
**Чем лучше.** У YNAB what-if только для долгов; hledger — периодические правила без амортизации; ре-якорения по факту нет нигде.
**Риски/цена.** Нестандартные договоры (комиссии, плавающая ставка) — списком платежей.
**Приоритет** P1 · **Сложность** M · **Вопросы** Q1, прочее (долги)

### IDEA-23 Сценарии как наборы параметров и дельта-слои

**Проблема.** PocketSmith — дельта-сценарии без авто-итога; Float — до 8 сценариев в закрытом SaaS; у Budget Guru только «с/без единоразовых».
**Идея.** Сценарий = {режим (IDEA-13), набор hypothetical-событий, переопределения правил}; копий данных нет. Сравнение — два ряда и таблица Δmin, Δ`close` на дату; слияние = превращение hypothetical в planned. Базовые три: base (plan/expected), pessimistic (conservative), optimistic (лаг p10, часы max, курс +h).
**Как работает.** Аддитивность (IDEA-08, № 6): `proj(base+Δ) = proj(base)+proj(Δ)` — быстрый пересчёт без полной проекции.
**Чем лучше.** Дельта с авто-минимумом, которого нет у [PocketSmith](../tools/pocketsmith.md); не облачный B2B, как [Float](../tools/business-cashflow-tools.md).
**Риски/цена.** Взрыв числа сценариев → лимит и имена.
**Приоритет** P0 · **Сложность** S · **Вопросы** Q1, Q3

### IDEA-24 Монте-Карло с воспроизводимым seed и общими случайными числами

**Проблема.** Интервалов неопределённости нет ни у одного личного продукта: у Float скалярный Forecast Confidence, у стороннего DzenAnalytics — коридор оптимист/пессимист ([страница](../tools/zenmoney-coinkeeper.md)); Monte Carlo в Actual — про пенсионные накопления.
**Идея.** Параметры — распределения из данных пользователя: лаг клиента (bootstrap из его лагов, иначе prior), часы (треугольное min/mode/max), курс (лог-нормальное по σ), коэффициент оценочных трат (bootstrap actual/plan), сумма счёта (min/max). Генератор без состояния: `u = hash(seed, event_id, path)` — правка одного события не перемешивает остальные, сценарии сравниваются на *общих* путях (CRN): разность не содержит шума выборки.
**Как работает.**

```pseudo
seed = H(engine_version, inputs_hash, user_seed)
for p in 0..N−1: возмутить события (u(seed,id,p)); path_p = project(…)           # O(N+H)
P10/P50/P90[d] = nearest_rank(sort_p(close_p[d]));   p_gap[d] = #{p: trough_p[d] < 0}/N
p_gap_any = #{p: min_d trough_p[d] < 0}/N          # ≠ max_d p_gap[d]
```

Пример (точный, без выборки): 8 лагов клиента А, каждый 1/8. Минимум Датасета R = 630,00 при лаге 14 (12,5 %), 2 220,00 при остальных (87,5 %). С дорожкой 1 100,00: −470,00 (12,5 %) / 1 120,00; P(разрыв) = 12,5 %. MC при N = 2 000 даёт 12,5 % ± 0,7 п.п. (√(p(1−p)/N)). Цена: порядка 10⁶ операций, десятки мс в Web Worker.
**Чем лучше.** Нет ни у кого среди изученных; воспроизводимость (seed + CRN) и опора на лаги самого пользователя.
**Риски/цена.** Ложная точность: мало истории → широкие prior'ы и пометка «оценка».
**Приоритет** P1 · **Сложность** L · **Вопросы** Q1, Q3

### IDEA-25 Вероятностный Q3: допуск риска α

**Проблема.** «Безопасно» без вероятности либо слишком осторожно, либо слепо.
**Идея.** Брать квантиль *минимумов путей*, а не минимум квантилей по дням: P10 в разные дни относится к разным путям и занижает риск.
**Как работает.**

```pseudo
m_p = min_{t≥D} trough_p[t];   Q_α = nearest_rank_α(sort(m_p))
OK(α) ⇔ Q_α − S ≥ B;   S_max(α) = max(0, Q_α − B);   p_fail(S) = #{p: m_p − S < B}/N
```

Пример (8 лагов): α = 10 % → Q = 630,00, S_max = 0; α = 15 % → Q = 2 220,00, S_max = 1 338,00; p_fail(1 100,00) = 12,5 %. CRN делает S_max монотонным по α, а p_fail — по S: ползунок не «мигает».
**Чем лучше.** Float и PocketSmith дают одну траекторию; вероятностного Q3 нет нигде.
**Риски/цена.** Скачки на малых N → N ≥ 2 000 и округление p до 1 п.п.
**Приоритет** P1 · **Сложность** M · **Вопросы** Q3

### IDEA-26 Подача диапазонов без паники

**Проблема.** P10/P90 пугают, «80 % вероятно» неясно, красный цвет приучает игнорировать.
**Идея.** (1) Заголовок = ответ + одна причина + одно действие; (2) слова-пороги: < 1 % «практически нет», 1–5 % «маловероятно», 5–20 % «возможно», 20–50 % «вероятно», > 50 % «скорее да», цифры по раскрытию; (3) веер 80 % (P10–P90), а не min/max; (4) красный — только детерминированный разрыв в expected или p_fail ≥ 20 %, иначе жёлтый «хрупко»; (5) риск привязан к дате, виновнику и ближайшей безопасной дате; допуск α — настройка «осторожности». Без советов.
**Как работает.** Шаблон (числа подставляет движок): «Дорожка 1 100,00 на 12.10: по плану минимум 1 120,00 (31.10). Возможно (12 %) просадка до −470,00 28.10, если клиент А задержит платёж на 14 дней. Безопасная дата в этом случае — 30.10.»
**Чем лучше.** Одиночный балл Float без формулы; коридор DzenAnalytics без вероятностей.
**Риски/цена.** Пороги слов — продуктовое решение, тестировать на пользователях.
**Приоритет** P1 · **Сложность** S · **Вопросы** Q1, Q3

### IDEA-27 Калибровка по факту: лаги и коэффициенты

**Проблема.** «Система учится на реальных задержках» (идея 6 из STATE.md) — механизм не определён; Float Smart Expected Dates закрыт.
**Идея.** Ключ потока (клиент/правило/категория) → наблюдения `lag = F.date − P.date`, `ratio = F.amt/P.amt` (bp). Окно 12–24; квантили nearest-rank для лагов (p50/p80/p90), EWMA (α = 0,3) для дрейфа коэффициентов, сжатие к prior: λ = n/(n+3), `ĥ = λ·медиана + (1−λ)·prior`.
**Как работает.** Хранится набор наблюдений (он же выборка для bootstrap в IDEA-24), не параметры; всё локально.
Пример: лаги [0,3,7,5,14,6,2,9] → sorted [0,2,3,5,6,7,9,14]: p50 = 5, p80 = 9, p90 = 14; EWMA = 6,3; prior 7, n = 8: λ = 8/11 → 5,5 ≈ 6 дн. Новый клиент, n = 2, лаги [10,12] (медиана 11): λ = 0,4 → 0,4·11 + 0,6·7 = 8,6 ≈ 9 дн.
**Чем лучше.** Формула и выборка видны пользователю; «Smart» у Float — чёрный ящик.
**Риски/цена.** Выбросы (болезнь клиента) → пометка «исключить наблюдение».
**Приоритет** P1 · **Сложность** M · **Вопросы** Q1, Q3

### IDEA-28 Backtest «что предсказали месяц назад»

**Проблема.** Forecast Confidence у Float — балл без опубликованных границ; флаги коррекции PocketSmith сверяют прогноз с банком, агрегированной метрики не найдено.
**Идея.** Журнал append-only с `recorded_at` даёт *as-of replay*: `state_at(t0)` = записи с `recorded_at ≤ t0` и версии правил на t0 — честный прогноз «как знали тогда», задним числом внесённые факты его не портят.
**Как работает.**

```pseudo
MAE(h) = mean_t |F_t(t+h) − A(t+h)|;   bias(h) = mean_t (F − A)
coverage80 = доля A(d) ∈ [P10,P90] (цель 0,80);   skill(h) = 1 − MAE(h)/MAE_naive(h)   # naive: баланс не меняется
gap recall/precision: p_gap ≥ 20 % ↔ реальный минус
```

Индекс доверия = coverage80 и skill, формула открыта; список промахов — по событиям (лаги, суммы, пропущенное). Иллюстрация: из 21 проверенного дня факт попал в P10–P90 в 17 → 81 % при цели 80 %; ниже — MC расширяется (пересчёт σ).
**Чем лучше.** Воспроизводимый backtest с открытой формулой — нет ни у Float, ни у PocketSmith.
**Риски/цена.** Нужна история ≥ 2–3 месяцев; до тех пор метрика скрыта.
**Приоритет** P2 · **Сложность** M · **Вопросы** Q1

### IDEA-29 Объяснимость: цепочка виновников и контрфакты

**Проблема.** «Почему именно такая узкая точка?» — Budget Guru показывает цифру; ассистент без evidence может выдумать причину.
**Идея.** Каждый расчёт возвращает evidence: события-источники и контрфакты, вычисленные *движком* (leave-one-out), а не LLM.
**Как работает.**

```pseudo
(t*, m*) = argmin trough;  chain = события в (peak_date, t*], по убыванию |суммы|, накопленная доля ≥ 90 %
for e in top_k(chain): Δ_e = min(project(без e)) − m*                          # O(k·H)
evidence = { claim, value, date, event_ids[], rule_versions, scenario, inputs_hash, engine_version }
```

Пример (conservative, t* = 10-28, m* = 630,00): из 4 200,00 ушло 3 570,00 — аренда 1 250,00 (35,0 %), продукты ×3 630,00 (17,6 %), налог «130» 620,00 (17,4 %), страховка 480,00 (13,4 %), налог «303» 410,00 (11,5 %), ЖКХ 180,00 (5,0 %). Контрфакты: клиент А платит 10-15 → минимум 2 220,00 (+1 590,00); без страховки — 1 110,00, узкая точка переезжает на 10-26. Каждое число в ответе ассистента обязано быть в evidence (верификатор — в [предложении по архитектуре](proposal-architecture.md)).
**Чем лучше.** Цепочки причин с контрфактами нет нигде; у Float видны «причины» низшей точки без контрфактов (вывод, [страница](../tools/business-cashflow-tools.md)); у Budget Guru не показано.
**Риски/цена.** Много событий — сворачивать по правилам и категориям.
**Приоритет** P0 · **Сложность** M · **Вопросы** Q1, Q2, Q3
